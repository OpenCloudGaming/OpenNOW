# Fallbacks and recovery decisions

The supplied client has several unrelated fallback mechanisms. Automatic codec selection is not the same as rebuilding a failed decoder; endpoint retry is not alliance switching; an HTTP-backend swap is not a media-transport downgrade. The table separates the decisions actually traced from the paths that remain unknown.

## Observations that are not proven fallback policies

**S.** `fallbackToLogicalResolution`, recording fallback query names, RTP receiver-fallback symbols, and various bundled third-party fallback implementations are present. Their presence is not a proven branch condition, policy priority, default, or successful recovery. The configuration catalog deliberately records names without assigning those semantics.

**I.** The VT frame object's reported range and Metal's fourcc-derived range can differ in the traced path. [color.md](color.md) describes the evidence. That candidate inconsistency is not an established image-fidelity bug and does not justify a workaround without further caller/runtime checks.

**U.** The study does not establish every reconnect/resume policy, GPU-device-loss path, decoder drain, audio-device reopen, recording fallback, native-media proxy behavior, provider failover, or cross-domain fallback precedence. It also does not establish that any particular live session chooses the inspected optional paths.

## Compatibility recommendation

Give each recovery decision its own typed state and failure reason. Keep accepted session settings distinct from saved preferences, propagate sender-authored identifiers through recovery, and release queued media/input resources explicitly. Do not copy the vendor's unchecked ring writes, ambiguous callback types, or unbounded thread-join behavior into OpenNOW merely to imitate the binary. The findings identify compatibility boundaries; they do not authorize changes to OpenNOW's current behavior.
