Session & CloudMatch

Session creation and CloudMatch orchestration

This note records how the official GeForce NOW Linux x86_64 Flatpak creates a cloud seat and hands it to the native streamer, then maps that path onto OpenNOW. The evidence is the unpacked Flatpak commit 235a800084abb2246e4578e5b60c33397fac73152c02a5751e663ddafd00e260, the CEF tree under files/cef, string and symbol extracts under /workspace/audit/gfn-official/extracts/, and the OpenNOW owners native/opennow-core/src/cloudmatch.rs, native/opennow-core/src/streamer.rs, and docs/core-protocol.md.

The binaries are stripped ELF objects. Exported C symbols, demangled C++ symbols, and adjacent read-only strings are reliable. Integer enum values are reliable only where OpenNOW already treats them as a live CloudMatch contract. Where a string table is a contiguous Unknown … run, this note treats the names as the vendor vocabulary and does not invent indexes from file order.

Build and process split

Flatpak metadata names the app com.nvidia.geforcenow, runtime org.freedesktop.Platform/x86_64/24.08, and command GeForceNOW. The runtime is granted network, IPC, X11, Wayland, PulseAudio, session and system buses, all devices including DRI, and the Gamescope Vulkan layer. Environment variables ENABLE_GAMESCOPE=1, ENABLE_GAMESCOPE_HDR=1, and GAMESCOPE_HDR=1 are set in the manifest, so HDR and Gamescope are part of the packaged Linux session environment rather than a user preference.

The mall config that ships beside the shell, files/mall/shared/assets/config/config.json, identifies itself as official release build 2.0.84.127. The CEF shell string table carries Chromium 128.4.13+ge76af7e+chromium-128.0.6613.138.nv27, product path gfn_release/2f4a4c46, and Jenkins sources under GFN-cx-lin-official/client/cef. Geronimo and Bifrost debug paths both sit on Perforce branch gs_04_87 (/dvs/p4/build/sw/gcomp/rel/gs_04_87/...). Geronimo is linked against the Mjolnir vcpkg snapshot dated 2025.04.09 (gRPC 1.71.0, OpenTelemetry C++ 1.16.1).

GeForceNOW does not talk to CloudMatch itself. It hosts the mall at a relative URL, receives JavaScript queries, and forwards them into GridApp. Source paths burned into the shell make that boundary explicit: client/cef/src/gfn/simple_grid_app.cc, simple_grid_app.h, gfn_query_handler.cc, gfn_sdk_connector.cc, gfn/serenity/serenity.cc, and gfn/serenity/rtsp_handler.cc. Shell logs say “Browser app is initializing Geronimo”, “Creating grid app”, “Geronimo GRID Init”, then later “QUERY_GFN_PREPARE values, Server:” and “QUERY_GFN_START values, Server:”.

The live chain is:

  1. Mall Angular code in files/mall/main.*.js and 923.*.js builds a start-parameter object from appConfig.streamer and the selected game.
  2. The page issues a CEF query (QUERY_GFN_PREPARE, QUERY_GFN_START, QUERY_GFN_RESUME, and the rest of the QUERY_GFN_* set).
  3. simple_grid_app calls GridApp::prepare, start, resume, stop, pause, cancel, getActiveSessions, or getSessionInfo.
  4. GridApp owns a SessionControl::SessionController created by SessionControl::createSessionController.
  5. The controller calls the exported nvb* API in libBifrost2.so.
  6. NVB::GridServer performs HTTPS against https://<host>:<port>/v2/session and /v2/serverInfo, polls until the seat is usable, then Geronimo calls nvbStartStreaming with the connection list.

OpenNOW collapses steps 2 through 6. opennow-core speaks CloudMatch over reqwest, normalizes the seat, and streamer.prepare / streamer.start attach the in-process NVST runtime. There is no CEF query bus and no nvb* call.

libBifrost2 NVB API

nm -D on libBifrost2.so exports one C session surface plus a small C++ HTTP helper. The C entry points, in the order they appear in the dynamic symbol table, are:

The C++ helpers are nvbutil::WebRequest (create, cancel, getResponse, getRedirectURL, getLocalAddress, getError, getStatus, HttpDecomposeUrl, reconfigureHttpClient, ErrorToString) and nvbutil::Network (startup(bool, bool), shutdown). WebRequest can be constructed from either NVbClientImpl* or nvbutil::Network*. The library’s own NEEDED list is only libpthread, libdl, libatomic, libstdc++, libm, libgcc_s, and libc, with RUNPATH ./. TLS, JSON, and HTTP are compiled in.

Log strings document the argument checks the SDK actually enforces:

  • nvbCreateClient failure is reported by Geronimo as “Failed to create nvbClient” / GERONIMO_GRIDAPP_CREATE_CLIENT.
  • nvbRegisterCallback rejects a null NVbCallback.callback.
  • nvbInitializeClient rejects an invalid profile, a server type that cannot be initialized synchronously, a bad NVbClientInitParams, and a second initialization. Success logs “NVbClient successfully initialized. Server type: %d, supported authentication types: %d”.
  • nvbSetAuthInfo rejects a null or empty token and an invalid auth type.
  • nvbSetAvailableInputDevices rejects a null list and any device index at or beyond NVB_DEVICE_MAX_TYPE.
  • nvbGetServerInfo rejects bad NVbServerParams.
  • nvbStartSession requires NVbSessionParams.streamSettings to be non-null and streamSettingsCount >= 1. A count above what “NVSC supports” is rejected. Resolution and fps must be present (“Missing resolution/fps value in NVbSessionParams”). Keyboard layout and client locale are copied out of the same struct.
  • nvbStartStreaming applies the same stream-count rule to NVbStreamingParams, and additionally requires connectionInfoCount >= 1 and a non-null connectionInfo pointer.
  • nvbJoinSession, nvbResumeSession, nvbPauseSession, nvbPauseStream, nvbStopSession, nvbStopStreaming, nvbGetSession, nvbSendInputEvent, nvbFeatureControl, nvbSendClientInfo, nvbCollectStatistics, and the video-state updates all log the session identifier. Video, decoder, and de-jitter updates also check streamIndex against VIDEO_STREAM_MAX_COUNT.
  • nvbCancelRequest refuses request id 0.
  • nvbFeatureControl checks the type against NVB_FEATURE_MAX_TYPE. Named feature ids in the string table include NVB_FEATURE_NETWORK_CAPTURE_CLIENT, NVB_FEATURE_NETWORK_CAPTURE_SERVER, NVB_FEATURE_RECORD_STATS_CLIENT, and NVB_FEATURE_RECORD_TRACES_SERVER.
  • nvbSendClientInfo checks the info type against NVB_CLIENT_INFO_MAX_TYPE.
  • nvbTestNetworkLatency requires a server list. nvbTestNetworkCapability requires a server address and logs NetworkTestProfilesCount.
  • nvbUpdateAdState is keyed by session setup request id, and the client refuses the call outside an allowed session-control state.

Callbacks are registered once and then dispatched by type. The string table names three callback classes: NVB_CB_LOG, NVB_CB_EVENT, and NVB_CB_SESSIONSETUP_PROGRESS. “Unknown Callback Type” is the fallback. Several events are synchronous from the SDK’s point of view: the client must return before a logged deadline. The strings name those waits explicitly.

NVB_EVT_SSL_CERTIFICATE_NOTIFICATION times out after a logged number of seconds and, on the connection path, rejects the socket if the client does not return. NVB_EVT_SESSION_INFO times out per session id, and a client-set abortSession flag on that event is ignored. NVB_EVT_AGENT_STARTED has the same per-session wait. NVB_EVT_SESSION_NOTIFICATION subtypes NVB_SN_STREAMER_UPSTREAM_READY and NVB_SN_STREAMER_CONNECTED have their own waits. NVB_SN_SERVER_RESUME, NVB_EVT_INTERFACE_CHANGE_EVENT, NVB_EVT_HID_OUTPUT_EVENT, and NVB_EVT_HID_CHANGE_RESPONSE_EVENT log that the SDK resumes anyway if the client is late. NVB_SN_STOPPED_BY_USER and NVB_SN_STREAMER_NETWORK_ERROR also have waits.

GridServer: the CloudMatch state machine inside Bifrost

Demangled symbols place the HTTP client in NVB::GridServer, with tasks ProvisionSeatTask, GetSessionTask, GetActiveSessionsTask, SessionModifyTask, and SessionCleanUpTask. The methods that show up as local symbols are requestSession, sendSessionPUTRequest, pollSession, getSessionInformation, sendRequestToServer, sendSyncStopRequest, sendSessionSetupProgressEvent, getSessionTaskFunc, and getActiveSessionsTaskFunc.

URL formats are literal:

  • %s://%s:%d/v2/serverInfo
  • https://%s:%d/v2/session
  • https://%s:%d/v2/session/%s

Verbs and command names in the same cluster are POST, DELETE, RESUME, JOIN, FORWARD, TRANSFER, SESSION_RATING, AD_UPDATE, setup, PollSession, PostSession, DeleteSession, GetSessionList, and SendStopRequest. PUT is logged as “PUT request URL: %s”. A create is logged “Session request URL: %s”, “Serialized session request. Size: %d, Data: '%s'”, “Accepted new session request. Request Id: %d”, and “Created session: %s” / “Creating/Resuming session: %s”.

Polling is a first-class loop, not a client timer. Strings say “Polling session. The request url is %s”, “Polling for session %s, request id: %d, QueuePosition: %d, ETA: %d(msec)”, “Received response during polling is: '%s'”, “Unexpected state %s (%d) while polling for session”, and “Session %s state changed to Finished, aborting session poll”. A network error during polling sends DELETE for that session id. A session that was canceled also sends DELETE (“Session %s was canceled, sending DELETE request for session: %s”), including the case “Start session canceled before setting up session on PM.” Delete retries log “Retry Delete Attempt %d”. If the control server is missing, DELETE is refused (“Unable to send session DELETE request to the server. Control server not found”).

Zone forwarding is explicit: “Session: %s is forwarded from zone %s:%d to %s:%d”. Ads pause the poll (“Polling for session %s stopped for ADs flow”) and resume it (“Either ADs flow is completed or the AdsWaitTimeout expired. Restarting polling”). Ad updates carry AdId, AdAction, queue position, ETA in milliseconds, and an ads count. The SDK caches pause/resume pairs and drops back-to-back duplicates before calling sendAdupdatesRequestToServer. ConvertNvbAdActionToAdState rejects an unexpected action. State transitions that skip a legal edge are refused.

Server-info handling rejects a payload with no version, an unexpected server type, and an unexpected authorization type. Headers compiled into the client include x-nv-client-identity and the NV-Client-Type / NV-Device-Type / NV-Client-Stream family (the last three appear concatenated in one rodata run because they are adjacent C strings). RTSP header names that Bifrost owns for later media, and that OpenNOW already mirrors at ANNOUNCE time, include x-nv-vqos, x-nv-audio, x-nv-bwe, x-nv-sessionid, x-nv-video, x-nv-general, x-nv-mic, x-nv-packet, x-nv-ping, x-nv-qscore, x-nv-ri, x-nv-runtime, x-nv-aqos, x-nv-abtesting, and x-nv-cli.

Session status names in the same binary are INITIALIZING, READY_FOR_CONNECTION, PLAYING, PAUSED_UNINTENTIONAL, PAUSED_INTENTIONAL, RESUMING, FINISHED, plus “Unknown Status”. Mapping onto OpenNOW

OpenNOW’s protocol 5 session methods are session.create, session.poll, session.stop, session.active.get, session.remote.list, session.claim, session.ad.report, then streamer.detect, streamer.prepare, streamer.start, streamer.status.get, and streamer.stop. That is the same lifecycle as QUERY_GFN_PREPARE / START / RESUME / STOP / GET_ACTIVE_SESSIONS / GET_SESSION_INFO / UPDATE_AD_STATE, with the HTTP stack moved into CloudMatchService.

session.create builds sessionRequestData in build_create_body. Field for field, the body matches the Bifrost request run for the keys OpenNOW fills: appId, internalTitle, availableSupportedControllers [2], preferredController 2, networkTestSessionId, parentSessionId null, clientIdentification GFN-PC, deviceHashId, clientVersion 30.0, sdkVersion 2.0, streamerVersion 14, clientPlatformName, one clientRequestMonitorSettings entry (monitorId 0, origin 0,0, width, height, fps, sdrHdrMode, displayData, null HDR10+ gaming data, dpi 96 on Linux), useOps true, audioMode 2, metadata, sdrHdrMode, null clientDisplayHdrCapabilities, surroundAudioInfo 0, remoteControllersBitmap 0, timezone offset, enhancedStreamMode 0, appLaunchMode, secureRTSPSupported true, null partner data, accountLinked, enablePersistingInGameSettings, requestedAudioFormat 0, userAge, requestedStreamingFeatures, and null transport.

requestedStreamingFeatures sends reflex, bitDepth, cloudGsync, enabledL4S, mouseMovementFlags 0, trueHdr, supportedHidDevices 0, profile 0, fallbackToLogicalResolution false, null hidDevices, chromaFormat, and zeroed prefilter and HUD fields. Codec, max bitrate, and dynamic streaming mode are left out of this object on purpose: Bifrost’s own later path carries them as RTSP x-nv-vqos, and OpenNOW’s ANNOUNCE does the same. HDR sets sdrHdrMode 1, trueHdr true, and bit-depth enum 1, which is the contract in docs/core-protocol.md.

Headers in cloudmatch_headers line up with the Bifrost header fragments: Authorization: GFNJWT <token>, x-nv-client-identity, nv-client-type: NATIVE, nv-client-streamer: NVIDIA-CLASSIC, nv-client-id equal to the mall LCARS id ec7e38d4-03af-4b58-b131-cfb0495903ab, x-device-id, and a user agent GFN-PC/30.0 (Linux) BifrostClientSDK/4.9 (38495286). Content type is text/plain. The classic-streamer header is the HTTP form of clientStreamerClassic: true.

The POST URL is v2/session on https://prod.cloudmatchbeta.nvidiagrid.net/ unless a strict zone override replaces the origin. That is grid.server plus grid.version. An optional network-test session id is acquired first and stored on the body, which is the OpenNOW counterpart of networkTestSessionId and nvbTestNetwork*, limited to a single typed test allocation.

Response normalization in session_info keeps sessionId, subSessionId, numeric status, queuePosition, seatSetupStep, ads, gpuType, appLaunchMode, connectionInfo, derived rtspsEndpoints, iceServers, signaling URL, and a negotiated profile. RTSPS endpoints are recognized when usage is 16, appLevelProtocol is 6, or resourcePath starts with rtsps:// or rtsp://. Media candidates use usage 2 or 17. Signaling prefers usage 14. Those integers are OpenNOW’s live decoding of the usage names Bifrost prints (SIGNALING, MEDIA, NVB_PU_RTSPS). session_phase maps status 1 to preparing, 2 ready, 3 streaming, 4 and 5 paused, 6 resuming, and 7 finished. streamer.prepare and streamer.start accept only status 2 or 3, which is READY_FOR_CONNECTION or PLAYING in the Bifrost names, and they require RTSPS endpoints before attachment. That matches the protocol rule that a RESUME acknowledgement is not stream readiness.

Claim sends action: 2, data: "RESUME" and polls. Bifrost’s command list includes RESUME as a PUT/modify verb, and Geronimo’s “Unknown resume type … Defaulting to NONE” confirms resume type is part of the session object. OpenNOW treats SESSION_NOT_PAUSED (statusCode 34) as “poll anyway”, which matches NVB_R_SESSION_NOT_PAUSED being a distinct result rather than a fatal create error. Session limit is statusCode 11, description containing SESSION_LIMIT, and unified error 4AF1201E, mapped to session_conflict so the shell lists seats instead of allocating another. That is NVB_R_SESSION_LIMIT_REACHED / NVB_R_SESSION_LIMIT_PER_DEVICE_REACHED and the otherUserSessions field.

Cancellation parity is structural. Bifrost deletes a session that was canceled before the PM seat exists, deletes on poll network failure, and Geronimo refuses deleteSession while setup is still in progress. OpenNOW holds one admission lock, waits for a protocol-5 ack for at most ten seconds, then DELETE with an eight-second timeout, and persists pending-session-cleanup.json if DELETE fails. The next create returns session_cleanup_pending or session_update_busy. That is the same “do not start a second seat while the first is unresolved” rule, implemented as core state instead of NVB_SSS_PREVIOUS_SESSION_CLEANUP.

streamer_context passes the normalized session plus settings into the in-process streamer and forces transportMode nvst. Official nv-gfn-streamer=true plus NVIDIA-CLASSIC is the same choice. Software renderers are refused for HDR and for advanced color on Linux Vulkan, which is the OpenNOW form of nv-renderer-blocklist plus Geronimo’s decoder-not-supported returns. Frame-rate ceilings (1920×1080 and 1920×1200 up to 360 fps, everything else 240, and 240 without a confirmed hardware decoder and entitlement) line up with unsupportedFpsIdentifier: 240 being a UI warning threshold rather than a hard protocol maximum.

Parity gaps

The HTTP create body and the classic NVST attachment path are the parts that already match. The gaps below are the orchestration behaviors this Flatpak implements and OpenNOW does not yet expose with the same controls.

Client version advertised to CloudMatch. This Flatpak’s mall build is 2.0.84.127 on Geronimo branch gs_04_87. OpenNOW sends nv-client-version: 2.0.87.131 with clientVersion 30.0, sdkVersion 2.0, and streamerVersion 14. The user-agent SDK tail matches the Bifrost fragment BifrostClientSDK/. The marketing build number is ahead of this Linux snapshot. A parity test against this exact Flatpak should treat 2.0.84.127 as the official Linux build under test and 2.0.87.131 as OpenNOW’s current impersonation, which comes from a later client.

CEF query bus versus core RPC. Official prepare/start/resume/stop/cancel/get-session/get-active/set-auth/update-ad are QUERY_GFN_* calls into GridApp, which owns one NVbClient. OpenNOW’s RPC methods cover the same verbs, and the Qt shell never sees OAuth tokens. The gap is everything else on that query list that mutates a live seat through Bifrost: streaming-settings update, max bitrate, dynamic streaming mode, L4S, prefilter, vsync, HUD, cloud-gsync capability, and latency-based routing. OpenNOW applies a subset of those at ANNOUNCE or as settings on the next create. It does not expose a mid-session nvbFeatureControl / nvbSendClientInfo equivalent in the core protocol.

Setup progress vocabulary. Bifrost reports NVB_SSS_CONFIGURING, NVB_SSS_STARTINGSTREAMER, NVB_SSS_SEATREADY, NVB_SSS_QUEUEPOSITION, and NVB_SSS_PREVIOUS_SESSION_CLEANUP, with queue position and seatSetupEta in milliseconds. OpenNOW surfaces numeric status, phase, queuePosition, and seatSetupStep. ETA and the named setup states are not part of the normalized session. Mall UI that waits on those names has no direct core field.

Poll and delete policy. Bifrost polls inside GridServer, pauses the poll for ads, restarts it after AdsWaitTimeout, aborts on FINISHED, and sends DELETE if the poll itself hits a network error. OpenNOW polls on a 1.5 second Qt timer, at most 60 polls and 90 seconds, and does not treat a transient GET failure as terminal. DELETE runs for ack timeout, user cancel, and explicit stop. A poll network error keeps the seat. That is safer for a flaky link and different from Bifrost’s “polling failed, DELETE” path. Ads do not suspend OpenNOW’s poller; session.ad.report and normalize_ad_state record the opportunity, without the creative sort order (webm first on Linux), force-play timeout, or grace period from opportunity.

Join, forward, transfer, rating. Bifrost command names include JOIN, FORWARD, TRANSFER, and SESSION_RATING in addition to POST, RESUME, and DELETE. nvbJoinSession is an exported symbol with its own invalid-params check. OpenNOW claim is only RESUME. There is no join of another user’s seat, no transfer, and no session-rating POST.

Network test and LBR. Official code has synchronous and async latency and capability tests, a cancel, maxZonesPerFingerprint 3, prefetch, max-bandwidth tests, five cached latency samples, and deterministic server routing behind QUERY_GFN_LATENCY_BASED_ROUTING. OpenNOW can attach one networkTestSessionId and has a separate zone/queue selector for free-tier NVIDIA launches. It does not run nvbTestNetworkCapability profiles or the LBR cache as part of create.

Auth refresh callback. Bifrost blocks the request until NVB_EVT_UPDATE_AUTH_TOKEN returns a new Jarvis/GFN JWT, then retries. The mall wires refreshAuthToken into start parameters. OpenNOW captures the token before POST and can renew ServiceId credentials for cleanup when the original account is selected. It does not implement the in-flight “abort request N, retry with a token the SDK just asked for” callback. Certificate pinning UI is similarly absent: NVB_EVT_SSL_CERTIFICATE_NOTIFICATION can reject the connection, while OpenNOW uses the process trust store.

Session document fields Geronimo requires and OpenNOW does not promote. The native deserializer insists on networkSessionId, rtspSessionId, streamSessionId, and streamSubSessionIds. OpenNOW keeps raw connectionInfo and derived RTSPS, ICE, and signaling URLs, and copies subSessionId. Those four stream identifiers are not first-class fields on the normalized session. If a seat returns them only inside nested objects, the in-process streamer never sees them as named ids. parentSessionId is always null. Mall metadata ClientImeSupport and clientPhysicalResolution are not in build_create_body; OpenNOW metadata is SubSessionId plus surroundAudioInfo=2. keyboardLayout is applied by Geronimo at launch and again at upstream-ready. OpenNOW has language preferences and does not copy a layout string into NVbSessionParams.

userAge and controllers. OpenNOW sends userAge 25. The official start path passes the account’s userAge and contentRating. Controllers are fixed as available [2], preferred 2, bitmap 0, and supportedHidDevices 0 with null hidDevices. Geronimo on this build synthesizes DS4/DS5, honors generic HID vid/pid lists, and can set remoteControllersBitmap. Linux config also disables wheels and flight controllers. OpenNOW’s gameplay input path is separate; the create body does not advertise the local HID set the way nvbSetAvailableInputDevices does before nvbStartSession.

Remote config overrides. Official GeronimoSettingsImpl::overrideNVbSessionParams can rewrite the session struct from GXT/rconfig after the mall has chosen resolution and features. OpenNOW resolves codec and color from saved settings plus embedded runtimeCapabilities before POST, and the server’s finalizedStreamingFeatures overlay the request afterwards. There is no second JSON document that patches NVbSessionParams between prepare and start.

Serenity recording versus native recording. useSerenity: true and recordCodec: "h264" mean the official Linux client transcodes the seat to H.264 for local record when the hardware decoder cannot transcode the live codec, and it will drop resolution to a supported transcode size. OpenNOW records the negotiated encoded video and Opus into Matroska without a second encoder. Replay is a bounded packet buffer. Highlights, ShareServer autoHighlights, and the Serenity RTSP handler have no counterpart. frameStatsEnabled / summaryStatsEnabled / networkCapture map to nvbCollectStatistics and network-capture feature flags. OpenNOW has streamer stats and diagnostics stages; it does not toggle NVB_FEATURE_RECORD_STATS_CLIENT or server-side trace recording.

Frame-loss and reconnect timers. Official start parameters carry 500 ms warning and 30 s error timeouts, and the mall will auto-resume for up to five minutes with a five-second refresh, classifying NVST errors with the 8004xxxx regex. OpenNOW’s reconnect budget is the poll deadline plus eight recovery attempts with backoff up to eight seconds, reset only by a presented frame, and an exhausted video SETUP (missing-video-peer) stops automatic recovery. The 500 ms / 30 s pair is not applied as a client-side frame-loss fault. analyticsTimeout 10000 has no OpenNOW setting.

Termination reasons. Bifrost emits distinct notifications for idle timeout, entitlement timeout, session time limit, operator kill, windowed mode, TDR, process integrity, and multiple login, and Geronimo forwards resumable plus sessionAlive with a 32-bit reason and extended code. OpenNOW maps CloudMatch status 7 to phase: finished with termination.source = cloudmatch-session-status and resumable: false, and it refuses to invent a vendor reason. Transport EOF is source: nvst-transport with resumable: null. The official reason enum is the gap. Idle-warning fields userIdleWarningTimeoutInMs and the approaching-timeout notifications are not surfaced.

Window and renderer policy. Official streaming wants fullscreen (requireFullscreenInStreaming), a black custom window, SDL vsync, HiDPI, a 640×360 minimum, and an async EGL renderer, with software GL blocked. Linux packaging turns on Gamescope HDR. OpenNOW’s Qt shell keeps the stream item alive under overlays, confirms before ending a session, and takes HDR from the current output (nativeHdrSupported, nativeHdrDisplay) rather than from ENABLE_GAMESCOPE_HDR. mirrorClientHDRProperties is false in this config; OpenNOW copies validated min/max nits when the compositor reports them and otherwise uses the 1000 / 0 / 400 requested-content defaults. Primary chromaticities stay at protocol defaults on both sides when no capture defines a scale. The behavioral gap is Gamescope-specific HDR and the forced-fullscreen mall policy, not the CloudMatch HDR bits.

Multi-stream and server maintenance results. Bifrost allows more than one stream only up to an NVSC maximum and rejects zero. OpenNOW sends one monitor. Result codes for patching, region hold, storage, GES, invitation-only registration, and queue abandonment exist in the SDK and collapse in OpenNOW to generic upstream or HTTP errors unless they match the session-limit or not-paused special cases.

What already matches and should stay stable. The create URL family, GFNJWT authorization, NVIDIA-CLASSIC and NATIVE client headers, LCARS client id, secureRTSPSupported, useOps, stereo audioMode 2 with requestedAudioFormat 0, monitor width/height/fps, HDR trio (sdrHdrMode, monitor sdrHdrMode, trueHdr), bit-depth and chroma enums, omission of codec from the POST body, RTSPS endpoint extraction, status 2/3 as the only attachable phases, status 7 as terminal, RESUME-then-poll, session-limit conflict handling, and single-flight create with DELETE compensation. Those are the parity surface to protect when the gaps above are closed.

Static inspection cannot show timing, exact enum integers for every NVB_R_* and NVB_PU_* name, or the bytes of a live POST from this Flatpak. It can show the exported calls, the URL templates, the JSON keys, the query names, and the config values the mall passes into GridApp. OpenNOW already speaks the subset of that contract that allocates a seat and attaches NVST. The remaining official surface is progress reporting, ads-aware polling, auth-refresh callbacks, LBR and network-capability tests, join/transfer, Serenity H.264 recording, frame-loss timers, and the richer termination enum.

GFN transport in libGeronimo.so and libBifrost2.so

This note is a static reading of the Linux GeForce NOW client under /workspace/audit/gfn-official/, set next to OpenNOW’s NVST implementation in native/opennow-streamer (nvst_rtsp.rs, nvst.rs, nvst_input.rs, nvst_control.rs) and the comparison notes in docs/streamer-comparison/ and docs/mjolnir-nack-v2.md. The official libraries are the Flatpak payload com.nvidia.geforcenow (Freedesktop runtime 24.08). Both are stripped ELF64 x86-64 shared objects. libBifrost2.so is 19,052,024 bytes, SHA-256 8400714f98b7db928ef4377515b1ed35be12523b7fa306566e776b76965537c9, GNU build id fa3685038bd71962fe30ad09482bcb0721a54f35. libGeronimo.so is 34,347,824 bytes, SHA-256 4863f02ed7d82b06b8152b23e8683dd9b77bcd63165890ce4c6c1cd883fc0cd1, build id 15d0eebc08da503f1f37ea9cae2dbac1d760fea4. Embedded Perforce paths are gs_04_87 (/dvs/p4/build/sw/gcomp/rel/gs_04_87/...), not the Windows gs_04_90 install described in docs/streamer-comparison/README.md. Bifrost’s rodata also names OpenSSL 3.5.6 (7 Apr 2026) and a Mjolnir vcpkg tree (Poco, usrsctp-era SCTP helpers, StunConsent.cpp). The Bifrost hash is the same artifact already cited for private NACK-v2, so addresses below are ELF virtual addresses in that file and can be checked with objdump or radare2 5.5.0.

The split of ownership is the whole architecture. Geronimo is the Grid shell: SDL windows, Vulkan and VDPAU decode, session UI, and the C++ types GridApp, IOInterface, and BifrostSDKExecutor. It does not implement RTSP, Mjolnir, ICE, DTLS, or SCTP. Its dynamic symbol table imports the Bifrost C API (nvbCreateClient, nvbInitializeClient, nvbStartSession, nvbStartStreaming, nvbSendInputEvent, nvbFeatureControl, nvbSendMicAudioFrame, nvbUpdateVideoFrameState, nvbUpdateVideoDecoderState, and the rest of that list). Bifrost is the stream SDK. Its rodata is full of NVSTE_RTSP_* stage names, x-nv-* SDP keys, Mjolnir receiver types, ServerControl channel labels, and NVST_R_SERVER_CONTROL_* failures. Geronimo decides when a session is allowed to send. Bifrost decides how the bytes are framed, which socket they leave on, and which ServerControl command code they carry.

RTSP and RTSPS

Signaling is RTSP carried on a secure WebSocket, not a raw TCP RTSP socket. Bifrost strings include NVB_PU_RTSP, NVB_PU_RTSPS, secureRTSPSupported, rtsps://, Using Secure WebSockets for Signaling, WebSocket Loop Starting., WebSocket Loop Exiting., Exception during WebSocket operation: %s, and RTSP/WebSocket upgrade forbidden (403): %s. The SDP key general.rtspWebSocketPerConnection (also emitted as x-nv-general.rtspWebSocketPerConnection) is the switch for one WebSocket per RTSP connection. OpenNOW’s ANNOUNCE hard-codes a=x-nv-general.rtspWebSocketPerConnection:1 and connects with RtspClient to the first CloudMatch endpoint that starts with rtsps:// or rtsp://.

The method set, recovered from the NVSTE_RTSP_* / NVST_RTSP_* name table, is the classic sequence plus a GFN-specific fan-out inside SETUP:

Stage Success / failure names present in Bifrost
OPTIONS NVST_RTSP_OPTIONS_OK, NVST_RTSP_OPTIONS_BAD_REQUEST, NVSTE_RTSP_OPTIONS, timeout
DESCRIBE NVST_RTSP_DESCRIBE_OK, NVSTE_RTSP_DESCRIBE, connect failure
SETUP Split into audio, video, control, mic, and extended. Each has its own NVSTE_RTSP_SETUP_* prefix
ANNOUNCE NVST_RTSP_ANNOUNCE_OK, NVST_RTSP_ANNOUNCE_NOT_FOUND, connect failure
PLAY NVST_RTSP_PLAY_OK, NVST_RTSP_PLAY_BAD_REQUEST, timeout
TEARDOWN NVST_RTSP_TEARDOWN_OK, timeout

SETUP is not one transaction. Bifrost names five sub-stages: NVSTE_RTSP_SETUP_AUDIO, NVSTE_RTSP_SETUP_VIDEO, NVSTE_RTSP_SETUP_CONTROL, NVSTE_RTSP_SETUP_MIC, and NVSTE_RTSP_SETUP_EXTENDED. Each sub-stage has a parallel response-code family: bad request, unauthorized, forbidden, not found, not allowed, authentication required, timeout, not enough bandwidth, session not found, not valid in this state, unsupported transport, destination unreachable, invalid CSeq, malformed response, internal server error, not implemented, version not supported, a stage-specific “not supported” code (SETUP_AUDIO_NOT_SUPPORTED, SETUP_VIDEO_NOT_SUPPORTED, and the same for control and mic), and STREAMER_COMMUNICATION_FAILED. Transport failures are named separately from HTTP-style codes: RTSPE_OPERATION_TIMEDOUT, RTSPE_COULDNT_CONNECT, RTSPE_SSL_CONNECT_ERROR, RTSPE_SEND_ERROR, RTSPE_RECV_ERROR, RTSPE_SSL_INVALIDCERTSTATUS, RTSPE_NOT_AUTHENTICATED_EXCEPTION, and three Poco SSL exceptions (SSLCONTEXT, CERTVALIDATION, SSLCON_UNEXPECTEDLYCLOSED). A session can therefore fail “at SETUP” in twenty different ways that a single status integer would collapse. OpenNOW’s client collapses this to ensure_rtsp_ok plus a video-SETUP retry. nvst_rtsp.rs treats a 200 that comes back without a usable video peer as retryable (three rounds, three seconds apart) because a rig whose streamer is still starting answers SETUP with 200 and an empty peer, and repeating that SETUP can poison later ANNOUNCE on some alliance seats. That retry policy is OpenNOW’s, not a loop visible as a string in this Bifrost build.

Two SETUP bypass strings change the media map. Bifrost logs Bypassing 'Mjolnir' SETUP for the Audio stream. Deferring to WebRtcTransport setup and the same sentence for the mic stream. Video stays on the Mjolnir SETUP. Audio and microphone are expected to ride the WebRTC bundle once rtcAudioOnNativeBundle and rtcMicOnNativeBundle are set. OpenNOW matches that shape: ANNOUNCE sets rtcVideoOnNativeBundle:0, rtcAudioOnNativeBundle:1, rtcDataChannelOnNativeBundle:1, and, when a microphone is available, rtcMicOnNativeBundle:1 plus a=x-nv-mic.micSsrcConfig.senderSsrc:1. It also sets enableUnifiedSocket:0. Bifrost still contains the other mode: general.enableUnifiedSocket, MjolnirVideoReceiver created early for unified socket mode, setupUnifiedSocketMode: MjolnirVideoReceiver not found in WebRtcTransport, and MjolnirVideoReceiver not set on WebRtcTransport for unified socket mode. Unified socket is a real code path in gs_04_87. It is not the path OpenNOW advertises, and it is not what docs/streamer-comparison/video.md describes for the Windows log from 2026-08-30.

Ports

Neither library contains the immediates 49005 or 49006 as UDP port constants. A byte search for 6d bf 00 00 and 6e bf 00 00 in Bifrost returned no hits. The two Geronimo hits for 6e bf 00 00 sit inside pointer-sized data (0xbf6ed0-style addresses), not a mov of the port. Decimal 5004 appears once in Bifrost and seven times in Geronimo; that is the historical RTP port the Windows comparison log called “server 5004”, but this static pass does not show a mov $5004 on the bind path, so it should not be treated as the Linux client’s listen port.

What the binary does contain is the reservation policy. Strings, in order of the failure they describe:

  • Enable dynamic fallback when using reserved ports
  • Setup a stream clientAddress=%s, serverPort=%d
  • clientPorts.useReserved: Failed to create a bound VIDEO stream on %s.
  • clientPorts.useReserved [Fallback plan]: On. Attempting to use the next available port from the dynamic range.
  • the same pattern for AUDIO, MIC, and CONTROL, with CONTROL’s fallback text saying “the first available port” rather than “the next”
  • useReserved port [Fallback:On]. Use next available port from dynamic range.
  • general.clientPorts.useReserved and general.clientPorts.fallbackDynamic

So the official client tries a reserved bind per stream kind (video, audio, mic, control) and, if that bind fails and fallback is on, takes an ephemeral port. The reserved numbers themselves are not in this build’s immediates. They are either computed, read from configuration, or simply the ports the process already holds when ANNOUNCE fills clientBundlePort and clientPorts.*. The Windows comparison notes record 49005 for video RTP and 49006 for the WebRTC audio bind on one session. That is a log fact about that install, not a constant in gs_04_87.

OpenNOW makes the pair explicit because it does not link these libraries. reserve_nvst_socket_pair_from(49_005) in nvst.rs binds video on 49005 and the bundle on 49006, then falls back to a dynamic adjacent pair (ephemeral video port, bundle = video+1, up to 32 attempts). The comment there cites Bifrost’s useReserved=1 behavior. ANNOUNCE then publishes the ports that were actually bound: clientBundlePort is the bundle socket, and the video m= line carries the Mjolnir port. clientPorts.video/audio/mic/control/bundle/session are written as 0 with useReserved:1 and fallbackDynamic:1, which tells the server to use the reserved client ports rather than a list of fixed per-media ports in the SDP. A test fixture still speaks the older Transport form unicast;X-GS-ClientPort=49005-49006.

Packet size is a port-adjacent MTU problem, not a port number. Bifrost logs Configured packetSize value is invalid and it is getting overridden to 512 bytes. and Updating streamer packetSize of stream %zu to use MTU value determined by NCT. New packetSize: %u bytes, NCT detected packet size: %u bytes. SDP also has packetSizeDetection and two dynamic levels packetSizeL0 and packetSizeL1. OpenNOW keeps 1280 unless the video route’s interface is a detected VPN and a measured datagram size is tighter. The 512-byte override is a Bifrost safety floor this tree does not copy.

Mjolnir

Mjolnir is the video receive stack, not a synonym for “the UDP socket.” The socket is the dedicated video UDP flow. The types in Bifrost are MjolnirVideoReceiver, MjolnirExtension, MjolnirGsFrameHeader (an RtpExtensionHeader), and VirtualAssignable wrappers around those headers. Log lines:

  • Using mjolnir header.
  • Invalid MjolnirExtension length %u, it should be %zu
  • Can't read MjolnirExtension with ID %02X and length %zu, not enough bytes %zu
  • Mjolnir packet received but MjolnirVideoReceiver not set
  • MjolnirVideoReceiver has been set
  • MjolnirVideoReceiver destroyed. Stats: received=%llu dropped=%llu queue_size=%zu
  • MjolnirVideoReceiver queue full (%zu packets), dropping packet. This may indicate RtpSourceQueue is not consuming fast enough.

The queue is bounded and drop-newest-or-drop-incoming when the RTP source queue falls behind. There is no string that says the receiver blocks the network thread until the decoder catches up. That matches the streamer rule that codec work must not run on the receive thread, and it matches OpenNOW’s bounded reorder queue (1024 packets, hard cap 2048) rather than an unbounded jitter buffer.

The header OpenNOW parses is the same object Bifrost names MjolnirGsFrameHeader. In nvst.rs the profile constant is GS_VIDEO_EXTENSION_PROFILE = 0x4753 (“GS”), a fixed 16-byte RTP extension, not an in-payload prefix. Flags inside that header are SOF (0x04), EOF (0x02), and picture data (0x01). Frame assembly uses those bits plus the stream packet index. Bifrost’s “invalid extension length” and “not enough bytes” strings are the official parser rejecting a short or mistyped extension before decode. OpenNOW’s assembler resets, marks the access unit non-contiguous, and asks for an IDR when the GS header is bad. Both sides refuse to invent a frame from a truncated header.

Video confidentiality is SRTP on that socket. OpenNOW’s receiver comments record Bifrost’s SecureRtp mapping: sec_serv_conf_and_auth with a 256-bit key selects srtp_crypto_policy_set_aes_gcm_256_8_auth, an 8-byte tag, not the 16-byte tag of RFC 7714 AEAD_AES_GCM. RTP key derivation uses labels 0x00 and 0x02. SRTCP, if used, uses 0x03 and 0x05 on a separate session derived from the same master key. ANNOUNCE carries x-nv-runtime.videoSrtp:1 and the key id. Audio and mic SRTP are advertised off (audioSrtp:0, micSrtp:0) because those flows are DTLS-protected inside the bundle instead. A replay window attribute exists (srtpReplayWindowSize). OpenNOW sizes its replay bitmap to the reorder window (2048 packets). A 64-packet bitmap, which an earlier receiver used, rejected legitimate retransmissions after a few milliseconds at high bitrate and turned every NACK into a keyframe.

FEC is configured in the same ANNOUNCE block and applied before access-unit assembly. Bifrost exposes fec.enable, repair percents, minRequiredFecPackets, maxAllowedFecPackets, numSrcPackets, rateDropWindow, and fec.type, including an rtcMultiStream mode. OpenNOW enables systematic Reed-Solomon with repair 20 percent, floor 20, ceiling 35, minimum two FEC packets, and a rate-drop window of 10. The Windows log in video.md recorded dynamic FEC on and, for that session, zero recovered FEC packets against 639 used of 677 NACKed packets. FEC and NACK are both advertised. A session can run with NACK doing the work and FEC idle.

ServerControlReliableUdp and ServerControlReliableUdpAggregated are still linked. They observe enet connect, readable, peer-disconnected, error, and telemetry notifications. That is the pre-bundle control transport. It remains in the binary next to the native data-channel path. OpenNOW does not implement enet. It only advertises an MTU and disables the partially reliable UDP channel.

ICE, DTLS, and SCTP

The bundle is a normal ICE/DTLS association that then carries SCTP data channels and Opus audio. SDP names both credential generations: iceUsernameFragment and iceUserNameFragmentV2, icePasswordV2, iceUsernamePwd, dtlsFingerprint and dtlsFingerprintV2, plus iceTransportPolicy. OpenNOW publishes V2 attributes and the standard a=ice-* / a=fingerprint lines from the same ufrag, password, and SHA-256 fingerprint, with a=setup:actpass and a=ice-options:trickle. One host candidate is written at priority 2122260223. STUN in nvst.rs is RFC 5389: magic cookie 0x2112a442, binding request 0x0001, success 0x0101, attributes username 0x0006, message-integrity 0x0008, XOR-mapped-address 0x0020, and fingerprint 0x8028 XORed with 0x5354554e. Integrity is checked against the remote ICE password. A response that does not match a sent transaction is ignored. Displayed RTT prefers the selected ICE pair, then video STUN, then bundle STUN, and samples expire after five seconds. That order is what NACK-v2 retry timing uses.

DTLS protects everything on the bundle socket: audio RTP, microphone RTP, and every data channel. Video does not join that DTLS session when rtcVideoOnNativeBundle is 0. Diagnostics have to keep those facts apart. Bundle audio running, or DTLS handshake complete, does not mean a Mjolnir datagram has arrived. docs/streamer-comparison/windows-udp-diagnostics.md records a capture that reached PLAY, DTLS, and SCTP with zero video datagrams.

SCTP channels are created by label. The label strings sit together in Bifrost rodata:

SID values in OpenNOW are local choices of the str0m data-channel API (even numbers, negotiated in creation order). They are not constants in Bifrost. At 0x2c4769 the partially reliable control channel is created by loading the address of control_channel_partially_reliable and calling through the channel factory (call *%r14). The returned ax is stored at object offset 0x1f0 (mov %ax, 0x1f0(%rbx)). The next site, 0x2c488c, does the same for control_channel_unreliable and stores ax at 0x1ee. The SCTP stream id is whatever the factory returns. A comment in docs/mjolnir-nack-v2.md already separates “logical channel 1” from “SCTP SID 1”. This instruction sequence is why: the logical slot is the field in the ServerControl object; the SID is an output of channel creation. OpenNOW’s use of SID 6 for control_channel_partially_reliable matches the label and the unordered 300 ms lifetime. It does not match an official immediate mov $6.

Reliability policy is also not identical just because the label matches. OpenNOW’s partial channels are unordered with a 300 ms PR-SCTP lifetime, which is the value advertised as x-nv-ri.partialReliableThresholdMs:300. The NACK-v2 note records the inspected official default for that channel as ordered with two SCTP retransmissions. Ordered partial reliability is why mouse motion felt like delayed catch-up: one lost report holds every newer report until the lifetime expires. OpenNOW therefore forces ordered: false on control_channel_partially_reliable even though the official default observed previously was ordered. Reusing the label routes the command to the right server handler. It does not copy the official retransmission policy.

rtcp_on_sctp_private is the bundle-only feedback channel. OpenNOW names it rtcp1 in log lines and sends receiver reports and, on the bundle-only route, RTCP generic NACK there. When a Mjolnir port is selected, loss feedback leaves on control_channel_partially_reliable as command 0x0317 instead, and does not fall back to RTCP if that channel is closed.

NACK

Loss recovery on the dedicated video route is private NACK-v2, command 0x0317, not RTCP generic NACK. The send site is still where the earlier note placed it. At 0x2b2c88 the code does mov $0x317, %esi and call *%r14 with the ServerControl object in rdi. esi is the command code. The serializer just above the length calculation, at 0x2b74d9 through 0x2b7531, is:

  • movb $0x2, 0x40(%rsp) writes version 2 at payload byte 0.
  • movzwl 0x242(%rbx), %eax then mov %al, 0x41(%rsp) writes the low byte of a u16 stream ordinal at object offset 0x242 into payload byte 1. A single-stream client stores 0 there.
  • The count byte lives at 0x42(%rsp). It is compared with 0x40 (64). A count above 64 is rejected.
  • lea 0x0(%rbp,%rbp,4), %rax is count * 5, then lea 0x3(%rax,%rax,1), %edx is count * 10 + 3. That is the payload length: 3 bytes of header plus 10 bytes per record.
  • The buffer is then passed to the framer that the 0x317 site sends.

Each record is a little-endian u16 base RTP sequence plus a little-endian u64 bitmap. The base itself is missing. Bit j requests base+1+j modulo 65536. A run of 64 consecutive losses is one record with 63 bits set, not 64. The maximum framed command is 4 bytes of ServerControl header plus 3 + 10×64 = 647 bytes of payload. Records do not carry frame ids, timestamps, or SSRCs. Empty and oversized batches are rejected rather than truncated. OpenNOW’s nack_v2 in nvst_control.rs implements that layout and is covered by nvst_nack_tests on paired DTLS/SCTP peers.

Retry timing is separate from the payload. Bifrost SDP exposes rtpNackInitialWaitTimeMs, rtpNackBackoffTimeMs, rtpNackMaxRetries, rtpNackDjbInteractionMode, queue length, and queue max packets, per video index, and it logs the resolved integers (video[%d].rtpNackMaxRetries: %d and the rest). The constants OpenNOW uses, and that docs/mjolnir-nack-v2.md ties to this same binary, are a 4 ms extra wait, a 52 ms tracking budget, a starting RTT of 30 ms, and a send cap of clamp(floor(52 ms / RTT), 1, 3) including the first send. A zero RTT uses three sends and a 4 ms interval. With no fresh RTT sample the 30 ms default allows one send inside the 52 ms budget. The first request is eligible immediately. The 4 ms control tick can delay a retry; it does not fire one early. Sent requests stay resolvable until expiry even after they hit the send cap. Bundle-only generic NACK keeps a fixed 4 ms retry and a three-send cap. The official initial-delay and the mode-dependent 52/68 ms wait are named as outside OpenNOW’s implementation. rtpNackDjbInteractionMode is the attribute that would select that mode. OpenNOW does not emit it.

The Windows session log summarized in video.md is the runtime picture for an older branch: NACK wait 52 ms, 1024-packet hold, 2048 pending, 3 retries, 4 ms backoff. Those numbers are the same envelope OpenNOW advertises (rtpNackQueueMaxPackets:1024, rtpNackQueueLength:2048, rtpNackMaxPacketCount:64) and the same retry constants above. What that log also showed, and what this Linux binary names but OpenNOW does not send, is the next rung: NVST_R_SERVER_CONTROL_PICTURE_REQUEST_FAILED (IDR), NVST_R_SERVER_CONTROL_FRAME_INVALIDATION_FAILED, and a client request to freeze the display on an invalidated reference. OpenNOW’s unrecoverable-gap path sends RTCP PLI plus control 0x0302 (idr_request bytes 02 03 02 00 00 00) and drops inter frames until a keyframe. It has no reference-invalidation command. Intra-refresh is a frame-type string in Bifrost (Intra Refresh, Ref PIC I, Non Ref P). The Windows log advertised it and then ran with enableIntraRefresh: 0.

NACK version is an SDP integer (video.rtpNackVersion, logged as video[%d].rtpNackVersion: %d). The serializer’s hard-coded 2 is version 2 of that field. A peer that negotiates a different version would not be speaking this payload. OpenNOW always writes version 2 and does not branch on a negotiated version byte.

nvbSendInputEvent under radare2

nvbSendInputEvent is a global text symbol at 0x1a2090 in Bifrost (nm -D). pdf in radare2 shows a 642-byte function. The System V / Itanium return slot is rdi (preserved in r12). The real arguments are rsi (client object), rdx (session-id C string), and a 72-byte NvstInputEvent passed on the stack. The function returns the slot pointer in rax.

Control flow:

  1. If rsi is null, it writes result code 0x66 into the return object and returns. No session lookup, no log.
  2. Otherwise it locks (call 0x2144c0) and walks a tree rooted at the global 0x122bdb0 / 0x122bd60, comparing the client pointer with the u64 at node+0x20. This is a std::map/std::set lookup of registered clients, not a hash. Misses fall through to the 0x66-style early return path that actually stores 1 after a second check.
  3. On a hit it calls 0x1664a0 on the client, unlocks, then calls 0x166980. If that predicate returns zero, the result dword is 1.
  4. If the predicate passes and the session id (r13) is null or has length zero, it logs nvbSendInputEvent(). SessionIdentifier is '%s' through BifrostClient: Interface (0xd2f451 / 0xd30058), substituting the literal NULL (0xe38507), and stores result 0x65.
  5. Otherwise it calls 0x167660 with the result slot, the client, the session id, and the event pointer.

0x167660 is the session gate. It clears the result to 0xffffffff, locks the client at offset 0x358, and reads the byte at client+0x354. If that flag is clear, the result is 1 and it returns. If the session id is null, the result is 0x65. It then calls 0x167070 to resolve the session. Failure logs Session %s is not active. (0xd29b9a) under BifrostClient: BifrostClient and stores 0x134. Success calls 0x1aafd0(session, event) and stores eax as the result.

0x1aafd0 is a one-instruction trampoline: load the pointer at session+0x88 and jump to 0x1f8f80. That function is the stream send. It requires three pointers (object+0x70, a vfunc at vtable+0x90 returning non-null, and object+0x218). If any is missing it returns 0x155. Otherwise it pushes the nine qwords at event offsets 0x00 through 0x40 and calls vtable+0x38. A non-zero return becomes result 0x97 after logging Sending Input event failed: Nvsc Error: %s (0x%x) (0xd35de0) under BifrostClient: Streamer. A zero return checks a one-shot byte at object+0x198. If set, it clears the flag, zeroes 0x78 bytes, allocates 0x550 bytes, and calls 0x1b7040 with esi=0xe, then logs Sending NVB_SN_CLEAR_IDLE_TIMEOUT with event type: %d using the first dword of the event as the type. 0x0e here is an internal notification id on that queue, not ServerControl 0x0206 and not remote-input type 14. The event’s first dword is the NVST input type the log prints.

Geronimo’s call site matches this ABI exactly. BifrostSDKExecutor::sendNvstInputEvent is at 0x354a50. The byte at this+9 must be non-zero or the function returns without calling Bifrost (streaming not armed). Otherwise:

  • r9 = this+0x70 (the NVbClient)
  • rdx = this+0x10 (session id)
  • rdi = a stack return slot
  • nine pushes of 0x40(%rsi) down through (%rsi), which is the 72-byte event by value
  • call 0x1d5c00, the PLT stub whose jmpq *got at 0x1d5c05 is the R_X86_64_JUMP_SLOT for nvbSendInputEvent (GOT 0x20693d0)

The result dword is read back from the slot. The executor returns true only when that dword is zero (sete %al). So in this build, success is numeric 0, regardless of the order of the NVB_R_* name list in rodata. That list begins NVB_R_CANCELLED, NVB_R_SUCCESS, NVB_R_UNINITIALIZED, and continues through NVB_R_INVALID_PARAM, NVB_R_INVALID_CLIENT_OBJECT, NVB_R_INVALID_PORT_NUMBER, NVB_R_INVALID_INPUT_DEVICE, NVB_R_SESSION_NOT_ACTIVE, and stops being a pure NVB_R_ run after 74 names at Unknown NVbEvent. The immediates 0x66, 0x65, 0x134, 0x155, and 0x97 are outside that short prefix, so the name table is not a dense index of those failure codes. nvbEnumToString is how Geronimo turns a non-zero mic-audio result into a name; the input path in the executor does not log, it only returns the boolean.

The wrappers above the executor do not touch bytes. IOInterface::sendNvstInputEvent at 0x351ec0 loads this+0x68 and calls vtable+0x40, then returns 0 even if the executor failed. GridApp::sendNvstInputEvent (0x33edf0) and GridApp::doSendNvstInputEvent (0x3415a0) are the same tail call: object at this+8, vtable slot 0x208. There is no second encoder in Geronimo. SDL events become an NvstInputEvent before this chain. The 72-byte image is what crosses the ABI. Bifrost’s stream vfunc is what later wraps that image in ServerControl 0x0206 or gamepad 0x020d and writes it to a labeled data channel. This static pass stops at the vfunc call. It does not recover the per-type serializer that turns type 7 into the relative-mouse body OpenNOW builds in remote_input_packet.

A nearby function at 0x1ab120 is a different mapper, not the send. It walks a stride-0x40c table, switches on a field at offset 0x404 (compared against 11), and writes small integers 1 through 8 into an output descriptor, with a second field at 0x400 selecting among 0, 2, and 3. That is device-capability translation (the same region mentions NVB profile to NVSC profile: Converted NVB profile %d to NVSC profile %d.). It is easy to misread those movl $0x7 stores as remote-input type 7. They are not on the nvbSendInputEvent path.

What OpenNOW already matches

OpenNOW does not load either library. The overlap is behavioral and was checked against this image rather than assumed from the Windows log.

Signaling shape matches: OPTIONS, DESCRIBE, SETUP, ANNOUNCE, optional PLAY, WebSocket RTSPS, session id header, SDP application body. Video is a separate UDP socket with SRTP and a GS RTP extension. Audio, microphone, input, and RTCP are on the ICE/DTLS/SCTP bundle. ANNOUNCE says video is not on the bundle and data/audio are. Reserved ports are preferred and dynamic fallback exists. NACK-v2 is command 0x0317, version 2, stream ordinal, count, then 10-byte records, length 3+10N, cap 64, sent on control_channel_partially_reliable. The eight channel labels OpenNOW creates are a subset of the labels in this Bifrost. Activation order on the reliable channel (input off, device descriptor, cursor capture, cursor track, window state 19, system state, input on) is an OpenNOW test vector that lines up with the command names and the feature-type errors, not a trace lifted from this .so.

The differences that matter for feel and recovery:

  • Official channel creation stores factory-returned SIDs. OpenNOW uses fixed even SIDs. Routing is by label.
  • Official partial control was observed ordered with two retransmissions. OpenNOW’s partial channels are unordered with a 300 ms lifetime, on purpose, so mouse motion does not head-of-line block.
  • Official recovery can invalidate reference frames and freeze the display. OpenNOW NACKs, then PLI plus 0x0302, and has no invalidation command.
  • Official audio and mic SETUP are explicitly bypassed onto WebRtcTransport. OpenNOW never issues a Mjolnir SETUP for those streams.
  • Unified-socket mode is compiled into this Bifrost and compiled out of OpenNOW’s ANNOUNCE (enableUnifiedSocket:0).
  • input_channel_v1, gamepad_channel_v1, stats_channel, remote_trace_channel, and wac_metadata_channel are absent from OpenNOW’s profile.
  • Port numbers 49005 and 49006 are OpenNOW’s preferred pair plus a Windows log. They are not immediates in gs_04_87.
  • Mouse-settings feature type 10 still has no captured payload in either library.
  • The enet/ServerControlReliableUdp stack and the dcSCTP tuning attributes are present in Bifrost and reduced to one MTU line in OpenNOW.
  • NACK DJB interaction mode, initial wait, and the 52-versus-68 ms policy are attributes and prior analysis, not a path OpenNOW selects dynamically.
  • Geronimo drops the Bifrost result on the IOInterface path (always returns 0). A failed nvbSendInputEvent (0x134 session not active, 0x97 NVSC send failure, 0x155 missing stream) does not surface as a distinct shell error at that wrapper.

This is static analysis of one Linux Flatpak build. Decode

VulkanDecoder::decode is the hardware picture path on this build. The object keeps the decode-unit source at this+0x88, a frame pool at this+0x1e0, an allocator context at this+0x1e8, and two device-side shared pointers at this+0x1d0 and this+0x1d8. The incoming unit is rsi. The second integer argument, the bool, is saved and later inverted. The first virtual call is slot +0xc8 on the object at this+0x88. The stream id is the 16-bit field at unit offset 0x40. A second dword is taken from unit offset 0x8. The callee receives a pointer to a stack dword that the decoder sets to 13 before the call, with an extra zero pushed as the last argument. That call happens before any picture is allocated. It is a “work started” report, not a present.

The decoder then calls VulkanDecoder::allocFrame. A null return logs Failed to allocate frame against VulkanDecoder.cpp at level 5 and returns a null renderer. On success it calls an internal get-next function (0x4bdaa0) with the new frame and a byte out-parameter. If that function returns a count greater than 1, the decoder logs %d frames returned from GetNextFrame! and drains. Each extra picture drops two shared_ptr slots at frame +0x10 and +0x18 (the Itanium deleter is virtual +0x20 when the use count hits zero, unless the vtable identity mismatches a sentinel at 0x405690, in which case it calls the raw destructor). It then zeroes the frame header: qword at +0 becomes 0xffffffffffffffff, qword at +8 becomes 0, byte +0x68 is masked with 0xf8, and the block from +0x20 through +0x6c is cleared. The same get-next call is repeated until the count is no longer greater than 1. A Vulkan decode that surfaces a burst does not present the burst. It releases the extras and continues with a single frame. That is the opposite of a queue that accumulates decoder output for the presenter to catch up.

After the drain, a set out-parameter byte, or a negative count, is Stream/Decode Error! at level 5. The same virtual slot +0xc8 is invoked again with the stack dword set to 4. If the count is zero, level 4 logs No Frame. In every failure case VulkanDecoder::freeFrame runs and the function returns null. The bool argument selects whether a successful picture becomes a renderer. The decoder computes (count > 0) AND (bool XOR 1). When the bool is true, a decoded frame is freed and not wrapped. That matches a drain-or-skip entry point on the same function, not a second decode implementation.

The success path reads a description object from 0x4b8fa0 and writes a picture descriptor into the frame:

  • Bit 3 of the byte at description +0x48 is stored at frame +0xb4. One flag bit survives; the rest of that byte is discarded.
  • The byte at description +0x19, plus 8, is packed with the dword at description +0xc and stored at frame +0x10c.
  • The byte at description +0x49 selects a pair of identical dwords at frame +0xb0 and +0x100. The value 1 maps to 2, the value 9 maps to 4, and every other value maps to 1. Those are the only three chroma-or-format codes this function can emit.
  • The byte at description +0x4a is compared with 0x10. Equality stores 2 at frame +0x104; any other value stores 1. A 16-valued bit-depth field therefore takes the second code, which is the 10-bit container case (P010-style 16-bit storage), and every other depth stays on the first code.

The renderer is a 0x120-byte heap object. FrameRenderer::FrameRenderer(NvstVideoDecodeUnit_t const&, unsigned int, unsigned int) runs first, then the vptr is replaced with vtable for VulkanRenderer plus 0x10, which is the Itanium adjustment from the vtable symbol (offset-to-top and typeinfo) to the first virtual function. The decoded frame pointer is stored at renderer +0x108. The two device shared pointers are copied to +0x110 and +0x118, with an atomic increment when libpthread is linked. Width and height used for the constructor come from frame +0x90 and from +0x94 divided by the double at frame +0xa8. That double is initialized from the rodata constant 1.0 (0x3ff0000000000000 at 0x18a8f08) immediately before the division, so the height passed into the renderer is the integer truncation of height / 1.0 unless an earlier write changed +0xa8. The function returns the renderer pointer. Presentation is not performed here.

Sibling decoders exist and were not the ones listed with pdf, but their symbols fix the backend set. LAVCDecoder::decode is 1055 bytes at 0x5220a0 and is constructed either with a VulkanDeviceContext or with a thread count. Log strings record LAVCDecoder: using max %d threads for decoding, YUV converter failures, and avcodec open/find failures. VDPAUDecoder::decode and parseBuffer sit at 0x42d500 and 0x42d4f0, with capability queries for 10-bit, 4:4:4, and 4:2:2. platformCreateVideoDecoder and platformCheckVideoDecoderRgbaSupport choose among these at startup. The Linux official client can therefore decode with Vulkan video, with FFmpeg through LAVC, or with VDPAU. OpenNOW’s Linux path is the FFmpeg Vulkan-video decoder plus a VulkanPresenter. It does not carry a VDPAU backend, and it does not keep a second software LAVC renderer class beside the Vulkan one. The Windows note in video.md (D3D11 decode device, separate present device, ulNumDecodeSurfaces = 10) is a different binary. This .so does contain the split in a weaker form: VulkanDecoder owns the decode frame, and VulkanRenderer is a distinct object handed to AsyncFrameQueue. Decode and present are different types even when they share a Vulkan device.

Format changes are not handled inside decode. They are handled by the unexported VideoDecoder routine at 0x3dfe50 (2986 bytes, from endbr64 to the next endbr64 at 0x3e0a51). That function logs and stores:

  • Stream bit depth changed to: %u when the new depth differs from the byte at this+0x180.
  • Stream chroma format changed to: %u when the new chroma differs from the dword at this+0x184.
  • Stream colorspace changed to: %u hdr: %d range: %s when colorspace, HDR, or range differ from the cached dword at this+0x188 and the word at this+0x18c.
  • Stream resolution changed to: %ux%u only after the same width and height have been observed five times (cmp eax, 5 on a counter at a stack slot that is incremented while the size is unchanged). A one-frame glitch in the SPS does not announce a resolution change. Bit depth, chroma, and colorspace update on the first differing sample.

Colorspace values 2 and 4 take separate branches before a virtual call at slot +0x198 on the object at this+0x78. The other colorspace values fall through with the HDR byte zero-extended as an extra argument. The official session described in video.md (10-bit, chroma 3, colorspace 2, limited range, HDR off) is exactly the tuple this logger is built to print. OpenNOW’s Linux session adopts a decoder format change immediately and emits BackendEvent::FormatChanged, then LinuxFrameProducer::ensure_slot reallocates the output image. It does not debounce resolution across five frames, and it does not keep a separate colorspace/HDR/range cache that is compared field by field before the presenter is told. The practical difference shows up on a dynamic-resolution stream: Geronimo will keep the previous announced size until the new size has been stable for five samples, while still updating chroma and depth immediately. OpenNOW resizes the Vulkan image on the first accepted format change.

Two parser strings, Invalid SPS change at non-IDR and Invalid PPS change at non-IDR, are present twice (the decoder and a second copy of the same parser). A mid-stream parameter-set change that is not an IDR is rejected rather than applied. OpenNOW’s keyframe rule is the access-unit classifier in nvst.rs (H.264 NAL type 5, HEVC IRAP 16–21, AV1 SOF header byte 2). It will still submit a non-IDR access unit that happens to carry a new SPS unless the assembler has already declared the frame non-contiguous and dropped inter frames until a keyframe. Geronimo’s parser makes that rejection itself, inside the decode library, even when the transport delivered a complete access unit.

VideoDecoder::getNextFrame(bool, unsigned int) is the exported consumer at 0x3d6840, about 5808 bytes, and VideoDecoderSet multiplexes streams above it. The set also has setWaitTimeoutMs, updateDecoderSize, and requestProcessedFrame. HUD video is a separate HudVideoDecoderSet. OpenNOW has a single video queue in output.rs and no second decoder set for HUD. Overlay video, if the server sends it, has nowhere to go except the same frame queue.

Presentation

VulkanDecoder::decode returns a VulkanRenderer. The queue that owns presentation timing is AsyncFrameQueue. flush(bool) is the recovery-side view of that queue, and it also shows the state the presenter keeps. The function takes the mutex at this+0x30 when pthread_key_create resolved, calls an internal drain at 0x1db150 with the bool widened to 0 or 1, then logs Total video frames dropped : %u from the counter at this+0x1c8 at level 3 under the tag AsyncFrameQueue. It then zeroes that counter and a qword at this+0x1c0. An xmm constant from 0x19055b0 (a 1-ulp denormal in the low double and zero in the high double) is written to this+0x220, and a zero xmm is written to this+0x230. The dword at this+0x200 becomes 0xffffffff. Qwords at this+0x208 and this+0x210 become zero. The byte at this+0x21a becomes zero. The qword at this+0x250 becomes zero. The abs-mask constant at 0x18ae370 (0x7fffffffffffffff in the low qword, zero in the high) is stored at this+0x240. Two further subobjects, at this+0x290 and this+0x2c0, are reset through 0x1d72e0. std::condition_variable::notify_one runs on the condition variable at this+0x58. If the byte at this+0x1b8 is nonzero, a second condition variable at this+0x88 is notified as well. If the pointer at offset 0 is non-null, flush calls it with the same bool. The mutex is unlocked on the way out. A failed pthread_mutex_lock throws std::__throw_system_error.

The presenter’s queued state is therefore a drop counter, a pacing block of about 0x90 bytes starting at this+0x1c0, two condition variables, and an optional child queue. Flush does not destroy the decoder and does not send an IDR. It wakes every waiter, forgets the drop total after printing it, and clears the pacing block so the next frame is not scheduled from a pre-flush deadline. The recursive call means a queue can own another queue, which matches a decode queue feeding a present queue. OpenNOW’s Linux queue in output.rs is a single VecDeque behind one mutex. Overflow drops the oldest frame and sets a dropped flag. clear_linux_video empties it when the window is paused or hidden. There is no drop counter that is logged and then zeroed, no second condition variable gated by a mode byte, and no child queue. The Windows path in video.md is different again: the encoded queue capacity is 2, and overflow marks desync and requests a keyframe. Geronimo’s flush is a presentation reset, not an encoded-queue overflow policy.

FrameTiming::updateJitterAdvance(double, double) is the phase nudge applied once the queue has seen enough frames. The counter at this+0x100 is converted to a double, with the usual unsigned fixup when the high bit is set (shift, convert, add the value to itself). If that double is below 100.0 (0x4059000000000000 at 0x18a5d48), the function returns without touching the estimate. The first hundred samples are a warmup. After warmup, the first double argument is clamped to the closed interval from -0.075 to +0.075 (0xbfb3333333333333 and 0x3fb3333333333333). The second double argument arrives in xmm1 and is overwritten by the counter conversion, so this build does not consume it. The clamped value is passed to an updater at this+0xc8 (call 0x1d7800). If the pointer at this+0xf8 is non-null, the clamped value is passed through andpd with the mask at 0x18ae370, which clears the sign bit, and control jumps to 0x3f6190. The callback therefore observes the absolute advance, not the signed one. The signed value is what the estimator at +0xc8 sees.

An advance of at most 7.5 percent of a frame, withheld for the first hundred frames, is a small correction on top of a queue that already has min and max depth. It is not the jitter buffer. The buffer depth is the DJB config discussed below. The advance only slides the presentation timestamp inside that buffer. OpenNOW’s LinuxFramePacer estimates jitter differently and uses it for a different decision. observe_frame computes the absolute difference between the arrival interval and the media timestamp interval, ignores samples whose interval is zero or greater than 75 ms, and updates an EMA with weights 0.90 and 0.10. A decaying bound tracks the max. adaptive_queue_depth turns that bound into a depth of 0, 1, or 2 (MAX_ADAPTIVE_QUEUE_DEPTH is 2, and the threshold is 0.25 of the presentation interval). There is no 100-frame warmup, no ±0.075 clamp, and no split between a signed estimator and an absolute callback. VRR and fast streams do not use the depth at all: decision returns LatestReady and target_queue_depth 0, and take_linux_video_for_presentation then pops the newest frame and clears the rest. Geronimo’s cinematic and VRR hooks are separate methods on the same queue (vrrPresentDurationForFrame, cinematicPresentDurationForFrame, setVRRHardwarePacingEnabled, setServerDrivenFramePacingEnabled on SDLWindow). OpenNOW folds VRR into “present the newest frame immediately, and let FIFO plus the compositor provide tear-free scanout.” That matches the intent of the official VRR path only when the server is already pacing. It does not implement server-driven present durations, and it does not implement the cinematic interval helper.

Swapchain behavior is visible as a log, not as a function that was listed. Skipping swapchain recreation - only vsync changed and present mode is in cached compatible list is referenced from the graphics code near 0x51837e. A vsync-only change is not a full swapchain rebuild when the new present mode is already in a cached compatible set. Unable to resize vulkan swapchain to: %dx%d is the failure string for a real extent change. OpenNOW’s Linux presenter calls reconfigure when the drawable size changes and rebuilds the presenter when the decoder’s Vulkan device no longer matches (matches_vulkan_video_device). It does not keep a compatible-present-mode cache that would skip recreation for a vsync toggle. On Windows, video.md records the opposite policy from the official client: the UI starts vsync-on, streaming sets vsync 0 and DXGI_PRESENT_ALLOW_TEARING, and the missed-vsync counter climbs because present is not vsync-locked. The Linux binary’s optimization is “do not rebuild if only vsync changed and the mode is already legal,” which is compatible with that session behavior but is not the same mechanism as the Windows flip-discard swapchain.

output.rs also keeps presentation off the input path. Captured input is published before present, because FIFO acquire and queue_present can block in the compositor. Geronimo’s queue uses condition variables and a dedicated decoder thread (VideoDecoderThread is a typeinfo string). Both designs try to avoid coupling input to a stalled present. OpenNOW does it by ordering the pump. Geronimo does it by putting decode and present on different queues with explicit notify.

Recovery

The exported recovery entry point does not recover anything. IOInterface::flushAndRecoverVideoStream(unsigned short, bool) at 0x351da0 is endbr64; ret. IOInterface::handleDJBConfigRequest at 0x351e20 is the same two instructions. IOInterface::flushAllVideoStreams is the neighboring symbol at 0x351d80. Whatever those methods used to do, this build’s exported definitions are empty. Callers that go through the exported IOInterface symbols get a success return and no flush. The flush that actually runs is AsyncFrameQueue::flush, reached from the decoder and the renderer, not from that stub.

Decoder health leaves the process through BifrostSDKExecutor::updateVideoDecoderState at 0x354680 (172 bytes). The same this+8 gate applies. The call is nvbUpdateVideoDecoderState(context, session, streamId, frameId, state). Failure logs UpdateVideoDecoderState failed. state: %d. Error %s (%d) at level 5. This is how a stuck or reset decoder tells the server, and it is distinct from the in-process virtual call at slot +0xc8 that VulkanDecoder::decode uses with codes 13, 2, and 4. OpenNOW has no nvbUpdateVideoDecoderState. Its decoder-state signal to the server is the keyframe request: RTCP PLI plus NVST control 0x302, with a 250 ms cooldown, after an unrecoverable gap, a bad GameStream header, or an encoded-queue overflow. video.md records that the official session log contains Sent IDR request and Sent invalidation request, and that it does not contain PLI or FIR strings. Those IDR and invalidation messages are Bifrost’s, reached after Geronimo reports decoder state or after Bifrost’s own packet layer gives up. They are not emitted by VulkanDecoder::decode or by AsyncFrameQueue::flush.

The recovery ladder in video.md still describes the official client as a whole, and this binary confirms the client-side half of the lower rungs while leaving the upper rungs outside the library:

  1. Packet NACK and FEC stay in Bifrost. Geronimo never formats them.
  2. A presentation stall becomes AsyncFrameQueue::flush: log the drop total, zero the pacing block, notify waiters, flush the child queue. The decoder object survives.
  3. Decoder state, including the codes decode already reported locally, is forwarded with nvbUpdateVideoDecoderState when the executor path is used.
  4. IDR and reference invalidation are server requests made by Bifrost after that state, which is why the session log can say Sent IDR request for stream 0 and Sent invalidation request without either string appearing as a Geronimo log format in the video functions above. The strings that do exist here are the parser’s Invalid SPS change at non-IDR and Invalid PPS change at non-IDR.
  5. There is no device-lost path in the functions that were listed. video.md already notes that the sampled official session had no device-lost log. This library’s Vulkan decoder returns null and frees the frame on Stream/Decode Error!. It does not rebuild a device inside decode.

OpenNOW’s ladder is shorter and more local. A gap inside the NACK window is retried. An unrecoverable gap resets the assembler, sets contiguous=false, and requests a keyframe. Inter frames are dropped until that keyframe, and the keyframe rebuilds the transform. Encoded overflow clears the reference chain. A decoder error rebuilds the transform on the same device, then recreates graphics plus decoder for up to five seconds, then becomes fatal. There is no invalidation range, no “freeze the display on a bad reference” request, and no flush that preserves the decoder while wiping only the present queue. The closest OpenNOW operation to AsyncFrameQueue::flush is clear_linux_video on pause or hide, which drops queued frames without telling the server and without zeroing a pacing estimator beyond LinuxFramePacer::reset on stop and on a pacing-mode change.

reset_decoder after loss remains necessary on the Windows Media Foundation path, because MFSampleExtension_CleanPoint does not forget damaged H.264 references. Geronimo’s equivalent statement is the non-IDR SPS/PPS rejection plus the requirement that a real IDR arrive before the parser will accept a parameter-set change. A flush of the present queue does not substitute for that IDR. OpenNOW’s PLI/0x302 is the right family of request, and the official client’s extra invalidation command is still absent.

Mjolnir

Mjolnir, in the sense that matters for video, is the dedicated UDP socket that carries video SRTP, separate from the ICE bundle. video.md records that both clients prefer local port 49005 and that ANNOUNCE sets rtcVideoOnNativeBundle:0. OpenNOW implements that socket inside NvstVideoReceiver. SRTP key derivation uses labels 0x00 and 0x02 for RTP video, and 0x03 and 0x05 for SRTCP, matching the libsrtp split. The GameStream header is 16 bytes. FEC coordinates live in that header. The reorder window defaults to 1024 packets and is capped at 2048. The Mjolnir dequeue timeout while a gap is open is 52 ms. The SRTP replay window is the full 2048-packet cap so that a retransmission is not rejected as a replay. The UDP receive buffer is 8 MB. Access units are capped at 2 MB by default and 16 MB absolute.

None of those constants appear as immediates in the three Geronimo functions that were listed, and the Mjolnir strings in the extract are build paths. The video bytes enter Geronimo only as NvstVideoDecodeUnit_t. The unit fields this decode function actually reads are the dword at +0x8 and the 16-bit stream id at +0x40. Everything else about the unit is consumed by FrameRenderer’s constructor and by the description object returned from 0x4b8fa0. Parity work on the header layout, the FEC word (percent in bits 4–11, index in bits 12–21, source-packet count in bits 22–31), and the SOF/EOF flags belongs in nvst.rs, which already parses them, and in Bifrost, which this audit did not open. Changing Geronimo is not available, and copying a Mjolnir receiver into the Qt client beside NvstVideoReceiver would duplicate the socket OpenNOW already owns.

The practical parity gap on Mjolnir is not the socket. It is the set of client-to-server messages that ride beside it. Geronimo’s executor can send dynamic-streaming mode, L4S state, max bitrate, G-Sync or VRR info, a region-of-interest debug marker, DJB state, and decoder state, all as Bifrost calls, at any time after this+8 says a session exists. OpenNOW sends the corresponding video policy once, in the RTSP ANNOUNCE (x-nv-vqos[0].dynamicStreamingMode, dfc.adjustResAndFps, bitrate, FEC percentage, packet size), and then sends per-frame feedback (ack, pacing, NACK, IDR) from nvst_control.rs. A mid-session bitrate change is rejected. WindowsBackend::reconfigure_video has no in-tree caller. Live size changes arrive only as a decoder format change. Geronimo can push a new max bitrate with feature type 0x10 and log Successfully updated max bitrate to %d kpbs without a new ANNOUNCE. OpenNOW cannot.

NACK

Because the video NACK machine is not in this .so, the parity statement has to be made against the official client’s observed envelope, which nvst.rs already encodes, and against what Geronimo does when NACK fails to fill a gap.

OpenNOW’s constants, from nvst.rs, are the envelope video.md attributes to the official session: retry spacing 4 ms (NACK_RETRY_INTERVAL), default RTT 30 ms, tracking timeout 52 ms (NACK_TRACKING_TIMEOUT and MJOLNIR_REORDER_DEQUEUE_TIMEOUT), three attempts (MAX_NACK_ATTEMPTS), reorder depth 1024, and a NACK queue bound discussed as 2048 entries. A Mjolnir session sends nack_v2 on the partial control channel and preserves wrapping RTP sequence numbers. A non-Mjolnir session keeps RTCP generic NACK on the rtcp SCTP channel. A closed NACK channel does not spend an attempt and does not fall back to the other transport. Failed sends keep the shared budget. The FCI packer emits at most 64 packets per report, 17 sequence numbers per entry. Retransmissions that arrive before the NACK is sent still clear the range, and they are counted as recovered. After the tracking timeout the range is dropped and the assembler treats the gap as unrecoverable, which raises the keyframe request.

FEC sits in front of that. Repair packets are recognized when the percentage field is nonzero and the shard index is at least the source-packet count. Up to 128 FEC blocks can be held so that a later block does not discard an earlier incomplete one. The official session in video.md recovered 0 FEC packets and used 639 of 677 NACKed packets, with dynamic FEC enabled. OpenNOW advertises FEC in the 20–35 percent range at ANNOUNCE and will repair when the header describes a consistent block. A conflicting FEC layout invalidates only the discarded picture data, which is the behavior covered by nvst_recovery_tests.rs. Geronimo never sees this. By the time VulkanDecoder::decode runs, either the access unit was completed by Bifrost, or it was not delivered.

What Geronimo adds on top of a failed NACK is the present-queue flush and the decoder-state report, not another NACK. OpenNOW adds PLI and control 0x302. The official session log, per video.md, shows IDR and reference invalidation and does not show PLI or FIR. So the packet-level NACK parity is already the part OpenNOW has copied, and the gap that remains is the post-NACK server command: invalidation of a frame range and a display freeze on a bad reference, rather than a generic PLI. Implementing that command belongs in nvst_control.rs next to idr_request, and it has to use the Bifrost wire format. It cannot be inferred from AsyncFrameQueue::flush, which only forgets local frames.

The xDS “will NACK” string must stay out of that work. Wiring a video recovery path to a gRPC nonce would send the wrong message on the wrong socket.

DJB

DJB is the server-assisted jitter buffer. The receive path and the send path are both in the unexported VideoDecoder function at 0x3dfe50, and the wire send is BifrostSDKExecutor::setCurrentDJBConfig at 0x354730.

On receive, the function logs Received DJB Config request at frame %u. Force: %d, minDepthUs: %u at level 2 under the tag VideoDecoder. It stores the request: a dword at this+0x2cc, a byte/dword image at this+0x2c8, and a 16-byte image at this+0x2b8. If the force byte is nonzero, the min-depth dword and the following dword are each multiplied by 0x3e8 (1000) and passed to two setters (0x1d9d00 and 0x1d6d70). FrameTiming::overrideMinQueueTime and overrideMaxQueueTime take chrono::nanoseconds. Multiplying a microsecond field by 1000 produces nanoseconds, which matches those signatures and matches the log’s minDepthUs name. A force value of zero skips the override. The server can therefore push a config that is recorded but not applied until a later force, or push one that immediately replaces the queue bounds.

On send, the function compares a freshly computed status dword with the cached dword at this+0x2d4. An unchanged status does not generate a config. A change packs a mode dword and a reason dword into the qword at this+0x2d0 and logs Sending DJB Config at frame %u. Mode: %s, reason: %s, minDepthUs: %u, maxDepthUs: %u. The reason code selects the reason string: 3 stays on FIXED, 1 selects VVSYNC, and any other value selects UNKNOWN. The mode code selects the mode string: 1 stays on QOS, 2 selects MODE, and any other value selects UNKNOWN. The non-force path hardcodes mode 2 (MODE) before that compare. The force path sets mode from the saved byte at this+0x2c8: if that byte is below 1, mode becomes 2 (MODE); otherwise mode stays 1 (QOS). If the reason code is not 2, the qword at this+0x2d8 (the depth pair) is cleared before the send. The actual call is virtual slot +0x168 on the object at this+0x78, with the stream id taken from offset 0x90 of the object at this+0x70, the frame number, and a pointer to the packed config at this+0x2d0.

setCurrentDJBConfig forwards that pointer to nvbUpdateDJBState. If this+8 is clear the function returns zero and does not call Bifrost. A nonzero status logs setCurrentDJBConfig failed. Error %s (%d) at level 5. There is no local retry. The empty IOInterface::handleDJBConfigRequest means an inbound request that arrives through that exported method is ignored; the live inbound path is the decoder function above, which reads the request from the stream object rather than from the stub.

OpenNOW has no NvstClientDJBConfig_t, no nvbUpdateDJBState, and no mode enum of QOS, MODE, FIXED, or VVSYNC. LinuxFramePacer is a local substitute with a different control law:

  • VRR (cloud_gsync on the stream, and the negotiated flag) presents the latest frame on every pump, with no deadline and no target depth.
  • A fast stream, or a deadline missed by more than 75 ms, also takes the latest frame and rebases the presentation clock in mark_presented so missed deadlines are not replayed.
  • Otherwise the pacer waits until next_deadline and keeps the oldest frame, leaving adaptive_queue_depth() frames queued. That depth is at most 2.

Geronimo’s DJB depth is a time interval in microseconds, supplied by the server, converted to nanoseconds, and applied as min and max queue time on FrameTiming. It can be many frames at 120 FPS if the server asks for it. OpenNOW’s depth is a frame count capped at 2, computed from local arrival jitter, and ignored entirely in the VRR and fast-stream modes. The ±0.075 jitter advance, with its 100-frame warmup, has no counterpart. A high-jitter 120 FPS session on OpenNOW will either hold one or two frames or, once the stream is classified fast or VRR, always show the newest frame and drop the rest. The official client will hold whatever interval the server’s DJB config names, and it will only nudge the phase by 7.5 percent of a frame after the warmup. That is the largest presentation-quality gap on the Linux path. Closing it means accepting a server DJB config on the control channel and driving overrideMinQueueTime / overrideMaxQueueTime equivalents from minDepthUs and maxDepthUs, including the times-1000 conversion into nanoseconds, and reporting the chosen mode and reason back with the same QOS/MODE and FIXED/VVSYNC labels. Inventing a deeper local queue without the server config will not match, because the official depth is not locally derived.

FrameTiming also exposes nextPresentationTimestamp, boundedJitterEstimate, arrivalJitterBoundEstimate, targetQueueTime, vrrFrameDuration, and jitterAdvance. The advance getter is the value updateJitterAdvance maintains. OpenNOW’s jitter_bound_ns is an analogue of arrivalJitterBoundEstimate only in the sense that both are a decaying peak of arrival error. The official bound then feeds queue time. The OpenNOW bound feeds a depth of at most two frames and only on the slow, non-VRR path.

Dynamic streaming

Dynamic streaming is feature type 0x0F, and the failure string groups it with resolution and frame-rate control: Fail to update feature DRC/DFC. BifrostSDKExecutor::setDynamicStreamingMode(unsigned short, NvstDynamicStreamingMode_t) at 0x353e00 builds a 16-byte blob. The first dword is 0x0F. The stream id is stored as a word. The mode dword is the NvstDynamicStreamingMode_t argument. nvbFeatureControl is called with the Bifrost context and the session pointer. Success stores the mode at this+0x30 and logs Successfully set dynamic streaming mode to %d at level 3. Failure logs GERONIMO_ERROR 0x%08X %s: %s with code 0xC001000F and the tag GERONIMO_GRIDAPP_CONTROL_FEATURES, then nvbFeatureControl failed for type: %d. Error %s (%d) with type 15. The return value is the session-ready byte, cleared to zero on the failure path. IOInterface::setDynamicStreamingMode does not contain this logic. It loads the pointer at this+0x68 and tail-calls virtual slot +0x88. GridApp::setDynamicStreamingMode is 48 bytes at 0x3423c0, another forwarder. The executor is the only place the mode becomes a Bifrost feature write.

The same listing shows the neighboring feature writes, which share the prologue and the log helper and are easy to confuse with the mode function if pdf is allowed to run past its ret:

  • setL4sState uses feature type 0x13 and logs Successfully %s L4S feature with enabled or disabled. Failure text is Fail to update feature L4S.
  • setStreamingMaxBitrate uses feature type 0x10 and logs Successfully updated max bitrate to %d kpbs. The stored value is kept at this+0x38.
  • sendGsyncInfoToServer uses nvbSendClientInfo twice, type 2 then type 3, and logs Failed to send VRR info! if the first call fails. It still attempts the second call after that log.
  • A later helper sends a client region-of-interest marker through nvbSendStreamStats with an outer type byte of 3 and an inner code 0x11a, and logs %s client region of interest debugging marker with either Sent or Failed to send. If this+0x18 is null it logs No active session at level 5 and returns zero.

startStreaming logs the mode in the same line as the rest of the request: Requested Resolution: %dx%d@%d, codec: %s, SDR colorSpace: %d, HDR colorSpace: %d, bitDepth: %d, chromaFormat: %d, HDR: %d, bitrate: %d, dynamicStreamingMode: %d. A second line records the converted request, including drcDfc and framePacingMode. The mode is therefore both an ANNOUNCE-time parameter and a live feature-control value. video.md already records the schema: 0 off, 1 prefer FPS, 2 prefer resolution, 3 on. The official client does not put that field in CloudMatch requestedStreamingFeatures. It travels as x-nv-vqos. The sampled sharedstorage.json profile had dynamicStreamingMode: 0.

OpenNOW matches the ANNOUNCE half. negotiated_dynamic_streaming_mode in nvst_rtsp.rs takes a server-finalized value from negotiatedStreamProfile.dynamicStreamingMode when it is in 0..=3. Otherwise it sends 1 when saveBandwidth is true and 0 when it is false. negotiated_adjustment_enabled sets dfc.adjustResAndFps to 1 exactly when the mode is nonzero. The comment in that function states the same CloudMatch omission the official client uses. A mid-session toggle of saveBandwidth does not rewrite the running ANNOUNCE, which video.md also states. What OpenNOW does not do is the live nvbFeatureControl of type 0x0F. The official client can change the mode after the stream has started, store it at executor+0x30, and have the server apply DRC/DFC without a new RTSP session. OpenNOW’s next opportunity to change the mode is the next ANNOUNCE. Locally, a format change still resizes the Vulkan image, so a server that changes resolution on its own will be displayed. A server that is waiting for a feature-control update before it changes resolution will keep the original size for the whole session.

The same gap applies to max bitrate (type 0x10) and L4S (type 0x13). OpenNOW’s ANNOUNCE carries a bitrate ceiling, and a missing maxBitrateMbps becomes 75 Mbps on the wire while the local media config still says 10 Mbps. That internal disagreement is an OpenNOW bug of its own, already called out in video.md, and it is independent of Geronimo. Geronimo’s live bitrate update is a separate channel, in kilobits per second, logged explicitly, and stored on the executor. A parity implementation would send feature type 0x10 when the user changes the ceiling mid-session, rather than rejecting the IPC bitrate message.

drc and dfc are not the same knob. The executor’s failure string treats feature 0x0F as the combined DRC/DFC update, while the start log prints drcDfc as its own integer next to dynamicStreamingMode and framePacingMode. OpenNOW emits dfc.adjustResAndFps as the boolean companion of the mode and leaves drc.enable and the resControl attributes at the streamer defaults, because it does not emit them. That matches the “do not override what we do not know” choice in video.md. It is not the same as sending the integer the start log calls drcDfc. Until a capture shows the ANNOUNCE integer and the feature-control mode diverging, the safe client behavior is the one OpenNOW already has at session start: mode 0 or 1 from the Data Saver toggle, adjustResAndFps following the mode, and no CloudMatch field. The missing piece is the mid-session nvbFeatureControl of type 0x0F, not a second CloudMatch field.

What parity requires, and what it does not

The Linux official video path in this build is a pipeline with a hard boundary. Bifrost delivers decode units and accepts feature, DJB, and decoder-state calls. Geronimo decodes on Vulkan, LAVC, or VDPAU, wraps one picture in a VulkanRenderer, and presents through AsyncFrameQueue and FrameTiming. Bursts from GetNextFrame are released, not queued. Chroma bytes 1 and 9 become format codes 2 and 4, and any other byte becomes code 1. A bit-depth byte of 0x10 becomes code 2, and every other depth becomes code 1. Format changes update depth, chroma, and colorspace immediately, and they update resolution only after five identical samples. SPS or PPS changes at a non-IDR are rejected. The jitter advance warms up for 100 frames and then clamps to ±0.075, with the absolute value forwarded to an optional callback. DJB min and max depths arrive in microseconds, scale by 1000 into nanoseconds, and are reported back with modes QOS or MODE and reasons FIXED, VVSYNC, or UNKNOWN. Dynamic streaming, L4S, and max bitrate are nvbFeatureControl types 0x0F, 0x13, and 0x10. The exported flushAndRecoverVideoStream and handleDJBConfigRequest are empty. The flush that runs clears present-queue pacing state under a mutex and can recurse into a child queue. It does not send an IDR.

OpenNOW already matches the transport half that this .so does not contain: Mjolnir on its own UDP socket, the 16-byte GameStream header, FEC, a 1024-packet reorder window, a 52 ms gap wait, three NACK attempts, and a 4 ms retry. It already matches the session-start half of dynamic streaming: the mode is RTSP-only, values outside 0..=3 are ignored, and adjustResAndFps follows the mode. The gaps that this binary makes concrete are all on the far side of the decode unit.

The present queue should learn a server DJB depth instead of a local cap of two frames, and VRR should remain a mode inside that config (VVSYNC as a reason, force selecting QOS versus MODE) rather than only a “latest frame, depth zero” shortcut. The jitter advance should stay a small clamped nudge after a warmup, not the thing that decides the depth. A present-queue flush should drop queued frames, zero pacing deadlines, and keep the decoder, which OpenNOW’s pause path already approximates and which its loss path does not: loss currently jumps straight to a keyframe and a transform rebuild. Decoder state should be reported to the server as a distinct message from the PLI, because Geronimo’s codes 13, 2, and 4, and nvbUpdateVideoDecoderState, are how the official client gets Bifrost to emit the IDR and the invalidation that video.md observed. Dynamic streaming, max bitrate, and L4S need a mid-session feature write, types 0x0F, 0x10, and 0x13, or the server will keep the ANNOUNCE values until the next session. Resolution changes from the server can keep a short stability count before the swapchain extent changes; chroma, bit depth, and colorspace should move on the first sample, and a parameter-set change that is not a keyframe should be refused.

None of that work belongs in a second Mjolnir receiver, and none of it should be keyed off the xDS NACK strings. The packet path in nvst.rs is the right place for the NACK and FEC envelope that this library does not implement. The platform path in output.rs and linux_frame_pacing.rs is the right place for DJB depth, the clamped advance, and the flush that preserves the decoder. The RTSP and control path is the right place for feature types 0x0F, 0x10, and 0x13, and for a decoder-state report that can provoke an official-style IDR and reference invalidation instead of only a PLI.

Audio

Audio: Opus, RFC 2198 RED, and jitter

The Linux official client splits game audio across three libraries, and only one of them is an Opus stack. libGeronimo.so owns the playback sink and the microphone glue. libGsAudioWebRTC.so owns capture, playout devices, and acoustic processing. Neither binary contains an Opus encoder, an Opus decoder, a NetEq jitter buffer, or an RFC 2198 redundant-audio depacketizer. Those strings live in the sibling NVST library libBifrost2.so, which Geronimo reaches through BifrostSDKExecutor and nvbSendMicAudioFrame / nvbConfigureAudioChannelCount. Reading Geronimo or GsAudioWebRTC alone and concluding that official GFN has no RED, or that GsAudioWebRTC is the playback jitter buffer, would invert the ownership. The comparison notes in docs/streamer-comparison/audio.md describe the Windows session (WASAPIAudioRenderer, NVST:OpusAudioDecoderWrapper, NVST:RtpAudioPlayer, NVST:TimestampAudioBuffer). The Linux extracts confirm the same NVST names and add the SDL and WebRTC device path that the Windows notes do not cover.

Where each stage sits

Bifrost’s audio receive path is WebRtcTransport plus WebRtcAudioRtpReceiver plus RtpAudioPlayer plus OpusAudioDecoderWrapper. The receiver thread logs “Webrtc RTP receiver thread started”, “Client received the first audio packet”, and “Client received the first audio packet after: %f ms since start of session”. Decoded PCM is handed upward as NvstAudioFrame_t. Geronimo’s IOInterface::registerAudioCallback installs an AudioFunc. On Linux that function object is SDLAudio, which implements operator()(NvstAudioFrame_t const*) and renderAudio. The log “IOInterface is NULL when rendering audio” and the error GERONIMO_IOINTERFACE_INVALID_IOINTERFACE_AUDIO fire when that handoff has no owner. Audio Renderer is NULL is the matching failure when the callback itself is missing. So the jitter buffer and the Opus decode finish before SDL ever sees a sample. SDL’s job is to queue PCM and satisfy the audio callback.

FrameTiming inside Geronimo is a video dejitter, and it is easy to misread as the audio buffer because the names overlap. The methods are updateJitterAdvance, jitterAdvance, boundedJitterEstimate, and arrivalJitterBoundEstimate, plus targetQueueTime and overrides for min and max queue time. The format strings are “Updating adaptive queue depth %zu => %zu for jitter %ldus”, “Size dejitter buffer to match network conditions”, and “The target queue depth is sized based on observed frame arrival jitter multiplied by jitter factor.” FrameStats prints pJitter, tqt, and faj in the same video line. The CEF shell even has a source path client/cef/src/nvxjitter.cpp. None of that is the audio jitter buffer. Audio has its own object, named in Bifrost as TimestampAudioBuffer, gated by audio.enableTimestampAudioBuffer and the SDP key x-nv-audio.enableTimestampAudioBuffer.

Codec, payload types, and the ANNOUNCE contract

Bifrost’s SDP templates pin the clock and the redundancy payload type. The strings include a=rtpmap:63 red/48000/2, the same map for 6 and 8 channels, a=fmtp:63 111/111, and a=rtcp-fb:63 transport-cc. Primary Opus is payload type 111 (a=rtpmap:111). multiopus/48000/ is present for the surround maps. fmtp:63 111/111 means each RED block, primary and redundant, is itself payload type 111. That is the nested-RED form RFC 2198 uses when the redundant encoding is the same codec, not a second codec. Channel count is a separate negotiation: audio.surround.numChannels, audio.surround.channelMask, audio.surround.AudioQuality, x-nv-audio.surround.enable, x-nv-audio.samplesPerSecond, and x-nv-audio.apiType. Geronimo logs “Channel count supported %u” and “Streaming channel count is %d , incoming channel count is %d”, and it calls nvbConfigureAudioChannelCount. A mismatch is an error string, nvbConfigureAudioChannelCount Error %s (%d), and the renderer can refuse the stream with GERONIMO_SDLAUDIO_RENDER_AUDIO_PARAMS / “Incompatible audio stream.” The Windows session note that stereo plus surroundAudioInfo: 2 logs “Number of channels(2) is not valid for surround” matches this split: CloudMatch can ask for a surround info value while the open device is stereo, and both sides of that check exist as distinct fields.

AQOS keys in the same binary are x-nv-aqos.enableRedundancy, x-nv-aqos.redundancyLevel, x-nv-aqos.packetDuration, x-nv-aqos.bitRate, x-nv-aqos.bitDepth, x-nv-aqos.enableEcn, x-nv-aqos.forceEnableEcn, and x-nv-aqos.enableAudioStats. Microphone redundancy is a second pair, aqos.enableRedundancyForMic and aqos.redundancyLevelForMic, also spelled as x-nv-aqos.enableRedundancyForMic. Playback and mic do not share one redundancy level. The runtime logs are explicit: “Audio redundancy enabled using RFC2198 (RED), redundancy level is %u” and, separately, “Mic redundancy enabled using RFC2198 (RED), redundancy level is %u”. A coarser line, “Enabling RED audio redundancy” and “%s audio redundancy”, brackets enable and disable. The comparison doc’s Windows session printed level 2 on playback and level 3 on the mic, with in-band Opus FEC disabled. Those integers are session output. The Linux string table shows the format, not the value the server chose for that capture.

OpenNOW’s current ANNOUNCE in nvst_rtsp.rs writes a=x-nv-aqos.enableRedundancy:1 and a=x-nv-aqos.redundancyLevel:2, and the audio track is payload type 111, Opus, 48000 Hz, two channels. docs/streamer-comparison/audio.md still says the client advertises enableRedundancy:0 and redundancyLevel:0. That sentence describes an older tree. The transport that matches the current ANNOUNCE is in nvst.rs: GFN_OPUS_PAYLOAD_TYPE is 111 and GFN_RED_PAYLOAD_TYPE is 63. A packet matches the audio track when its payload type is the negotiated Opus type, or when the track is Opus 111 and the packet is RED 63. SSRC is checked when the track recorded one.

What RED recovery actually does

parse_red_opus follows the RFC 2198 header. A block whose high bit is clear is the primary: one byte, payload type in the low seven bits, and that type must be 111 or the packet is MalformedRedAudio. Blocks whose high bit is set are redundant headers of four bytes. The 14-bit timestamp offset is taken from the next two bytes (top 6 bits of the third byte included), and the 10-bit block length is the low 2 bits of that byte plus the fourth byte. OpenNOW accepts at most eight redundant headers (MAX_REDUNDANT_AUDIO_BLOCKS) and rejects an empty block or a block longer than 1275 bytes, which is the Opus packet maximum (MAX_OPUS_PACKET_BYTES). The primary is whatever remains after those blocks, and it has the same emptiness and size checks.

Recovery is sequence-driven, not a jitter buffer. NvstAudioReceiver remembers the last SSRC and sequence. A repeat or a large backward jump (delta 0 or delta at least 0x8000) yields no frames. A forward gap of N missing sequence numbers recovers min(N, redundant_blocks) older blocks, using the timestamp offset subtracted from the RTP timestamp, then appends the primary at the packet timestamp. contiguous on the first emitted frame is true only when the source did not change and every missing packet was filled from RED. A gap larger than the redundancy depth stays non-contiguous. A source change resets the measurement and does not invent concealment across senders. Packets that RED already restored carry their own timestamps, so a later stage that keys concealment off contiguous does not conceal them a second time. The comparison doc’s older line, “if a RED packet still arrives, OpenNOW keeps the primary and drops the rest,” is the behavior of a strip-only parser. The current receiver emits the redundant blocks when the sequence gap asks for them.

Official decode sits on the other side of that wire. OpusAudioDecoderWrapper logs “Opus decode returned %d (%s)”, “opus_multistream_decoder_create() failed”, and “Parameters: sampleRate=%u, channels=%u, streams=%d, coupled_streams=%d”. “Audio RED decode fail count: %u” is a session counter. The Windows note recorded a fail count of 0 alongside 17412 stale drops, which is the important split: RED can be healthy while the jitter buffer is still throwing late packets away. “Failed to encode RTP header for redundant, RED, packet” is the sender-side failure, used for the microphone and for any client-originated redundant audio. “Failed to parse headers for recovered packet %hu” is the receiver rejecting a reconstructed RTP header after a repair.

Three different “FEC” mechanisms, plus PLC

The binaries use “FEC” for more than one thing, and mixing them up produces the wrong fix.

In-band Opus FEC is a codec flag on OpusAudioEncoderWrapper. The strings are “Setting in-band FEC feature to: %s”, “Set bInBandFec mismatch: %d”, and “In-band FEC cannot be enabled in CELT_ONLY mode”. The Windows session log said this flag was off. OpenNOW’s Linux decoder calls decode_float with the FEC request argument 0, including the packet-loss concealment call that passes a null packet. So both clients can run with in-band FEC disabled and still have other redundancy.

RFC 2198 RED is the mechanism behind “Audio redundancy enabled using RFC2198 (RED)”. It repeats whole previous Opus packets inside a payload type 63 packet. It does not require the Opus in-band FEC bit. Level 2 on playback means the primary plus two older blocks when the server honors redundancyLevel. Level 3 on the mic is the same encoding with a deeper history, logged on its own format string.

A third path is an RTP FEC sink that is not RED. Bifrost logs “Creating plain RTP sink (no FEC)”, “Creating FEC RTP sink”, “Creating Packetizer RTP sink”, “MAX FEC audio payload size set to %d”, “FEC decoding: Received Opus buffer size = %d, exceeding maximum allowed of %d”, “FEC detected invalid parity packet”, and “Server uses FEC in legacy CBR mode”. Those lines sit next to Reed-Solomon and FlexFEC video machinery (ReedSolomonFecDecoder, FlexFecDecoder) but the Opus buffer-size line is explicitly an audio payload check. Video FEC repair percentages in ANNOUNCE (vqos[0].fec.repairPercent and the OpenNOW lines that set repair 20/20/35) are the Mjolnir video code. They do not conceal an Opus gap. Audio continuing while video FEC is unhealthy is exactly the diagnostic split the streamer rules call out: a live SDL callback does not prove the video receive path.

PLC is the fourth stage, and it runs inside the Opus decoder after the packet is already missing. Bifrost logs “PLC Error: Invalid Last Packet Length”. OpenNOW’s embedded Linux backend measures the hole from RTP timestamps. conceal_before subtracts the last decoded frame duration from the timestamp span, converts ticks to samples, and synthesizes that duration with a null-packet decode. The budget is MAX_PLC_MS of 100. Past that cap it stops fabricating and the next real packet re-anchors last_timestamp. A source change resets the decoder instead of concealing. A redundant recovery that already filled the sequence gap sets contiguous, so this PLC does not run for those samples. The shared non-Linux decoder path synthesizes one frame duration per gap. The WASAPI renderer described in the audio note is a different underrun policy: padding == 0 stops and resets the client, then waits for a larger preroll (15 ms, plus 5 ms per underrun, cap 60 ms). The SDL software fallback in that same note zero-fills a 120 ms ring. Official Linux SDL does the zero-fill equivalent on purpose: SDLAudio::resetSilence, s_silencePlayed, and s_audioPlayed are separate counters, and the buffer API is put, get, size, setMaxSize, setQueueSize, pause, resume, shouldExit.

OpenNOW has no TimestampAudioBuffer and does not advertise x-nv-audio.jbConfig.* or enableTimestampAudioBuffer. Loss recovery is RED plus PLC, as above. How a gap becomes something you hear

A lost Opus packet on the official Linux client can be repaired three times before silence. RED in the payload type 63 packet can supply the missing sequence if the redundancy depth covers it. The Opus decoder can PLC a remaining hole, unless in-band FEC was left off and the PLC length check fails. The TimestampAudioBuffer can absorb the arrival-time spike by raising its threshold, or it can drop the packet as stale if it arrives after the playout point. Only what survives that buffer reaches SDLAudio::put. If the callback still underruns, SDL plays silence and increments s_silencePlayed. A RED decode failure increments a different counter and does not by itself mean the jitter buffer flushed.

On OpenNOW the same loss is repaired if the RED depth covers the sequence gap, then by Linux PLC up to 100 ms measured from RTP timestamps, with in-band FEC left off. There is no adaptive audio threshold and no stale-drop counter of the TimestampAudioBuffer kind. Encoded and PCM queues drop oldest. The WASAPI shared path stops and resets on a true underrun instead of stretching silence in place. The SDL fallback zero-fills. Device loss on Windows clears PCM and retries every 250 ms so audio cannot stall video. Official Linux refuses that default-device retarget and keeps the sink it opened.

The practical difference is which stage you can see in a log. Official can tell you RED fail count, JB threshold, stale versus overflow versus max-size drops, write delay, and silence-versus-audio bytes. OpenNOW can tell you whether the sequence gap was contiguous after RED and whether PLC ran. GsAudioWebRTC can tell you AEC delay jitter on the microphone, which will move when the game-audio reverse stream is late, and that number is not the playback buffer depth.

Input: mouse, gamepad, and NVB features

Official input on this Linux build is a stack of four owners, and they do not share one packet format. libGeronimo.so captures devices and decides policy. libBifrost2.so turns that policy into NVST remote-input events and into nvbFeatureControl feature blobs. The wire OpenNOW actually sends is nvst_input.rs. docs/streamer-comparison/mouse-input.md, controller-input.md, and features.md were written against a Windows geronimo.log plus an older encoder. Several of their “OpenNOW does not send this” claims are stale against the current file, and several of their Windows capture details are a different platform path from the Linux symbols in libGeronimo.so. The feature-type numbers in the Windows log still match the Linux format strings. The bytes of feature type 10 still are not in either string table.

Two planes: remote input and feature control

Every gamepad sample, mouse sample, and key is an NvstInputEvent_t. Geronimo’s IOInterface::handleInputEvent and sendNvstInputEvent forward it. BifrostSDKExecutor::sendNvstInputEvent calls nvbSendInputEvent. The Bifrost log “Failed to execute sendInputEvent() since connection is not established” is that call before the session is up. Separately, IOInterface::controlFeatures(NVbFeatureControlType_t, unsigned int, bool) and BifrostSDKExecutor::controlFeatures call nvbFeatureControl. Geronimo logs “Update feature type: %d”, “%sabled feature type: %d”, and “nvbFeatureControl failed for type: %d. Error %s (%d)”. Bifrost logs “nvbFeatureControl(): NVbFeatureControlType: %d is invalid. NVB_FEATURE_MAX_TYPE = %d” and “nvbFeatureControl(). SessionIdentifier is '%s'”. The Windows log prints a heap pointer for the feature object and then the type number. That pointer is the client object. It is not a payload. The Linux strings do not add a hex dump either.

features.md maps the types that the Windows log actually emitted. Type 0 is toggled on every cursor-info change and is the server-composited cursor. Type 6 follows “Sending haptics state 1 to server” and is gamepad rumble. Type 8 is enabled once when the session is ready and tracks the remote cursor image. Type 10 is the line next to “Sending SDL mouse settings (accel=0, speed=10)” or “Sending alt mouse settings (accel=%d, speed=%d)”. No other type numbers appear in that log set. The Linux binary has the same verbs and adds the default-alt string below. It does not print a table of type numbers next to names, so the mapping still depends on the surrounding log line, not on a symbol named FeatureType10.

OpenNOW’s control header is a little-endian u16 command, a little-endian u16 length, then payload. 0x0308 on the wire is 08 03. The commands that correspond to the named features are COMMAND_MOUSE_CURSOR_CAPTURE 0x0308 for type 0, COMMAND_TRACK_REMOTE_CURSOR_IMAGE 0x030d for type 8, and remote-input type 13 under COMMAND_REMOTE_INPUT 0x0206 for the haptics enable that features.md aligns with type 6. There is no captured type 10 frame and no 0x0323 symbol in the current nvst_input.rs. features.md says the test helper used to insert a reconstructed mouse-settings command and that it must not be treated as a capture. The current activation_chain does not include that command at all.

Mouse capture on this Linux binary

The Windows notes describe SDL plus a focus-gated Raw Input thread, RIDEV_INPUTSINK, and WM_INPUT. libGeronimo.so is the Linux client (DVSOS = Linux in the Bifrost build strings, and the CEF path GFN-cx-lin-official). Its native mouse owner is XInput2InputController, not Raw Input. The strings are “XInput extension not available”, “XInput minimum required version not met”, “XInput Select raw events failed with error %d”, “XInput version: %d.%d”, “initMouse: mask %x”, “XInput2InputController::resume”, and “XInput2InputController::pause”. Failure to create epoll or the signalling pipe logs “disabling native input and falling back to SDL input”. SDLEventProcessor is the fallback and the always-present SDL path: “Using native input controller”, “Using SDL input”, “Initialized native input controller”, “Updating SDL Event Processor to use raw events” is the Windows-log wording; the Linux binary’s equivalent switch is the native-versus-SDL pair and “Input controller failed: %s”. “SDLEventProcessor::initialize called more than once” either updates the controller or disables it. Multi-window operation logs “Uninitializing and falling back to SDL input path”.

Wayland-on-X is a third controller, XWaylandInputController. It confines with the X pointer grab: “Cannot confine pointer, either display or window is not set” and “XGrabPointer failed: %s (%d)”. Grab results include AlreadyGrabbed, GrabFrozen, GrabNotViewable, and GrabInvalidTime. That is the Linux analogue of the Windows note’s ClipCursor, which the OpenNOW Windows crate does not call. OpenNOW’s embedded Linux mouse path is XInput2 as well, and the mouse note warns that XI2 can emit buttons twice when SDL still owns buttons. Official’s fallback is explicit: if the XInput2 controller cannot start, SDL remains the only producer. Official does not run both as equal sources once the native controller is up.

MouseAccel is a real object in Geronimo: s_mouseAccel, s_trackpadAccel, getMouseAccel, setMouseAccel, enableMouseAccel, disableMouseAccel. The Linux client reads the host curve before it decides what to send. Failures are “Failed to retrieve mouse sensitivity: libinput properties not available”, “Failed to get mouse sensitivity from gsettings”, “Failed to retrieve mouse acceleration”, “Failed to parse mouse accel-profile from gsettings”, and “Failed to get mouse accel-profile from gsettings”. The property names in the binary are “libinput Accel Speed” and “libinput Accel Profile Enabled”. The gsettings invocation string is gsettings get org.gnome.desktop.peripherals.mouse speed together with accel-profile. So the Linux official client both reads the desktop’s libinput speed and profile and also has a separate API that enables or disables acceleration inside the process. Those are different layers. Reading gsettings does not by itself prove the host game receives that curve. The host curve is the feature-control message.

Feature type 10, and the three log lines that bound it

IOInterface::sendMouseSettings(bool, int), SDLWindow::sendMouseSettings, SDLEventProcessor::sendMouseSettings and sendMouseSettingsIfNeeded, and BifrostSDKExecutor::sendMouseSettings(bool, unsigned int) are the producers. The format strings, in one cluster, are:

Sending SDL mouse settings (accel=0, speed=10)

Sending alt mouse settings (accel=%d, speed=%d)

Sending default alt mouse settings (accel=1, speed=10)

The SDL line is a fixed format, accel 0 and speed 10, compiled into the string. The alt line is parameterized. The default-alt line is accel 1 and speed 10, used when the client is not applying the “acceleration off” override. The Windows log’s “Disabling session mouse acceleration” at session start, and the focus and blur lines that print accel=0, speed=10, match the fixed SDL string and the alt format. The Linux binary adds the accel-1 default, which the Windows notes do not quote. Bifrost’s failure strings are “Failed to %s feature mouse acceleration. Nvst Error: %s (0x%x)” and “Failed to update mouse sensitivity: %d %s (0x%x)”. features.md already parsed the second format: the %d is the speed value, and a log line “Failed to update mouse sensitivity: 10 NVST_R_SUCCESS” means speed 10 came back with a success code that the client still treated as a failed update because NVST was not ready. That 10 is not the feature type. The type is the following “nvbFeatureControl failed for type: 10”.

Nothing in the string tables is the on-wire body. There is no hex format next to sendMouseSettings. features.md records the searches that failed: no pcap, no control-frame hex, no runtime.mouseAccel key. The SDP and config keys that do exist nearby are mouseMovementFlags in Bifrost and runtime.mouseCursorCapture / runtime.mimicRemoteCursor. OpenNOW’s ANNOUNCE sets x-nv-runtime.mouseCursorCapture:3 and x-nv-runtime.mimicRemoteCursor:0. Those are runtime flags in the RTSP body. They are not a substitute for the type 10 feature blob, and they do not encode accel and speed. OpenNOW’s client-side curve is tune_relative_mouse in the core crate, applied only when building a type 7 packet. OPENNOW_MOUSE_SENSITIVITY defaults to 1.0 and clamps to 0.1–3. OPENNOW_MOUSE_ACCELERATION defaults to 1.0, clamps to 1–150, and at 1.0 leaves the deltas unchanged. Above 1.0 the factor is 1 + min(0.6 * strength, speed/50 * strength) with strength = (percent - 1) / 149, then the result is rounded and clamped to i16. OnceLock means the first read wins until the process restarts. Official’s logged policy is the opposite shape: raw counts on the wire, and a host-side speed of 10 with accel 0, resent on focus changes. The Linux client may have just read a non-zero libinput speed from gsettings and still send accel 0 speed 10 on the SDL path. The desktop setting and the session setting are different messages.

docs/streamer-comparison/mouse-input.md says the proven OpenNOW activation chain sends enable-input, cursor capture 0x0308, cursor tracking 0x030d, and window state 19, and that the type 10 payload is absent. That part matches activation_chain in the current file. The chain is eight buffers: enable input false (0x020b, counter 1), a device descriptor, cursor capture on, track cursor on, window state 19 (0x0320), system state 0 (0x0321), enable input true, then haptics enable. features.md lists seven steps and says a reconstructed mouse-settings command used to sit between tracking and window state. The current chain has no mouse-settings step, and it appends haptics as the eighth buffer. Window state 19 remains load-bearing for the reason the features note gives: an all-zero window state leaves the session looking inactive and the server withholds system-cursor updates.

Cursor mode, lock, and NVB types 0 and 8

SDLCursorManager is the Linux cursor owner. The log lines are “Local cursor: %d. hasFocus: %d. fullscreen: %d, inputMode: %d, shouldLock: %d”, “updateCursor: Warping cursor to window point {%d, %d}”, “updateCursor: Update mouse control mode to %u”, “updateCursor: confining to window”, “captureCursor( %s ) succeeded” and the failure with SDLError, “Cannot find corresponding SDL cursor for the provided nvsc cursor id: %u”, “Receive new bitmap cursor, payload size: %u”, “Unable to decode bitmap cursor id %d”, and “Could not create a system cursor with SDL_SystemCursor %u”. “Hiding remote on NVB_SN_CURSOR_INFO_CHANGED” is the type 0 reaction: on a cursor-info change the client hides the remote cursor. “useConfinedHiddenCursorInsteadOfLocked %d for appId” is a per-app choice between confine and lock. The Windows note’s three modes (visible unlocked, visible warped, hidden locked) line up with these verbs: warp to a window point, confine, and shouldLock. The warp math in that note, coord / 65535 * windowSize, is the 16-bit normalized coordinate. The Linux string does not print the divisor. It prints the destination point.

OpenNOW’s inbound parser in nvst_input.rs reads COMMAND_SYSTEM_CURSOR 0x010f and COMMAND_BITMAP_CURSOR 0x0110 by walking command boundaries. A system cursor with type 0 and cursor id 0 is hidden relative. The features note’s examples are 0f 01 09 00 01 00 00 00 0c 80 16 80 01 for a visible id, and 0f 01 04 00 00 00 00 00 for the lock-style id 0. The parser must not scan inside unrelated payloads for cursor-looking bytes. Bitmap notifications need an eight-byte header before they affect composition. Composition is independent of visibility: a bitmap does not unhide a hidden cursor and does not change relative mode. Capture 0x0308 is sent on at activation and requested off after the first cursor notification, or after a three-second watchdog if the host publishes nothing. Tracking 0x030d stays on so notifications continue. Each of those commands is a one-byte payload, 00 or 01. Official’s type 0 and type 8 are the same product behavior. The features note is explicit that OpenNOW’s command codes match the session behavior and the comments, and that they are not proven byte-identical to Geronimo’s feature blob until a capture says so.

runtime.mimicRemoteCursor in Bifrost is the mimic-strategy flag. The features note says 0x0322 is cursor mimic strategy, and that an earlier mapping of haptics onto 0x0322 was wrong. OpenNOW’s ANNOUNCE sets mimic to 0. Haptics enable is remote-input type 13, not that command.

The mouse packets OpenNOW sends

captured_input_packet builds the native HID body. Type 7 relative is a little-endian type, then big-endian i16 dx and dy, six zero bytes, and a big-endian timestamp, 22 bytes. Type 5 absolute is x, y, a reserved u16, width, height, a reserved u32, and a timestamp, 26 bytes. Buttons are type 8 down and type 9 up, 18 bytes, button in the first body byte. Wheel is type 10, 22 bytes, with both delta_x and delta_y as big-endian i16. The mouse note’s table says the wheel’s horizontal component is always 0. The current builder writes the captured delta_x. A platform that never fills horizontal wheel still sends 0. The packet format itself has the field.

remote_input_message wraps that body in command 0x0206. It pads the body to at least 24 bytes and to a multiple of 8, then appends one little-endian microsecond timestamp. Keys and absolute mouse get a second timestamp. Relative mouse and absolute mouse are routed ControlPartial. Buttons, wheel, keys, and haptics are ControlReliable. The mouse note says motion uses unordered partially reliable SCTP with a 300 ms lifetime and that buttons and wheel use reliable control. The current route function agrees on buttons and on relative motion, and it also places absolute motion on the partial route. The 300 ms lifetime is the ANNOUNCE attribute x-nv-ri.partialReliableThresholdMs:300, which matches ri.partialReliableThresholdMs in Bifrost. x-nv-ri.usePartiallyReliableUdpChannel:0 leaves the UDP partial channel off. x-nv-ri.timestampsEnabled:1 matches ri.timestampsEnabled.

The Windows capture note still matters for feel even though this .so is Linux. Official Windows Raw Input splits an i32 lLastX that does not fit in i16 into several type 7 samples. OpenNOW does that too, on the Windows raw-input thread. Official’s host then interprets those counts with accel 0 and speed 10. OpenNOW can scale them first with tune_relative_mouse. A large HID burst therefore becomes several partial-reliability packets, and a stall on the NVST event thread batches them. The 300 ms lifetime exists so an ordered replay does not show up later as a catch-up flick. Foreground filtering drops events unless the SDL or Qt window is focused. Official’s async thread is also focus-scoped: the Windows log ends the thread on unfocus and resends mouse settings, and the send often fails. The Linux XWayland path confines with XGrabPointer instead. OpenNOW’s Windows crate has no ClipCursor and no RIDEV_NOLEGACY.

Queue capacity 256 and a drain of up to 32 samples per tick are the OpenNOW capture notes, not strings in Geronimo. Geronimo’s SDL event loop logs “SDLProcessEvent: pollTime: %ldus” and “procTime: %ldus”, which is the same kind of budget, without a published cap in the string table.

Gamepad capture, aggregation, and the four-slot limit

SDLGamepad is the device owner. It logs “Loaded %d gamepad mappings”, “Opened controller named %s with vendor id %x product id %x at index %d”, “Skipping SDL gamepad for device %04x:%04x at SDL index %d”, “Controller named %s is already opened”, “Closed a controller named %s”, “Could not find controller at index %d”, and “Max %d controllers are supported”. The embedded mapping database announces “# Game Controller DB for SDL in 2.0.10 format” and includes the usual VID/PID lines, among them Sony DualSense entries for Windows, Mac, and Linux. The Windows session note counted 858 mappings and an Xbox One controller at VID 045E PID 02FF. The Linux binary contains that same database text. “SDL: Failed to init game controller / haptic subsystem” is the startup failure. Hints SDL_JOYSTICK_HIDAPI_PS4_RUMBLE and SDL_JOYSTICK_HIDAPI_PS5_RUMBLE turn on HIDAPI rumble for those pads.

Above SDL, Gamepad aggregates. The methods are queueEvent, flushAggregatedEvents, scheduleAggregationTimer, updateAggregationTimer, eventLoopDidTurn, flushState, buildGamepadBitmap, getPlugState, and onConfigurationChanged. Settings hooks are GeronimoSettingsImpl::overrideGamepadAggregateInterval and overrideGamepadDestructiveAggregation, and the config key enablePartiallyReliableTransferGamepad. Destructive aggregation means a later sample replaces an earlier one inside the interval instead of sending both. The interval override is a duration in the settings object. OpenNOW does not have this timer. It sends on SDL ControllerAxisMotion and ControllerButton events, and it resends the last type 12 state every 100 ms so a quiet pad does not look unplugged. Official’s aggregate interval is the thing that can coalesce a stick sweep into fewer packets. OpenNOW’s keepalive is the thing that prevents the game from reverting to keyboard prompts. They solve different failures. A destructive aggregate that drops intermediate stick positions will feel like a lower poll rate. A missing keepalive will feel like the pad disconnected.

Four slots are hard. Geronimo logs “not supported: more than 4 gamepads connected” and getGamepadState fills std::array<NvstGamepadStateEvent_t, 4>. RIDeviceMediator assigns identity: getNextId, handleNewGamepad, getGamepadEffectiveIndex, getGamepadIndexFromXinputEffectiveIndex, getGamepadIndexFromHidId, getGamepadMechanism, shouldForwardGamepad_Locked, and reInitializeGamepads. The log line “%s: standard gamepad at effective ID: %d” is the Windows note’s “standard gamepad at effective ID: 0”. “%s: matched nvstId=%d at effective id=%u” and “%s: synthesizing nvstId=%d at effective id=%d” are the synth path. “Invalid gamepad mechanism (%d) for gamepad %d (effective %d)” is the failure. “Unhandled %s gamepad[%u], vid=%04x, pid=%04x” is an unrecognized device. Telemetry is “Sending gamepad telemetry for id %d, state: %d, eventMap: %s” with labels _L1, _R1, _TL, _TR, _LT, _RT, _DY, _DX, _ST, _SE, _LS, _RS.

OpenNOW’s native pad owner is SDL game controller as well, first-come slots 0–3, unmapped joysticks ignored. The bitmap always sets both the connected bit and the Xbox bit for every occupied slot. Guide, screenshot, recording toggle, and shortcuts produce an empty packet in captured_input_packet, so Guide stays local. SDL Misc1, touchpad, and paddles are dropped on the native path the controller note describes. enableGyroscopeControls is stored and unread. Official’s DualSense path is the opposite: gyro and touch are HID reports, not SDL axes, and they go through the synthesizer below.

HID synthesis, GSHID, and the Linux raw-USB gap

GamepadHIDSynthesizer parses and builds DualShock state: parseDS4Report, parseGamepadHidOutput, extractGamepadId, buildSynthesizedDS4State, and buildSynthesizedGamepadState. RIDeviceMediator gates it with serverSupportsDS4, supportSynthesizedDS4, allowSynthesizedDS4, allowSynthesizedDS5, allowCrossSynthDS5ToDS4, allowCrossSynthDS4ToDS5, allowCrossSynthGenericToDS4, allowCrossSynthGenericToDS5, and configureDualSenseController. Debug config can disable synth per direction: isSynthesizedDS4Disabled, isSynthDS4FromDS5Disabled, isSynthDS5FromDS4Disabled, isSynthDS4FromGenericEnabled, isSynthDS4AllGamesEnabled. The log “Configuring server supported Hid devices: Supports DS4: %s, DS5: %s (raw:%x)” is the server capability. “%sabling GSHID” is the client switch. “%s: DualSense controller is %shandled” records whether that pad is on the synth path. “Invalid device for synthesizing HID report: [%04x:%04x]” is the refusal. The Windows session note says DualShock synth was allowed and generic-to-DS synth was off, with synthesizeGamepadHid: true in remote config. Those are the same keys.

Bifrost still has a platform hole: “No implementation to handle USB gamepad raw input on this platform.” On Linux, raw USB gamepad input is not implemented inside the NVST mapper, so Geronimo’s SDL-plus-synthesizer path is how a DS4 becomes an NvstInputEvent. RiNvscGamepadMapper logs “Unrecognized axis control”, “Unrecognized trigger control”, “Unrecognized button control”, and “Unrecognized gamepad event” when a report does not map. “Gamepad ID %u is invalid” is the slot check. Partially reliable stats for the gamepad channel are “RI gamepad_channel_v1 stats: m_highestSequenceNumber, m_packetsLostCount, m_packetsDroppedCount” and a second line for devId and channelId. The config keys are ri.enablePartiallyReliableTransferGamepad, ri.enablePartiallyReliableTransferHid, and ri.usePartiallyReliableUdpChannel. OpenNOW’s ANNOUNCE sets gamepad partial reliability to 255, HID partial reliability to -1, and the UDP partial channel to 0. The value 255 is the all-slots mask the attribute expects. It does not mean “256 controllers”.

SDLGamepadRSDMM is a gesture layer on top of the pad. It parses NvstGamepadStateEvent_t, ticks a timer, detects a debug toggle gesture, and can sendMouseButtonEvent. IOInterface::setGamepadRsdmm and GridApp::setGamepadRsdmm enable it. enableRsdmmToggle sits in the same config blob as synthesizeGamepad. This is how a pad click becomes a mouse button without a type 7 packet from the physical mouse. OpenNOW has no RSDMM object. Stick-as-dpad thresholds in the Qt shell poller are a different feature, and that poller is gated off on the stream route.

The 38-byte type 12 packet, as built now

captured_input_packet for CapturedInput::Gamepad writes 38 bytes. Little-endian type 12, little-endian payload length 26, little-endian controller id masked with 0x03, little-endian bitmap, a constant 20, buttons, triggers packed as left in the low byte and right in the high byte, four little-endian stick axes, a zero u16, the constant 85, another zero u16, and a little-endian timestamp. Byte offset 6 is the controller id. The controller note’s layout matches this builder: type, payload 26, slot, bitmap, buttons, triggers, sticks, magic 85, timestamp.

gamepad_command wraps those 38 bytes rather than picking fields out. The payload starts with marker 0x23, an 8-byte big-endian timestamp, marker 0x26 plus packet[6] (the low byte of the controller id), a big-endian sequence, marker 0x21, a big-endian length 38, then the entire 38-byte packet. Command code is 0x020d. The controller note says the NVST body hardcodes inner index 0x03 and does not copy controller_id or the bitmap. That described an older encoder. The current wrapper copies packet[6] into the 0x26 field and then copies all 38 bytes, so the slot and the bitmap travel inside the packet even though the outer field repeats the low id byte. Multi-pad identity is on that wire to the extent the 38-byte layout carries it. x-nv-ri.useMultipleGamepads:1 is the ANNOUNCE flag, matching Bifrost’s ri.useMultipleGamepads.

The first gamepad still sends a device descriptor on reliable control. Updates go out as COMMAND_GAMEPAD. Partially reliable versus reliable for those updates follows the input route the encoder chooses for gamepad traffic. Motion-class mouse is the route documented as partial. Gamepad reliability is the 255 mask in ANNOUNCE plus the Bifrost channel stats, which count both lost and dropped packets on gamepad_channel_v1. A drop on that channel is why the 100 ms keepalive exists: a lossy partial send of a stick position must be repaired by a later full state, not by a retransmission of every intermediate aggregate.

Haptics: feature type 6, remote-input type 13, and Sony output

Geronimo logs “enable haptic state” and “disable haptic state” from SDLGamepad / Gamepad::updateHapticState. playHaptic takes a device and two integer arguments. isHapticEvent classifies an SDL event. The Windows note’s sequence is enable haptic state, then “Sending haptics state 1 to server”, then feature type 6, with telemetry hapticsSupported and hapticsFeedbackCount. Bifrost’s failure line is “Failed to %s feature gamepad haptics. Nvst Error: %s (0x%x)”. x-nv-runtime.hapticsState is the SDP key. Inbound HID output is NVbEventData_t::_HidOutputEvent, parsed by parseGamepadHidOutput. That is the server telling the client to rumble a synthesized DS4. The Linux mapper can still log that USB raw input has no implementation, so a rumble that depends on a raw USB write may stop at SDL playHaptic instead.

OpenNOW sends the enable flag. INPUT_HAPTICS_ENABLED is type 13. haptics_state packs a little-endian u16, 0 or 1, into the remote-input envelope on 0x0206, reliable, with the timestamp suffix. activation_chain sends enabled true after input is enabled. Disable uses body 00 00. features.md matches this to NVB type 6 and points at the Mac reference’s hapticsState framing. The test haptics_disable_uses_remote_input_envelope_and_preserves_timestamp locks the disable vector. Sending the enable flag is the feature-control equivalent. It is not the rumble sample itself.

Rumble samples are a second path in nvst_haptics.rs. NvstHaptics stores per-slot low and high frequency, including Sony rumble tagged with a slot and an incarnation, and coalesces pending commands. Sony HID reports have their own commands in nvst_input.rs. sony_device_change_command sends remote-input type 0x12 with a low id, an attach code 1 or a removal code 3, and SONY_DEVICE_CHANGE_FLAGS. sony_report_command sends command 0x020d with marker 0x22, type 0x11, the low id, the DS4 interface number, and a fixed-size DS4 report. parse_sony_output and for_each_sony_output walk inbound 0x0206 payloads for type 0x11 and deliver the output report to that low id. Low ids are checked against DS4_LOW_ID_BASE and MAX_SOURCES. This is the OpenNOW equivalent of Geronimo’s HID output event and DS4 synthesizer, scoped to the DS4 report size the hid crate defines. The controller note’s “OpenNOW has no GSHID synthesizer” and “never applies rumble” describe the older SDL-only type 12 path. The current transport can enable haptics, store Sony motor state, and exchange DS4-shaped HID reports. A generic Xbox pad still rides the 38-byte type 12 packet. SDL_JOYSTICK_HIDAPI_PS5_RUMBLE on the official side has a DualSense-specific synth (configureDualSenseController, cross-synth DS4/DS5) that this DS4 report path does not cover by itself.

Activation, keepalive, and the frames that are byte-checked

The activation order in the current activation_chain is the contract a session must see before gameplay input is accepted. Enable input false uses 0x020b with three little-endian u32 fields: stream index 0, counter 1, enabled 0. The device descriptor is 0x020d. Cursor capture on is 08 03 01 00 01. Track cursor on is 0d 03 01 00 01. Window state 19 is 0x0320 with state 13 00 00 00. System state 0 is 0x0321. Enable input true repeats 0x020b with enabled 1. Haptics true follows. Keepalive 0x0200 is a 4-byte stream value, sent on the control interval the transport uses (the features note says every 3 seconds for control_keepalive(0), which is 00 02 04 00 00 00 00 00). The input handshake is ready when reliable control delivers version 3: 0e 02 02 00 03 00, command 0x020e, length 2, version 3.

features.md prints a relative-mouse test vector under 0x0206 with inner type 7, dx 24, dy 24, and a timestamp, and a key-down vector for virtual key 0x41. Those vectors are the byte-exact checks. They are the right source for “what OpenNOW sends”. Geronimo’s logs are the right source for “what official says it sent”. The gap between them is type 10. Official’s Linux and Windows binaries both format accel and speed and then call nvbFeatureControl. OpenNOW’s activation chain does not send a mouse-settings command. Aim feel differs for that reason even when type 7 deltas are otherwise the same integers: the host still has whatever accel and speed it booted with, while official has just told it accel 0 and speed 10, and will tell it again on the next focus change. The Linux client may also have confined the pointer with XGrabPointer or fallen back to SDL if XInput2 failed, and it may have read a libinput speed that it then overrides with the session message. OpenNOW’s Windows raw-input thread can still multiply the delta by tune_relative_mouse before the host sees it.

Cursor lock differs in the same way. Official reacts to system cursor id 0 with shouldLock, a local cursor of 0, and a hide, and it warps other ids from normalized coordinates. It can choose confine instead of lock per app id. OpenNOW treats predefined type 0 id 0 as hidden relative, enters relative mode, and uses capture plus tracking commands whose payloads are known and whose equality to Geronimo’s feature blob is not captured. Bitmap cursors update composition only.

Gamepad feel differs in aggregation, identity, and HID. Official can destructively aggregate inside an override interval, synthesize a DS4 from another pad when the remote config allows it, assign an effective index distinct from the XInput index, and send haptics as feature type 6 with HID output coming back. OpenNOW sends a full 38-byte state that includes the slot, repeats that slot’s low byte in the 0x26 wrapper, keepalives every 100 ms, advertises four-pad partial reliability as 255, enables haptics with type 13, and can carry DS4 HID reports on the Sony commands. It does not run GSHID generic-to-DS4 synthesis, does not read enableGyroscopeControls, and does not implement RSDMM. A fifth pad is dropped on both clients. A quiet pad is not an idle wire on OpenNOW. On official, an aggregated empty interval is whatever flushAggregatedEvents decides, and the gamepad channel stats will show drops separately from losses.

The strings that should not be turned into a packet are the ones that only name a policy. accel=0, speed=10 is a format string. Update feature type: %d is a type number. nvbFeatureControl( <pointer> ) is an object. Failed to update mouse sensitivity: %d is the speed argument. Until a capture shows the feature blob, the honest implementation state is the one features.md already states for type 10: the log proves the meaning, and the current encoder does not send a guessed body.
