# libGeronimo video path and OpenNOW parity

The Linux GeForce NOW client split that this audit can actually see is `libGeronimo.so` at `audit/gfn-official/x86_64/master/235a800084abb2246e4578e5b60c33397fac73152c02a5751e663ddafd00e260/files/cef/libGeronimo.so`. The file is a 34,347,824-byte stripped ELF64 shared object, BuildID `15d0eebc08da503f1f37ea9cae2dbac1d760fea4`, with a populated `.dynsym`. Radare2 5.5.0 was used with `bin.cache=true`. Three functions were disassembled with `pdf` after `afu` pinned each function to the next symbol or the next `endbr64`, because an unbounded `af` followed C++ unwind landing pads and then refused `pdf` with “Linear size differs too much from the bbsum”. The three listings are `VulkanDecoder::decode(NvstVideoDecodeUnit_t const&, bool)` at `0x47a800` (1217 bytes), `AsyncFrameQueue::flush(bool)` at `0x3f7800` (341 bytes), and `FrameTiming::updateJitterAdvance(double, double)` at `0x3f6300`. Supporting listings of the same kind cover `BifrostSDKExecutor::setDynamicStreamingMode`, `BifrostSDKExecutor::setCurrentDJBConfig`, and `BifrostSDKExecutor::updateVideoDecoderState`.

OpenNOW uses the in-process NVST transport in `opennow-streamer-transport/src/nvst.rs` and negotiation in `opennow-streamer-core/src/nvst_rtsp.rs`. Its supported Linux desktop presentation path is the embedded media runtime, opaque GPU-frame publication, and Qt scene-graph composition. The FFI creates `Engine::with_embedded_media_runtime_and_hid`; `opennow-streamer-platform/src/runtime.rs` calls `MediaSession::spawn_embedded`, `media.rs` takes the newest decoded frame, and `graphics.rs` publishes it in the latest-frame slot. Qt acquires and records that frame through `NativeStreamRuntime` and the native render callback. `output.rs`, `VulkanPresenter`, and `LinuxFramePacer` describe a separate standalone presenter, not this Qt path. The comparison commit is fixed in the [overview](README.md). Windows log evidence in `docs/streamer-comparison/video.md` remains a different platform and vendor build.

## Where the video path actually stops

Geronimo is the decode, pacing, and feature-control shell. The RTP socket, SRTP unprotect, packet reorder, generic NACK, and FEC repair are not in this image. The imports that carry video policy out of the process are Bifrost entry points: `nvbFeatureControl`, `nvbUpdateDJBState`, `nvbUpdateVideoDecoderState`, `nvbSendClientInfo`, `nvbSendStreamStats`, and `nvbEnumToString`. Every successful policy call in the executor follows the same shape. A byte at `this+8` must be set or the call is refused locally. The executor then passes the Bifrost context at `this+0x10`, a session object at `this+0x70`, the stream id, and a feature blob whose first dword is a type code. A zero status dword comes back on success. A nonzero status is turned into a string with `nvbEnumToString` and logged at level 5 under the tag `BifrostSDKExecutor`.

That split matters for parity. OpenNOW’s `NvstVideoReceiver` is both the Mjolnir socket and the depacketizer. Geronimo never sees an RTP packet. It sees an `NvstVideoDecodeUnit_t`, a DJB config struct, and feature-control results. Matching OpenNOW to this binary means matching what Geronimo does after a decode unit exists, and matching the Bifrost calls Geronimo makes when the queue or the quality policy changes. It does not mean finding a second copy of the 1024-packet reorder window inside Geronimo. That window is already mirrored in `nvst.rs` from the official client’s documented envelope, and this `.so` neither confirms nor contradicts the packet layout.

The string extract is a trap on this point. `nacked`, `nacked_but_cached`, and `, will NACK: nonce=` sit in gRPC xDS client text (`received response`, `nonce=`, `num_resources=`, `does_not_exist_but_cached`). They are resource-state names for an ADS watch, not video RTCP. The many `Mjolnir_Vcpkg_mjolnir-vcpkg` paths are Jenkins build strings from the vcpkg tree that produced gRPC, protobuf, and OpenTelemetry. They are not the video UDP port. A string search that treats those hits as the video NACK machine will invent a recovery path this library does not implement.

## Decode

`VulkanDecoder::decode` is the hardware picture path on this build. The object keeps the decode-unit source at `this+0x88`, a frame pool at `this+0x1e0`, an allocator context at `this+0x1e8`, and two device-side shared pointers at `this+0x1d0` and `this+0x1d8`. The incoming unit is `rsi`. The second integer argument, the `bool`, is saved and later inverted. The first virtual call is slot `+0xc8` on the object at `this+0x88`. The stream id is the 16-bit field at unit offset `0x40`. A second dword is taken from unit offset `0x8`. The callee receives a pointer to a stack dword that the decoder sets to `13` before the call, with an extra zero pushed as the last argument. That call happens before any picture is allocated. It is a “work started” report, not a present.

The decoder then calls `VulkanDecoder::allocFrame`. A null return logs `Failed to allocate frame` against `VulkanDecoder.cpp` at level 5 and returns a null renderer. On success it calls an internal get-next function (`0x4bdaa0`) with the new frame and a byte out-parameter. If that function returns a count greater than 1, the decoder logs `%d frames returned from GetNextFrame!` and drains. Each extra picture drops two `shared_ptr` slots at frame `+0x10` and `+0x18` (the Itanium deleter is virtual `+0x20` when the use count hits zero, unless the vtable identity mismatches a sentinel at `0x405690`, in which case it calls the raw destructor). It then zeroes the frame header: qword at `+0` becomes `0xffffffffffffffff`, qword at `+8` becomes 0, byte `+0x68` is masked with `0xf8`, and the block from `+0x20` through `+0x6c` is cleared. The same get-next call is repeated until the count is no longer greater than 1. A Vulkan decode that surfaces a burst does not present the burst. It releases the extras and continues with a single frame. That is the opposite of a queue that accumulates decoder output for the presenter to catch up.

After the drain, a set out-parameter byte, or a negative count, is `Stream/Decode Error!` at level 5. The same virtual slot `+0xc8` is invoked again with the stack dword set to `4`. If the count is zero, level 4 logs `No Frame`. In every failure case `VulkanDecoder::freeFrame` runs and the function returns null. The bool argument selects whether a successful picture becomes a renderer. The decoder computes `(count > 0) AND (bool XOR 1)`. When the bool is true, a decoded frame is freed and not wrapped. That matches a drain-or-skip entry point on the same function, not a second decode implementation.

The success path reads a description object from `0x4b8fa0` and writes a picture descriptor into the frame:

- Bit 3 of the byte at description `+0x48` is stored at frame `+0xb4`. One flag bit survives; the rest of that byte is discarded.
- The byte at description `+0x19`, plus 8, is packed with the dword at description `+0xc` and stored at frame `+0x10c`.
- The byte at description `+0x49` selects a pair of identical dwords at frame `+0xb0` and `+0x100`. The value `1` maps to `2`, the value `9` maps to `4`, and every other value maps to `1`. Those are the only three chroma-or-format codes this function can emit.
- The byte at description `+0x4a` is compared with `0x10`. Equality stores `2` at frame `+0x104`; any other value stores `1`. A 16-valued bit-depth field therefore takes the second code, which is the 10-bit container case (P010-style 16-bit storage), and every other depth stays on the first code.

The renderer is a 0x120-byte heap object. `FrameRenderer::FrameRenderer(NvstVideoDecodeUnit_t const&, unsigned int, unsigned int)` runs first, then the vptr is replaced with `vtable for VulkanRenderer` plus `0x10`, which is the Itanium adjustment from the vtable symbol (offset-to-top and typeinfo) to the first virtual function. The decoded frame pointer is stored at renderer `+0x108`. The two device shared pointers are copied to `+0x110` and `+0x118`, with an atomic increment when libpthread is linked. Width and height used for the constructor come from frame `+0x90` and from `+0x94` divided by the double at frame `+0xa8`. That double is initialized from the rodata constant `1.0` (`0x3ff0000000000000` at `0x18a8f08`) immediately before the division, so the height passed into the renderer is the integer truncation of `height / 1.0` unless an earlier write changed `+0xa8`. The function returns the renderer pointer. Presentation is not performed here.

Sibling decoders exist and were not the ones listed with `pdf`, but their symbols fix the backend set. `LAVCDecoder::decode` is 1055 bytes at `0x5220a0` and is constructed either with a `VulkanDeviceContext` or with a thread count. Log strings record `LAVCDecoder: using max %d threads for decoding`, YUV converter failures, and `avcodec` open/find failures. `VDPAUDecoder::decode` and `parseBuffer` sit at `0x42d500` and `0x42d4f0`, with capability queries for 10-bit, 4:4:4, and 4:2:2. `platformCreateVideoDecoder` and `platformCheckVideoDecoderRgbaSupport` choose among these at startup. The Linux official client can therefore decode with Vulkan video, with FFmpeg through LAVC, or with VDPAU. OpenNOW does not carry a VDPAU backend. Its embedded Linux selector in `linux_backend.rs` supports negotiated, capability-constrained Vulkan Video, CUDA, VA-API, V4L2, and explicitly selected FFmpeg software paths. Software presentation is restricted to 8-bit 4:2:0 SDR; none of these choices adds a standalone presenter to Qt. The Windows note in `video.md` (D3D11 decode device, separate present device, `ulNumDecodeSurfaces = 10`) is a different binary. This `.so` does contain the split in a weaker form: `VulkanDecoder` owns the decode frame, and `VulkanRenderer` is a distinct object handed to `AsyncFrameQueue`. Decode and present are different types even when they share a Vulkan device.

Format changes are not handled inside `decode`. They are handled by the unexported `VideoDecoder` routine at `0x3dfe50` (2986 bytes, from `endbr64` to the next `endbr64` at `0x3e0a51`). That function logs and stores:

- `Stream bit depth changed to: %u` when the new depth differs from the byte at `this+0x180`.
- `Stream chroma format changed to: %u` when the new chroma differs from the dword at `this+0x184`.
- `Stream colorspace changed to: %u hdr: %d range: %s` when colorspace, HDR, or range differ from the cached dword at `this+0x188` and the word at `this+0x18c`.
- `Stream resolution changed to: %ux%u` only after the same width and height have been observed five times (`cmp eax, 5` on a counter at a stack slot that is incremented while the size is unchanged). A one-frame glitch in the SPS does not announce a resolution change. Bit depth, chroma, and colorspace update on the first differing sample.

Colorspace values `2` and `4` take separate branches before a virtual call at slot `+0x198` on the object at `this+0x78`. The other colorspace values fall through with the HDR byte zero-extended as an extra argument. The official session described in `video.md` (10-bit, chroma 3, colorspace 2, limited range, HDR off) is exactly the tuple this logger is built to print. OpenNOW’s Linux session adopts a decoder format change immediately and emits `BackendEvent::FormatChanged`, then `LinuxFrameProducer::ensure_slot` reallocates the output image. It does not debounce resolution across five frames, and it does not keep a separate colorspace/HDR/range cache that is compared field by field before the presenter is told. The practical difference shows up on a dynamic-resolution stream: Geronimo will keep the previous announced size until the new size has been stable for five samples, while still updating chroma and depth immediately. OpenNOW resizes the Vulkan image on the first accepted format change.

Two parser strings, `Invalid SPS change at non-IDR` and `Invalid PPS change at non-IDR`, are present twice (the decoder and a second copy of the same parser). A mid-stream parameter-set change that is not an IDR is rejected rather than applied. OpenNOW’s keyframe rule is the access-unit classifier in `nvst.rs` (H.264 NAL type 5, HEVC IRAP 16–21, AV1 SOF header byte 2). It will still submit a non-IDR access unit that happens to carry a new SPS unless the assembler has already declared the frame non-contiguous and dropped inter frames until a keyframe. Geronimo’s parser makes that rejection itself, inside the decode library, even when the transport delivered a complete access unit.

`VideoDecoder::getNextFrame(bool, unsigned int)` is the exported consumer at `0x3d6840`, about 5808 bytes, and `VideoDecoderSet` multiplexes streams above it. The set also has `setWaitTimeoutMs`, `updateDecoderSize`, and `requestProcessedFrame`. HUD video is a separate `HudVideoDecoderSet`. OpenNOW has a single video queue in `output.rs` and no second decoder set for HUD. Overlay video, if the server sends it, has nowhere to go except the same frame queue.

## Presentation

`VulkanDecoder::decode` returns a `VulkanRenderer`. The queue that owns presentation timing is `AsyncFrameQueue`. `flush(bool)` is the recovery-side view of that queue, and it also shows the state the presenter keeps. The function takes the mutex at `this+0x30` when `pthread_key_create` resolved, calls an internal drain at `0x1db150` with the bool widened to 0 or 1, then logs `Total video frames dropped : %u` from the counter at `this+0x1c8` at level 3 under the tag `AsyncFrameQueue`. It then zeroes that counter and a qword at `this+0x1c0`. An xmm constant from `0x19055b0` (a 1-ulp denormal in the low double and zero in the high double) is written to `this+0x220`, and a zero xmm is written to `this+0x230`. The dword at `this+0x200` becomes `0xffffffff`. Qwords at `this+0x208` and `this+0x210` become zero. The byte at `this+0x21a` becomes zero. The qword at `this+0x250` becomes zero. The abs-mask constant at `0x18ae370` (`0x7fffffffffffffff` in the low qword, zero in the high) is stored at `this+0x240`. Two further subobjects, at `this+0x290` and `this+0x2c0`, are reset through `0x1d72e0`. `std::condition_variable::notify_one` runs on the condition variable at `this+0x58`. If the byte at `this+0x1b8` is nonzero, a second condition variable at `this+0x88` is notified as well. If the pointer at offset 0 is non-null, `flush` calls it with the same bool. The mutex is unlocked on the way out. A failed `pthread_mutex_lock` throws `std::__throw_system_error`.

The inspected vendor queue contains a drop counter, a pacing block of about 0x90 bytes at `this+0x1c0`, two condition variables, and an optional child queue. Its flush resets presentation state without destroying the decoder or sending an IDR. That does not specify the policy of OpenNOW’s encoded queue or Qt render thread. OpenNOW’s embedded decoder publishes into the replaceable GPU-frame slot in `graphics.rs`; stale epochs are rejected and replaced frames are released through that ownership. A comparison with the standalone `output.rs` queue must not be used to prescribe a second queue or presenter for Qt.

`FrameTiming::updateJitterAdvance(double, double)` is the phase nudge applied once the queue has seen enough frames. The counter at `this+0x100` is converted to a double, with the usual unsigned fixup when the high bit is set (shift, convert, add the value to itself). If that double is below `100.0` (`0x4059000000000000` at `0x18a5d48`), the function returns without touching the estimate. The first hundred samples are a warmup. After warmup, the first double argument is clamped to the closed interval from `-0.075` to `+0.075` (`0xbfb3333333333333` and `0x3fb3333333333333`). The second double argument arrives in `xmm1` and is overwritten by the counter conversion, so this build does not consume it. The clamped value is passed to an updater at `this+0xc8` (`call 0x1d7800`). If the pointer at `this+0xf8` is non-null, the clamped value is passed through `andpd` with the mask at `0x18ae370`, which clears the sign bit, and control jumps to `0x3f6190`. The callback therefore observes the absolute advance, not the signed one. The signed value is what the estimator at `+0xc8` sees. The argument is a time error in seconds, as the caller trace below establishes.

`FrameTiming::nextPresentationTimestamp` converts its steady-clock nanosecond argument to seconds by dividing by the `1e9` double at `0x18a8fa8`, at instruction `0x3f6872`. It subtracts seconds-domain timestamps before calling `updateJitterAdvance` at `0x3f69c1–0x3f69d3`, adds `jitterAdvance()` to a seconds-domain timestamp at `0x3f6a30`, and multiplies by `1e9` at `0x3f6a9f` before returning nanoseconds. The updater’s ±0.075 bound is therefore ±75 ms, not 7.5 percent of a frame. The getter also calls `boundedJitterEstimate` and has warmup behavior, so the updater bound alone is not a specification of every presentation adjustment. The standalone `LinuxFramePacer` has a different local control law and a frame-count cap of two; its policy is not the production Qt presentation policy.

Vendor swapchain behavior is visible as a log, not a fully traced function. `Skipping swapchain recreation - only vsync changed and present mode is in cached compatible list` is referenced near `0x51837e`; `Unable to resize vulkan swapchain to: %dx%d` identifies an extent-change failure. OpenNOW’s Qt window, graphics context, and scene graph own the supported application’s surface lifecycle. The standalone `VulkanPresenter::reconfigure` and its device-matching logic are not evidence of Qt’s vsync or resize behavior. The Windows flip-discard behavior in the earlier log comparison is also a separate platform path.

The standalone `output.rs` pump orders captured input before a potentially blocking presentation call. The supported Qt path instead has explicit Qt-side input owners and native media workers, with the GPU render callback recording into the existing scene graph. Geronimo’s condition variables and `VideoDecoderThread` symbols likewise indicate separate responsibilities, but these static observations do not prove either client’s input latency under a stalled compositor.

## Recovery

The exported recovery entry point does not recover anything. `IOInterface::flushAndRecoverVideoStream(unsigned short, bool)` at `0x351da0` is `endbr64; ret`. `IOInterface::handleDJBConfigRequest` at `0x351e20` is the same two instructions. `IOInterface::flushAllVideoStreams` is the neighboring symbol at `0x351d80`. Whatever those methods used to do, this build’s exported definitions are empty. Callers that go through the exported IOInterface symbols get a success return and no flush. The flush that actually runs is `AsyncFrameQueue::flush`, reached from the decoder and the renderer, not from that stub.

Decoder health is reported through `BifrostSDKExecutor::updateVideoDecoderState` at `0x354680`, with the `this+8` gate and a call to `nvbUpdateVideoDecoderState(context, session, streamId, frameId, state)`. Failure logs `UpdateVideoDecoderState failed. state: %d. Error %s (%d)`. This is distinct from the local virtual-call codes 13, 2, and 4 in `VulkanDecoder::decode`. The call proves a Bifrost reporting API, not the server’s interpretation or a causal IDR/invalidation ladder. OpenNOW has control IDR requests and a cooldown; it additionally sends RTCP PLI only on the bundle-video feedback route, not the dedicated Mjolnir route. The earlier Windows logs show IDR and invalidation messages, but a Bifrost call-path trace or paired wire capture is needed to link them to a particular decoder-state report.

The recovery ladder in `video.md` still describes the official client as a whole, and this binary confirms the client-side half of the lower rungs while leaving the upper rungs outside the library:

1. Packet NACK and FEC stay in Bifrost. Geronimo never formats them.
2. A presentation stall becomes `AsyncFrameQueue::flush`: log the drop total, zero the pacing block, notify waiters, flush the child queue. The decoder object survives.
3. Decoder state, including the codes `decode` already reported locally, is forwarded with `nvbUpdateVideoDecoderState` when the executor path is used.
4. The earlier Windows session log contains IDR and reference-invalidation messages. Their relationship to these decoder-state reports is a hypothesis until Bifrost’s state-to-command path or a paired wire exchange is traced. Geronimo’s parser strings prove local rejection of particular SPS/PPS changes, not that server-command sequence.
5. There is no device-lost path in the functions that were listed. `video.md` already notes that the sampled official session had no device-lost log. This library’s Vulkan decoder returns null and frees the frame on `Stream/Decode Error!`. It does not rebuild a device inside `decode`.

OpenNOW’s ladder is shorter and more local. A gap inside the NACK window is retried. An unrecoverable gap resets the assembler, sets `contiguous=false`, and requests a keyframe. Inter frames are dropped until that keyframe, and the keyframe rebuilds the transform. Encoded overflow clears the reference chain. A decoder error rebuilds the transform on the same device, then recreates graphics plus decoder for up to five seconds, then becomes fatal. There is no invalidation range, no “freeze the display on a bad reference” request, and no `flush` that preserves the decoder while wiping only the present queue. The closest OpenNOW operation to `AsyncFrameQueue::flush` is `clear_linux_video` on pause or hide, which drops queued frames without telling the server and without zeroing a pacing estimator beyond `LinuxFramePacer::reset` on stop and on a pacing-mode change.

The earlier Windows Media Foundation comparison describes decoder reset after damaged references. A vendor present-queue flush is not itself a valid reference frame. OpenNOW’s recovery must still respect decoder-specific reference health and obtain a usable keyframe when required. Its dedicated-video control IDR and optional bundle-video PLI are route-specific requests. No reference-invalidation encoder is established by the current OpenNOW comparison, and this audit does not recover its vendor wire format.

## Mjolnir

Mjolnir, in the sense that matters for video, is the dedicated UDP socket that carries video SRTP, separate from the ICE bundle. `video.md` records that both clients prefer local port 49005 and that ANNOUNCE sets `rtcVideoOnNativeBundle:0`. OpenNOW implements that socket inside `NvstVideoReceiver`. SRTP key derivation uses labels `0x00` and `0x02` for RTP video, and `0x03` and `0x05` for SRTCP, matching the libsrtp split. The GameStream header is 16 bytes. FEC coordinates live in that header. The reorder window defaults to 1024 packets and is capped at 2048. The Mjolnir dequeue timeout while a gap is open is 52 ms. The SRTP replay window is the full 2048-packet cap so that a retransmission is not rejected as a replay. The UDP receive buffer is 8 MB. Access units are capped at 2 MB by default and 16 MB absolute.

None of those constants appear as immediates in the three Geronimo functions that were listed, and the Mjolnir strings in the extract are build paths. The video bytes enter Geronimo only as `NvstVideoDecodeUnit_t`. The unit fields this decode function actually reads are the dword at `+0x8` and the 16-bit stream id at `+0x40`. Everything else about the unit is consumed by `FrameRenderer`’s constructor and by the description object returned from `0x4b8fa0`. Parity work on the header layout, the FEC word (`percent` in bits 4–11, index in bits 12–21, source-packet count in bits 22–31), and the SOF/EOF flags belongs in `nvst.rs`, which already parses them, and in Bifrost, which this audit did not open. Changing Geronimo is not available, and copying a Mjolnir receiver into the Qt client beside `NvstVideoReceiver` would duplicate the socket OpenNOW already owns.

The practical parity gap on Mjolnir is not the socket. It is the set of client-to-server messages that ride beside it. Geronimo’s executor can send dynamic-streaming mode, L4S state, max bitrate, G-Sync or VRR info, a region-of-interest debug marker, DJB state, and decoder state, all as Bifrost calls, at any time after `this+8` says a session exists. OpenNOW sends the corresponding video policy once, in the RTSP ANNOUNCE (`x-nv-vqos[0].dynamicStreamingMode`, `dfc.adjustResAndFps`, bitrate, FEC percentage, packet size), and then sends per-frame feedback (ack, pacing, NACK, IDR) from `nvst_control.rs`. A mid-session bitrate change is rejected. `WindowsBackend::reconfigure_video` has no in-tree caller. Live size changes arrive only as a decoder format change. Geronimo can push a new max bitrate with feature type `0x10` and log `Successfully updated max bitrate to %d kpbs` without a new ANNOUNCE. OpenNOW cannot.

## NACK

Because the video NACK machine is not in this `.so`, the parity statement has to be made against the official client’s observed envelope, which `nvst.rs` already encodes, and against what Geronimo does when NACK fails to fill a gap.

OpenNOW’s constants, from `nvst.rs`, are the envelope `video.md` attributes to the official session: retry spacing 4 ms (`NACK_RETRY_INTERVAL`), default RTT 30 ms, tracking timeout 52 ms (`NACK_TRACKING_TIMEOUT` and `MJOLNIR_REORDER_DEQUEUE_TIMEOUT`), three attempts (`MAX_NACK_ATTEMPTS`), reorder depth 1024, and a NACK queue bound discussed as 2048 entries. A Mjolnir session sends `nack_v2` on the partial control channel and preserves wrapping RTP sequence numbers. A non-Mjolnir session keeps RTCP generic NACK on the `rtcp` SCTP channel. A closed NACK channel does not spend an attempt and does not fall back to the other transport. Failed sends keep the shared budget. The FCI packer emits at most 64 packets per report, 17 sequence numbers per entry. Retransmissions that arrive before the NACK is sent still clear the range, and they are counted as recovered. After the tracking timeout the range is dropped and the assembler treats the gap as unrecoverable, which raises the keyframe request.

FEC sits in front of that. Repair packets are recognized when the percentage field is nonzero and the shard index is at least the source-packet count. Up to 128 FEC blocks can be held so that a later block does not discard an earlier incomplete one. The official session in `video.md` recovered 0 FEC packets and used 639 of 677 NACKed packets, with dynamic FEC enabled. OpenNOW advertises FEC in the 20–35 percent range at ANNOUNCE and will repair when the header describes a consistent block. A conflicting FEC layout invalidates only the discarded picture data, which is the behavior covered by `nvst_recovery_tests.rs`. Geronimo never sees this. By the time `VulkanDecoder::decode` runs, either the access unit was completed by Bifrost, or it was not delivered.

Geronimo exposes a present-queue flush and a decoder-state report, while the earlier Windows log names IDR and reference invalidation. Those observations do not establish a mandatory sequence after every failed NACK. OpenNOW’s Mjolnir recovery uses control IDR; bundle video may also use PLI. Reference invalidation is a candidate protocol gap, not a byte-defined implementation task. Recover the Bifrost wire format and state transition before considering an encoder in `nvst_control.rs`; neither can be inferred from `AsyncFrameQueue::flush`, which changes local state.

The xDS “will NACK” string must stay out of that work. Wiring a video recovery path to a gRPC nonce would send the wrong message on the wrong socket.

## DJB

DJB is the server-assisted jitter buffer. The receive path and the send path are both in the unexported `VideoDecoder` function at `0x3dfe50`, and the wire send is `BifrostSDKExecutor::setCurrentDJBConfig` at `0x354730`.

On receive, the function logs `Received DJB Config request at frame %u. Force: %d, minDepthUs: %u` at level 2 under the tag `VideoDecoder`. It stores the request: a dword at `this+0x2cc`, a byte/dword image at `this+0x2c8`, and a 16-byte image at `this+0x2b8`. If the force byte is nonzero, the min-depth dword and the following dword are each multiplied by `0x3e8` (1000) and passed to two setters (`0x1d9d00` and `0x1d6d70`). `FrameTiming::overrideMinQueueTime` and `overrideMaxQueueTime` take `chrono::nanoseconds`. Multiplying a microsecond field by 1000 produces nanoseconds, which matches those signatures and matches the log’s `minDepthUs` name. A force value of zero skips the override. The server can therefore push a config that is recorded but not applied until a later force, or push one that immediately replaces the queue bounds.

On send, the function compares a freshly computed status dword with the cached dword at `this+0x2d4`. An unchanged status does not generate a config. A change packs a mode dword and a reason dword into the qword at `this+0x2d0` and logs `Sending DJB Config at frame %u. Mode: %s, reason: %s, minDepthUs: %u, maxDepthUs: %u`. The reason code selects the reason string: `3` stays on `FIXED`, `1` selects `VVSYNC`, and any other value selects `UNKNOWN`. The mode code selects the mode string: `1` stays on `QOS`, `2` selects `MODE`, and any other value selects `UNKNOWN`. The non-force path hardcodes mode `2` (`MODE`) before that compare. The force path sets mode from the saved byte at `this+0x2c8`: if that byte is below 1, mode becomes `2` (`MODE`); otherwise mode stays `1` (`QOS`). If the reason code is not `2`, the qword at `this+0x2d8` (the depth pair) is cleared before the send. The actual call is virtual slot `+0x168` on the object at `this+0x78`, with the stream id taken from offset `0x90` of the object at `this+0x70`, the frame number, and a pointer to the packed config at `this+0x2d0`.

`setCurrentDJBConfig` forwards that pointer to `nvbUpdateDJBState`. If `this+8` is clear the function returns zero and does not call Bifrost. A nonzero status logs `setCurrentDJBConfig failed. Error %s (%d)` at level 5. There is no local retry. The empty `IOInterface::handleDJBConfigRequest` means an inbound request that arrives through that exported method is ignored; the live inbound path is the decoder function above, which reads the request from the stream object rather than from the stub.

OpenNOW does not implement this vendor DJB reporting/configuration API. Its standalone `LinuxFramePacer` is useful comparison material, but not the Qt presentation owner. That standalone policy is:

- VRR (`cloud_gsync` on the stream, and the negotiated flag) presents the latest frame on every pump, with no deadline and no target depth.
- A fast stream, or a deadline missed by more than 75 ms, also takes the latest frame and rebases the presentation clock in `mark_presented` so missed deadlines are not replayed.
- Otherwise the pacer waits until `next_deadline` and keeps the oldest frame, leaving `adaptive_queue_depth()` frames queued. That depth is at most 2.

The inspected forced-DJB path converts microsecond limits to nanoseconds and applies them to `FrameTiming`; a non-force request skips those overrides. Local adaptation also exists in the payload’s strings, including `Updating adaptive queue depth %zu => %zu for jitter %ldus` and `The target queue depth is sized based on observed frame arrival jitter multiplied by jitter factor.` The evidence therefore supports server overrides and reporting alongside local policy, not universally server-derived depth. It does not establish which mode a live seat uses or a measured presentation-quality ranking. Any Qt-path parity proposal needs the wire representation, bounded depth and deadline behavior, and device/surface-recreation acceptance. Do not turn an arbitrary server depth into an unbounded local queue.

`FrameTiming` exports `nextPresentationTimestamp`, `boundedJitterEstimate`, `arrivalJitterBoundEstimate`, `targetQueueTime`, `vrrFrameDuration`, and `jitterAdvance`. These names and the traced updater identify parts of the controller, but do not define all relationships between them. The standalone OpenNOW `jitter_bound_ns` controls a limited local queue; it cannot be treated as the supported Qt path’s equivalent of the vendor getter without tracing both active paths.

## Dynamic streaming

Dynamic streaming is feature type `0x0F`, and the failure string groups it with resolution and frame-rate control: `Fail to update feature DRC/DFC`. `BifrostSDKExecutor::setDynamicStreamingMode(unsigned short, NvstDynamicStreamingMode_t)` at `0x353e00` builds a 16-byte blob. The first dword is `0x0F`. The stream id is stored as a word. The mode dword is the `NvstDynamicStreamingMode_t` argument. `nvbFeatureControl` is called with the Bifrost context and the session pointer. Success stores the mode at `this+0x30` and logs `Successfully set dynamic streaming mode to %d` at level 3. Failure logs `GERONIMO_ERROR 0x%08X %s: %s` with code `0xC001000F` and the tag `GERONIMO_GRIDAPP_CONTROL_FEATURES`, then `nvbFeatureControl failed for type: %d. Error %s (%d)` with type `15`. The return value is the session-ready byte, cleared to zero on the failure path. `IOInterface::setDynamicStreamingMode` does not contain this logic. It loads the pointer at `this+0x68` and tail-calls virtual slot `+0x88`. `GridApp::setDynamicStreamingMode` is 48 bytes at `0x3423c0`, another forwarder. The executor is the only place the mode becomes a Bifrost feature write.

The same listing shows the neighboring feature writes, which share the prologue and the log helper and are easy to confuse with the mode function if `pdf` is allowed to run past its `ret`:

- `setL4sState` uses feature type `0x13` and logs `Successfully %s L4S feature` with `enabled` or `disabled`. Failure text is `Fail to update feature L4S`.
- `setStreamingMaxBitrate` uses feature type `0x10` and logs `Successfully updated max bitrate to %d kpbs`. The stored value is kept at `this+0x38`.
- `sendGsyncInfoToServer` uses `nvbSendClientInfo` twice, type `2` then type `3`, and logs `Failed to send VRR info!` if the first call fails. It still attempts the second call after that log.
- A later helper sends a client region-of-interest marker through `nvbSendStreamStats` with an outer type byte of `3` and an inner code `0x11a`, and logs `%s client region of interest debugging marker` with either `Sent` or `Failed to send`. If `this+0x18` is null it logs `No active session` at level 5 and returns zero.

`startStreaming` logs the mode in the same line as the rest of the request: `Requested Resolution: %dx%d@%d, codec: %s, SDR colorSpace: %d, HDR colorSpace: %d, bitDepth: %d, chromaFormat: %d, HDR: %d, bitrate: %d, dynamicStreamingMode: %d`. A second line records the converted request, including `drcDfc` and `framePacingMode`. The mode is therefore both an ANNOUNCE-time parameter and a live feature-control value. `video.md` already records the schema: `0` off, `1` prefer FPS, `2` prefer resolution, `3` on. The official client does not put that field in CloudMatch `requestedStreamingFeatures`. It travels as `x-nv-vqos`. The sampled `sharedstorage.json` profile had `dynamicStreamingMode: 0`.

OpenNOW matches the ANNOUNCE half. `negotiated_dynamic_streaming_mode` in `nvst_rtsp.rs` takes a server-finalized value from `negotiatedStreamProfile.dynamicStreamingMode` when it is in `0..=3`. Otherwise it sends `1` when `saveBandwidth` is true and `0` when it is false. `negotiated_adjustment_enabled` sets `dfc.adjustResAndFps` to `1` exactly when the mode is nonzero. The comment in that function states the same CloudMatch omission the official client uses. A mid-session toggle of `saveBandwidth` does not rewrite the running ANNOUNCE, which `video.md` also states. What OpenNOW does not do is the live `nvbFeatureControl` of type `0x0F`. The official client can change the mode after the stream has started, store it at `executor+0x30`, and have the server apply DRC/DFC without a new RTSP session. OpenNOW’s next opportunity to change the mode is the next ANNOUNCE. Locally, a format change still resizes the Vulkan image, so a server that changes resolution on its own will be displayed. A server that is waiting for a feature-control update before it changes resolution will keep the original size for the whole session.

The same gap applies to max bitrate (type `0x10`) and L4S (type `0x13`). OpenNOW’s ANNOUNCE carries a bitrate ceiling. A missing `maxBitrateMbps` becomes 75 Mbps on the wire (`unwrap_or(75)` in `build_announce`). `MediaStreamConfig::default().bitrate_bps` is `75_000_000`, and the streamer builds `bitrate_bps` from that same settings value. `docs/streamer-comparison/video.md` still says the local decode config defaults to 10 Mbps; that split is not in the current tree. Geronimo’s live bitrate update is a separate channel, in kilobits per second, logged explicitly, and stored on the executor. A parity implementation would send feature type `0x10` when the user changes the ceiling mid-session, rather than rejecting the IPC `bitrate` message.

`drc` and `dfc` are distinct controls. The vendor failure string groups feature `0x0F` as DRC/DFC, while the startup log prints `drcDfc`, `dynamicStreamingMode`, and `framePacingMode` separately. OpenNOW’s fallback ANNOUNCE builder includes `drc.enable:0`, `resControl.bitrateIirFilterFactor:128`, and `dfc.adjustResAndFps` alongside its negotiated mode. `negotiate_stream` removes server-owned attributes already supplied by DESCRIBE before sending ANNOUNCE. Builder defaults are therefore not a promise that every session emits them. A live feature-control update remains separate from session-start negotiation and is not a reason to add an unverified CloudMatch field.

## What parity requires, and what it does not

The Linux official video path in this build is a pipeline with a hard boundary. Bifrost delivers decode units and accepts feature, DJB, and decoder-state calls. Geronimo decodes on Vulkan, LAVC, or VDPAU, wraps one picture in a `VulkanRenderer`, and presents through `AsyncFrameQueue` and `FrameTiming`. Bursts from `GetNextFrame` are released, not queued. Chroma bytes `1` and `9` become format codes `2` and `4`, and any other byte becomes code `1`. A bit-depth byte of `0x10` becomes code `2`, and every other depth becomes code `1`. Format changes update depth, chroma, and colorspace immediately, and they update resolution only after five identical samples. SPS or PPS changes at a non-IDR are rejected. The jitter advance warms up for 100 frames and then clamps to ±0.075, with the absolute value forwarded to an optional callback. DJB min and max depths arrive in microseconds, scale by 1000 into nanoseconds, and are reported back with modes `QOS` or `MODE` and reasons `FIXED`, `VVSYNC`, or `UNKNOWN`. Dynamic streaming, L4S, and max bitrate are `nvbFeatureControl` types `0x0F`, `0x13`, and `0x10`. The exported `flushAndRecoverVideoStream` and `handleDJBConfigRequest` are empty. The flush that runs clears present-queue pacing state under a mutex and can recurse into a child queue. It does not send an IDR.

OpenNOW implements the dedicated Mjolnir transport, the 16-byte GameStream header, FEC/reorder recovery, and the tested private NACK-v2 encoder. Its session-start dynamic-streaming selection is RTSP-owned and respects negotiated values. The actual ANNOUNCE also filters server-owned fields from DESCRIBE, so locally defined fallback limits must not be mistaken for unconditional wire policy. These source contracts do not prove target-device or live-server acceptance.

Candidate follow-up work is narrower than copying a presenter: trace DJB force/local-adaptation interactions, the getter’s seconds-domain timing behavior, and any decoder-state-to-invalidation path. Recover wire layouts before adding server controls, and validate bounded behavior through the embedded GPU publisher and Qt scene graph. The vendor feature writes for dynamic streaming, max bitrate, and L4S are static API observations; a new OpenNOW live-setting path would need documented negotiation, failure, and recovery behavior. This audit does not establish that those changes improve quality or that a particular resolution-stability count is appropriate for Qt.

Keep transport/protocol work in the existing native transport and control owners. Keep decoder and GPU-frame ownership in the embedded platform runtime, and keep composition and surface lifetime in Qt. Do not add another Mjolnir receiver or standalone presenter to implement these hypotheses. The xDS NACK strings are unrelated to media loss recovery, and the vendor’s CEF shell is not an OpenNOW architecture template.
