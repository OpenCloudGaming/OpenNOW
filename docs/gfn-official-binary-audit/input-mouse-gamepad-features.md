# Input: mouse, gamepad, and NVB features

Official input on this Linux build is a stack of four owners, and they do not share one packet format. `libGeronimo.so` captures devices and decides policy. `libBifrost2.so` turns that policy into NVST remote-input events and into `nvbFeatureControl` feature blobs. The wire OpenNOW actually sends is `nvst_input.rs`. `docs/streamer-comparison/mouse-input.md`, `controller-input.md`, and `features.md` were written against a Windows `geronimo.log` plus an older encoder. Several of their “OpenNOW does not send this” claims are stale against the current file, and several of their Windows capture details are a different platform path from the Linux symbols in `libGeronimo.so`. The feature-type numbers in the Windows log still match the Linux format strings. The bytes of feature type 10 still are not in either string table.

## Two planes: remote input and feature control

Every gamepad sample, mouse sample, and key is an `NvstInputEvent_t`. Geronimo’s `IOInterface::handleInputEvent` and `sendNvstInputEvent` forward it. `BifrostSDKExecutor::sendNvstInputEvent` calls `nvbSendInputEvent`. The Bifrost log “Failed to execute sendInputEvent() since connection is not established” is that call before the session is up. Separately, `IOInterface::controlFeatures(NVbFeatureControlType_t, unsigned int, bool)` and `BifrostSDKExecutor::controlFeatures` call `nvbFeatureControl`. Geronimo logs “Update feature type: %d”, “%sabled feature type: %d”, and “nvbFeatureControl failed for type: %d. Error %s (%d)”. Bifrost logs “nvbFeatureControl(): NVbFeatureControlType: %d is invalid. NVB_FEATURE_MAX_TYPE = %d” and “nvbFeatureControl(). SessionIdentifier is '%s'”. The Windows log prints a heap pointer for the feature object and then the type number. That pointer is the client object. It is not a payload. The Linux strings do not add a hex dump either.

`features.md` maps the types that the Windows log actually emitted. Type 0 is toggled on every cursor-info change and is the server-composited cursor. Type 6 follows “Sending haptics state 1 to server” and is gamepad rumble. Type 8 is enabled once when the session is ready and tracks the remote cursor image. Type 10 is the line next to “Sending SDL mouse settings (accel=0, speed=10)” or “Sending alt mouse settings (accel=%d, speed=%d)”. No other type numbers appear in that log set. The Linux binary has the same verbs and adds the default-alt string below. It does not print a table of type numbers next to names, so the mapping still depends on the surrounding log line, not on a symbol named `FeatureType10`.

OpenNOW’s control header is a little-endian `u16` command, a little-endian `u16` length, then payload. `0x0308` on the wire is `08 03`. The commands that correspond to the named features are `COMMAND_MOUSE_CURSOR_CAPTURE` `0x0308` for type 0, `COMMAND_TRACK_REMOTE_CURSOR_IMAGE` `0x030d` for type 8, and remote-input type 13 under `COMMAND_REMOTE_INPUT` `0x0206` for the haptics enable that `features.md` aligns with type 6. There is no captured type 10 frame and no `0x0323` symbol in the current `nvst_input.rs`. `features.md` says the test helper used to insert a reconstructed mouse-settings command and that it must not be treated as a capture. The current `activation_chain` does not include that command at all.

## Mouse capture on this Linux binary

The Windows notes describe SDL plus a focus-gated Raw Input thread, `RIDEV_INPUTSINK`, and `WM_INPUT`. `libGeronimo.so` is the Linux client (`DVSOS = Linux` in the Bifrost build strings, and the CEF path `GFN-cx-lin-official`). Its native mouse owner is `XInput2InputController`, not Raw Input. The strings are “XInput extension not available”, “XInput minimum required version not met”, “XInput Select raw events failed with error %d”, “XInput version: %d.%d”, “initMouse: mask %x”, “XInput2InputController::resume”, and “XInput2InputController::pause”. Failure to create epoll or the signalling pipe logs “disabling native input and falling back to SDL input”. `SDLEventProcessor` is the fallback and the always-present SDL path: “Using native input controller”, “Using SDL input”, “Initialized native input controller”, “Updating SDL Event Processor to use raw events” is the Windows-log wording; the Linux binary’s equivalent switch is the native-versus-SDL pair and “Input controller failed: %s”. “SDLEventProcessor::initialize called more than once” either updates the controller or disables it. Multi-window operation logs “Uninitializing and falling back to SDL input path”.

Wayland-on-X is a third controller, `XWaylandInputController`. It confines with the X pointer grab: “Cannot confine pointer, either display or window is not set” and “XGrabPointer failed: %s (%d)”. Grab results include `AlreadyGrabbed`, `GrabFrozen`, `GrabNotViewable`, and `GrabInvalidTime`. That is the Linux analogue of the Windows note’s `ClipCursor`, which the OpenNOW Windows crate does not call. OpenNOW’s embedded Linux mouse path is XInput2 as well, and the mouse note warns that XI2 can emit buttons twice when SDL still owns buttons. Official’s fallback is explicit: if the XInput2 controller cannot start, SDL remains the only producer. Official does not run both as equal sources once the native controller is up.

`MouseAccel` is a real object in Geronimo: `s_mouseAccel`, `s_trackpadAccel`, `getMouseAccel`, `setMouseAccel`, `enableMouseAccel`, `disableMouseAccel`. The Linux client reads the host curve before it decides what to send. Failures are “Failed to retrieve mouse sensitivity: libinput properties not available”, “Failed to get mouse sensitivity from gsettings”, “Failed to retrieve mouse acceleration”, “Failed to parse mouse accel-profile from gsettings”, and “Failed to get mouse accel-profile from gsettings”. The property names in the binary are “libinput Accel Speed” and “libinput Accel Profile Enabled”. The gsettings invocation string is `gsettings get org.gnome.desktop.peripherals.mouse speed` together with `accel-profile`. So the Linux official client both reads the desktop’s libinput speed and profile and also has a separate API that enables or disables acceleration inside the process. Those are different layers. Reading gsettings does not by itself prove the host game receives that curve. The host curve is the feature-control message.

## Feature type 10, and the three log lines that bound it

`IOInterface::sendMouseSettings(bool, int)`, `SDLWindow::sendMouseSettings`, `SDLEventProcessor::sendMouseSettings` and `sendMouseSettingsIfNeeded`, and `BifrostSDKExecutor::sendMouseSettings(bool, unsigned int)` are the producers. The format strings, in one cluster, are:

`Sending SDL mouse settings (accel=0, speed=10)`

`Sending alt mouse settings (accel=%d, speed=%d)`

`Sending default alt mouse settings (accel=1, speed=10)`

The SDL line is a fixed format, accel 0 and speed 10, compiled into the string. The alt line is parameterized. The default-alt line is accel 1 and speed 10, used when the client is not applying the “acceleration off” override. The Windows log’s “Disabling session mouse acceleration” at session start, and the focus and blur lines that print `accel=0, speed=10`, match the fixed SDL string and the alt format. The Linux binary adds the accel-1 default, which the Windows notes do not quote. Bifrost’s failure strings are “Failed to %s feature mouse acceleration. Nvst Error: %s (0x%x)” and “Failed to update mouse sensitivity: %d %s (0x%x)”. `features.md` already parsed the second format: the `%d` is the speed value, and a log line “Failed to update mouse sensitivity: 10 NVST_R_SUCCESS” means speed 10 came back with a success code that the client still treated as a failed update because NVST was not ready. That `10` is not the feature type. The type is the following “nvbFeatureControl failed for type: 10”.

Nothing in the string tables is the on-wire body. There is no hex format next to `sendMouseSettings`. `features.md` records the searches that failed: no pcap, no control-frame hex, no `runtime.mouseAccel` key. The SDP and config keys that do exist nearby are `mouseMovementFlags` in Bifrost and `runtime.mouseCursorCapture` / `runtime.mimicRemoteCursor`. OpenNOW’s ANNOUNCE sets `x-nv-runtime.mouseCursorCapture:3` and `x-nv-runtime.mimicRemoteCursor:0`. Those are runtime flags in the RTSP body. They are not a substitute for the type 10 feature blob, and they do not encode accel and speed. OpenNOW’s client-side curve is `tune_relative_mouse` in the core crate, applied only when building a type 7 packet. `OPENNOW_MOUSE_SENSITIVITY` defaults to 1.0 and clamps to 0.1–3. `OPENNOW_MOUSE_ACCELERATION` defaults to 1.0, clamps to 1–150, and at 1.0 leaves the deltas unchanged. Above 1.0 the factor is `1 + min(0.6 * strength, speed/50 * strength)` with `strength = (percent - 1) / 149`, then the result is rounded and clamped to i16. `OnceLock` means the first read wins until the process restarts. Official’s logged policy is the opposite shape: raw counts on the wire, and a host-side speed of 10 with accel 0, resent on focus changes. The Linux client may have just read a non-zero libinput speed from gsettings and still send accel 0 speed 10 on the SDL path. The desktop setting and the session setting are different messages.

`docs/streamer-comparison/mouse-input.md` says the proven OpenNOW activation chain sends enable-input, cursor capture `0x0308`, cursor tracking `0x030d`, and window state 19, and that the type 10 payload is absent. That part matches `activation_chain` in the current file. The chain is eight buffers: enable input false (`0x020b`, counter 1), a device descriptor, cursor capture on, track cursor on, window state 19 (`0x0320`), system state 0 (`0x0321`), enable input true, then haptics enable. `features.md` lists seven steps and says a reconstructed mouse-settings command used to sit between tracking and window state. The current chain has no mouse-settings step, and it appends haptics as the eighth buffer. Window state 19 remains load-bearing for the reason the features note gives: an all-zero window state leaves the session looking inactive and the server withholds system-cursor updates.

## Cursor mode, lock, and NVB types 0 and 8

`SDLCursorManager` is the Linux cursor owner. The log lines are “Local cursor: %d. hasFocus: %d. fullscreen: %d, inputMode: %d, shouldLock: %d”, “updateCursor: Warping cursor to window point {%d, %d}”, “updateCursor: Update mouse control mode to %u”, “updateCursor: confining to window”, “captureCursor( %s ) succeeded” and the failure with `SDLError`, “Cannot find corresponding SDL cursor for the provided nvsc cursor id: %u”, “Receive new bitmap cursor, payload size: %u”, “Unable to decode bitmap cursor id %d”, and “Could not create a system cursor with SDL_SystemCursor %u”. “Hiding remote on NVB_SN_CURSOR_INFO_CHANGED” is the type 0 reaction: on a cursor-info change the client hides the remote cursor. “useConfinedHiddenCursorInsteadOfLocked %d for appId” is a per-app choice between confine and lock. The Windows note’s three modes (visible unlocked, visible warped, hidden locked) line up with these verbs: warp to a window point, confine, and shouldLock. The warp math in that note, `coord / 65535 * windowSize`, is the 16-bit normalized coordinate. The Linux string does not print the divisor. It prints the destination point.

OpenNOW’s inbound parser in `nvst_input.rs` reads `COMMAND_SYSTEM_CURSOR` `0x010f` and `COMMAND_BITMAP_CURSOR` `0x0110` by walking command boundaries. A system cursor with type 0 and cursor id 0 is hidden relative. The features note’s examples are `0f 01 09 00 01 00 00 00 0c 80 16 80 01` for a visible id, and `0f 01 04 00 00 00 00 00` for the lock-style id 0. The parser must not scan inside unrelated payloads for cursor-looking bytes. Bitmap notifications need an eight-byte header before they affect composition. Composition is independent of visibility: a bitmap does not unhide a hidden cursor and does not change relative mode. Capture `0x0308` is sent on at activation and requested off after the first cursor notification, or after a three-second watchdog if the host publishes nothing. Tracking `0x030d` stays on so notifications continue. Each of those commands is a one-byte payload, `00` or `01`. Official’s type 0 and type 8 are the same product behavior. The features note is explicit that OpenNOW’s command codes match the session behavior and the comments, and that they are not proven byte-identical to Geronimo’s feature blob until a capture says so.

`runtime.mimicRemoteCursor` in Bifrost is the mimic-strategy flag. The features note says `0x0322` is cursor mimic strategy, and that an earlier mapping of haptics onto `0x0322` was wrong. OpenNOW’s ANNOUNCE sets mimic to 0. Haptics enable is remote-input type 13, not that command.

## The mouse packets OpenNOW sends

`captured_input_packet` builds the native HID body. Type 7 relative is a little-endian type, then big-endian i16 dx and dy, six zero bytes, and a big-endian timestamp, 22 bytes. Type 5 absolute is x, y, a reserved u16, width, height, a reserved u32, and a timestamp, 26 bytes. Buttons are type 8 down and type 9 up, 18 bytes, button in the first body byte. Wheel is type 10, 22 bytes, with both `delta_x` and `delta_y` as big-endian i16. The mouse note’s table says the wheel’s horizontal component is always 0. The current builder writes the captured `delta_x`. A platform that never fills horizontal wheel still sends 0. The packet format itself has the field.

`remote_input_message` wraps that body in command `0x0206`. It pads the body to at least 24 bytes and to a multiple of 8, then appends one little-endian microsecond timestamp. Keys and absolute mouse get a second timestamp. Relative mouse and absolute mouse are routed `ControlPartial`. Buttons, wheel, keys, and haptics are `ControlReliable`. The mouse note says motion uses unordered partially reliable SCTP with a 300 ms lifetime and that buttons and wheel use reliable control. The current route function agrees on buttons and on relative motion, and it also places absolute motion on the partial route. The 300 ms lifetime is the ANNOUNCE attribute `x-nv-ri.partialReliableThresholdMs:300`, which matches `ri.partialReliableThresholdMs` in Bifrost. `x-nv-ri.usePartiallyReliableUdpChannel:0` leaves the UDP partial channel off. `x-nv-ri.timestampsEnabled:1` matches `ri.timestampsEnabled`.

The Windows capture note still matters for feel even though this `.so` is Linux. Official Windows Raw Input splits an i32 `lLastX` that does not fit in i16 into several type 7 samples. OpenNOW does that too, on the Windows raw-input thread. Official’s host then interprets those counts with accel 0 and speed 10. OpenNOW can scale them first with `tune_relative_mouse`. A large HID burst therefore becomes several partial-reliability packets, and a stall on the NVST event thread batches them. The 300 ms lifetime exists so an ordered replay does not show up later as a catch-up flick. Foreground filtering drops events unless the SDL or Qt window is focused. Official’s async thread is also focus-scoped: the Windows log ends the thread on unfocus and resends mouse settings, and the send often fails. The Linux XWayland path confines with `XGrabPointer` instead. OpenNOW’s Windows crate has no `ClipCursor` and no `RIDEV_NOLEGACY`.

Queue capacity 256 and a drain of up to 32 samples per tick are the OpenNOW capture notes, not strings in Geronimo. Geronimo’s SDL event loop logs “SDLProcessEvent: pollTime: %ldus” and “procTime: %ldus”, which is the same kind of budget, without a published cap in the string table.

## Gamepad capture, aggregation, and the four-slot limit

`SDLGamepad` is the device owner. It logs “Loaded %d gamepad mappings”, “Opened controller named %s with vendor id %x product id %x at index %d”, “Skipping SDL gamepad for device %04x:%04x at SDL index %d”, “Controller named %s is already opened”, “Closed a controller named %s”, “Could not find controller at index %d”, and “Max %d controllers are supported”. The embedded mapping database announces “# Game Controller DB for SDL in 2.0.10 format” and includes the usual VID/PID lines, among them Sony DualSense entries for Windows, Mac, and Linux. The Windows session note counted 858 mappings and an Xbox One controller at VID 045E PID 02FF. The Linux binary contains that same database text. “SDL: Failed to init game controller / haptic subsystem” is the startup failure. Hints `SDL_JOYSTICK_HIDAPI_PS4_RUMBLE` and `SDL_JOYSTICK_HIDAPI_PS5_RUMBLE` turn on HIDAPI rumble for those pads.

Above SDL, `Gamepad` aggregates. The methods are `queueEvent`, `flushAggregatedEvents`, `scheduleAggregationTimer`, `updateAggregationTimer`, `eventLoopDidTurn`, `flushState`, `buildGamepadBitmap`, `getPlugState`, and `onConfigurationChanged`. Settings hooks are `GeronimoSettingsImpl::overrideGamepadAggregateInterval` and `overrideGamepadDestructiveAggregation`, and the config key `enablePartiallyReliableTransferGamepad`. Destructive aggregation means a later sample replaces an earlier one inside the interval instead of sending both. The interval override is a duration in the settings object. OpenNOW does not have this timer. It sends on SDL `ControllerAxisMotion` and `ControllerButton` events, and it resends the last type 12 state every 100 ms so a quiet pad does not look unplugged. Official’s aggregate interval is the thing that can coalesce a stick sweep into fewer packets. OpenNOW’s keepalive is the thing that prevents the game from reverting to keyboard prompts. They solve different failures. A destructive aggregate that drops intermediate stick positions will feel like a lower poll rate. A missing keepalive will feel like the pad disconnected.

Four slots are hard. Geronimo logs “not supported: more than 4 gamepads connected” and `getGamepadState` fills `std::array<NvstGamepadStateEvent_t, 4>`. `RIDeviceMediator` assigns identity: `getNextId`, `handleNewGamepad`, `getGamepadEffectiveIndex`, `getGamepadIndexFromXinputEffectiveIndex`, `getGamepadIndexFromHidId`, `getGamepadMechanism`, `shouldForwardGamepad_Locked`, and `reInitializeGamepads`. The log line “%s: standard gamepad at effective ID: %d” is the Windows note’s “standard gamepad at effective ID: 0”. “%s: matched nvstId=%d at effective id=%u” and “%s: synthesizing nvstId=%d at effective id=%d” are the synth path. “Invalid gamepad mechanism (%d) for gamepad %d (effective %d)” is the failure. “Unhandled %s gamepad[%u], vid=%04x, pid=%04x” is an unrecognized device. Telemetry is “Sending gamepad telemetry for id %d, state: %d, eventMap: %s” with labels `_L1`, `_R1`, `_TL`, `_TR`, `_LT`, `_RT`, `_DY`, `_DX`, `_ST`, `_SE`, `_LS`, `_RS`.

OpenNOW’s native pad owner is SDL game controller as well, first-come slots 0–3, unmapped joysticks ignored. The bitmap always sets both the connected bit and the Xbox bit for every occupied slot. Guide, screenshot, recording toggle, and shortcuts produce an empty packet in `captured_input_packet`, so Guide stays local. SDL Misc1, touchpad, and paddles are dropped on the native path the controller note describes. `enableGyroscopeControls` is stored and unread. Official’s DualSense path is the opposite: gyro and touch are HID reports, not SDL axes, and they go through the synthesizer below.

## HID synthesis, GSHID, and the Linux raw-USB gap

`GamepadHIDSynthesizer` parses and builds DualShock state: `parseDS4Report`, `parseGamepadHidOutput`, `extractGamepadId`, `buildSynthesizedDS4State`, and `buildSynthesizedGamepadState`. `RIDeviceMediator` gates it with `serverSupportsDS4`, `supportSynthesizedDS4`, `allowSynthesizedDS4`, `allowSynthesizedDS5`, `allowCrossSynthDS5ToDS4`, `allowCrossSynthDS4ToDS5`, `allowCrossSynthGenericToDS4`, `allowCrossSynthGenericToDS5`, and `configureDualSenseController`. Debug config can disable synth per direction: `isSynthesizedDS4Disabled`, `isSynthDS4FromDS5Disabled`, `isSynthDS5FromDS4Disabled`, `isSynthDS4FromGenericEnabled`, `isSynthDS4AllGamesEnabled`. The log “Configuring server supported Hid devices: Supports DS4: %s, DS5: %s (raw:%x)” is the server capability. “%sabling GSHID” is the client switch. “%s: DualSense controller is %shandled” records whether that pad is on the synth path. “Invalid device for synthesizing HID report: [%04x:%04x]” is the refusal. The Windows session note says DualShock synth was allowed and generic-to-DS synth was off, with `synthesizeGamepadHid: true` in remote config. Those are the same keys.

Bifrost still has a platform hole: “No implementation to handle USB gamepad raw input on this platform.” On Linux, raw USB gamepad input is not implemented inside the NVST mapper, so Geronimo’s SDL-plus-synthesizer path is how a DS4 becomes an `NvstInputEvent`. `RiNvscGamepadMapper` logs “Unrecognized axis control”, “Unrecognized trigger control”, “Unrecognized button control”, and “Unrecognized gamepad event” when a report does not map. “Gamepad ID %u is invalid” is the slot check. Partially reliable stats for the gamepad channel are “RI gamepad_channel_v1 stats: m_highestSequenceNumber, m_packetsLostCount, m_packetsDroppedCount” and a second line for `devId` and `channelId`. The config keys are `ri.enablePartiallyReliableTransferGamepad`, `ri.enablePartiallyReliableTransferHid`, and `ri.usePartiallyReliableUdpChannel`. OpenNOW’s ANNOUNCE sets gamepad partial reliability to 255, HID partial reliability to -1, and the UDP partial channel to 0. The value 255 is the all-slots mask the attribute expects. It does not mean “256 controllers”.

`SDLGamepadRSDMM` is a gesture layer on top of the pad. It parses `NvstGamepadStateEvent_t`, ticks a timer, detects a debug toggle gesture, and can `sendMouseButtonEvent`. `IOInterface::setGamepadRsdmm` and `GridApp::setGamepadRsdmm` enable it. `enableRsdmmToggle` sits in the same config blob as `synthesizeGamepad`. This is how a pad click becomes a mouse button without a type 7 packet from the physical mouse. OpenNOW has no RSDMM object. Stick-as-dpad thresholds in the Qt shell poller are a different feature, and that poller is gated off on the stream route.

## The 38-byte type 12 packet, as built now

`captured_input_packet` for `CapturedInput::Gamepad` writes 38 bytes. Little-endian type 12, little-endian payload length 26, little-endian controller id masked with `0x03`, little-endian bitmap, a constant 20, buttons, triggers packed as left in the low byte and right in the high byte, four little-endian stick axes, a zero u16, the constant 85, another zero u16, and a little-endian timestamp. Byte offset 6 is the controller id. The controller note’s layout matches this builder: type, payload 26, slot, bitmap, buttons, triggers, sticks, magic 85, timestamp.

`gamepad_command` wraps those 38 bytes rather than picking fields out. The payload starts with marker `0x23`, an 8-byte big-endian timestamp, marker `0x26` plus `packet[6]` (the low byte of the controller id), a big-endian sequence, marker `0x21`, a big-endian length 38, then the entire 38-byte packet. Command code is `0x020d`. The controller note says the NVST body hardcodes inner index `0x03` and does not copy `controller_id` or the bitmap. That described an older encoder. The current wrapper copies `packet[6]` into the `0x26` field and then copies all 38 bytes, so the slot and the bitmap travel inside the packet even though the outer field repeats the low id byte. Multi-pad identity is on that wire to the extent the 38-byte layout carries it. `x-nv-ri.useMultipleGamepads:1` is the ANNOUNCE flag, matching Bifrost’s `ri.useMultipleGamepads`.

The first gamepad still sends a device descriptor on reliable control. Updates go out as `COMMAND_GAMEPAD`. Partially reliable versus reliable for those updates follows the input route the encoder chooses for gamepad traffic. Motion-class mouse is the route documented as partial. Gamepad reliability is the 255 mask in ANNOUNCE plus the Bifrost channel stats, which count both lost and dropped packets on `gamepad_channel_v1`. A drop on that channel is why the 100 ms keepalive exists: a lossy partial send of a stick position must be repaired by a later full state, not by a retransmission of every intermediate aggregate.

## Haptics: feature type 6, remote-input type 13, and Sony output

Geronimo logs “enable haptic state” and “disable haptic state” from `SDLGamepad` / `Gamepad::updateHapticState`. `playHaptic` takes a device and two integer arguments. `isHapticEvent` classifies an SDL event. The Windows note’s sequence is enable haptic state, then “Sending haptics state 1 to server”, then feature type 6, with telemetry `hapticsSupported` and `hapticsFeedbackCount`. Bifrost’s failure line is “Failed to %s feature gamepad haptics. Nvst Error: %s (0x%x)”. `x-nv-runtime.hapticsState` is the SDP key. Inbound HID output is `NVbEventData_t::_HidOutputEvent`, parsed by `parseGamepadHidOutput`. That is the server telling the client to rumble a synthesized DS4. The Linux mapper can still log that USB raw input has no implementation, so a rumble that depends on a raw USB write may stop at SDL `playHaptic` instead.

OpenNOW sends the enable flag. `INPUT_HAPTICS_ENABLED` is type 13. `haptics_state` packs a little-endian u16, 0 or 1, into the remote-input envelope on `0x0206`, reliable, with the timestamp suffix. `activation_chain` sends enabled true after input is enabled. Disable uses body `00 00`. `features.md` matches this to NVB type 6 and points at the Mac reference’s `hapticsState` framing. The test `haptics_disable_uses_remote_input_envelope_and_preserves_timestamp` locks the disable vector. Sending the enable flag is the feature-control equivalent. It is not the rumble sample itself.

Rumble samples are a second path in `nvst_haptics.rs`. `NvstHaptics` stores per-slot low and high frequency, including Sony rumble tagged with a slot and an incarnation, and coalesces pending commands. Sony HID reports have their own commands in `nvst_input.rs`. `sony_device_change_command` sends remote-input type `0x12` with a low id, an attach code 1 or a removal code 3, and `SONY_DEVICE_CHANGE_FLAGS`. `sony_report_command` sends command `0x020d` with marker `0x22`, type `0x11`, the low id, the DS4 interface number, and a fixed-size DS4 report. `parse_sony_output` and `for_each_sony_output` walk inbound `0x0206` payloads for type `0x11` and deliver the output report to that low id. Low ids are checked against `DS4_LOW_ID_BASE` and `MAX_SOURCES`. This is the OpenNOW equivalent of Geronimo’s HID output event and DS4 synthesizer, scoped to the DS4 report size the hid crate defines. The controller note’s “OpenNOW has no GSHID synthesizer” and “never applies rumble” describe the older SDL-only type 12 path. The current transport can enable haptics, store Sony motor state, and exchange DS4-shaped HID reports. A generic Xbox pad still rides the 38-byte type 12 packet. `SDL_JOYSTICK_HIDAPI_PS5_RUMBLE` on the official side has a DualSense-specific synth (`configureDualSenseController`, cross-synth DS4/DS5) that this DS4 report path does not cover by itself.

## Activation, keepalive, and the frames that are byte-checked

The activation order in the current `activation_chain` is the contract a session must see before gameplay input is accepted. Enable input false uses `0x020b` with three little-endian u32 fields: stream index 0, counter 1, enabled 0. The device descriptor is `0x020d`. Cursor capture on is `08 03 01 00 01`. Track cursor on is `0d 03 01 00 01`. Window state 19 is `0x0320` with state `13 00 00 00`. System state 0 is `0x0321`. Enable input true repeats `0x020b` with enabled 1. Haptics true follows. Keepalive `0x0200` is a 4-byte stream value, sent on the control interval the transport uses (the features note says every 3 seconds for `control_keepalive(0)`, which is `00 02 04 00 00 00 00 00`). The input handshake is ready when reliable control delivers version 3: `0e 02 02 00 03 00`, command `0x020e`, length 2, version 3.

`features.md` prints a relative-mouse test vector under `0x0206` with inner type 7, dx 24, dy 24, and a timestamp, and a key-down vector for virtual key `0x41`. Those vectors are the byte-exact checks. They are the right source for “what OpenNOW sends”. Geronimo’s logs are the right source for “what official says it sent”. The gap between them is type 10. Official’s Linux and Windows binaries both format accel and speed and then call `nvbFeatureControl`. OpenNOW’s activation chain does not send a mouse-settings command. Aim feel differs for that reason even when type 7 deltas are otherwise the same integers: the host still has whatever accel and speed it booted with, while official has just told it accel 0 and speed 10, and will tell it again on the next focus change. The Linux client may also have confined the pointer with `XGrabPointer` or fallen back to SDL if XInput2 failed, and it may have read a libinput speed that it then overrides with the session message. OpenNOW’s Windows raw-input thread can still multiply the delta by `tune_relative_mouse` before the host sees it.

Cursor lock differs in the same way. Official reacts to system cursor id 0 with shouldLock, a local cursor of 0, and a hide, and it warps other ids from normalized coordinates. It can choose confine instead of lock per app id. OpenNOW treats predefined type 0 id 0 as hidden relative, enters relative mode, and uses capture plus tracking commands whose payloads are known and whose equality to Geronimo’s feature blob is not captured. Bitmap cursors update composition only.

Gamepad feel differs in aggregation, identity, and HID. Official can destructively aggregate inside an override interval, synthesize a DS4 from another pad when the remote config allows it, assign an effective index distinct from the XInput index, and send haptics as feature type 6 with HID output coming back. OpenNOW sends a full 38-byte state that includes the slot, repeats that slot’s low byte in the `0x26` wrapper, keepalives every 100 ms, advertises four-pad partial reliability as 255, enables haptics with type 13, and can carry DS4 HID reports on the Sony commands. It does not run GSHID generic-to-DS4 synthesis, does not read `enableGyroscopeControls`, and does not implement RSDMM. A fifth pad is dropped on both clients. A quiet pad is not an idle wire on OpenNOW. On official, an aggregated empty interval is whatever `flushAggregatedEvents` decides, and the gamepad channel stats will show drops separately from losses.

The strings that should not be turned into a packet are the ones that only name a policy. `accel=0, speed=10` is a format string. `Update feature type: %d` is a type number. `nvbFeatureControl( <pointer> )` is an object. `Failed to update mouse sensitivity: %d` is the speed argument. Until a capture shows the feature blob, the honest implementation state is the one `features.md` already states for type 10: the log proves the meaning, and the current encoder does not send a guessed body.
