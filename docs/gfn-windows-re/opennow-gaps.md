# OpenNOW gaps against the Windows client

This list compares OpenNOW `dev` at `7ce3cd54` (after PRs #1162, #1164 and #1165 merged) with the Windows GFN client 2.0.89.141. Entries distinguish implementation differences, deliberate choices, regression coverage, and negotiation unknowns. A Windows final config value does not establish an ANNOUNCE wire value. "Not found" means a repository search found no handling in the relevant Qt/native owner; read the code before acting on it.

Priority: **P1** affects what users see, hear or whether a session survives. **P2** is correctness or robustness. **P3** is parity or diagnostics.

## Existing handling and evidence limits

Windows observations agree with these OpenNOW baseline mechanisms:

- Ping version 6 and 20/100 ms ping intervals; RTSP over WSS with `wssignaling=1`.
- A partially reliable input channel with a 300 ms lifetime. Not every input event uses that lane.
- A dedicated video socket with audio, mic and data on the bundle in the observed non-unified NVIDIA shape. Explicit media mappings and the peerless-SETUP bundle fallback have separate routing rules (T8).
- Omission of V1 ICE/DTLS keys from ANNOUNCE: `opennow-streamer-core/src/nvst_rtsp.rs:1580-1586` writes only the `*V2` keys and standard ICE/fingerprint lines. Accepting V1 fields in DESCRIBE is a separate boundary.

Keep these comparisons qualified:

- **NACK:** 52 ms retention, 4 ms extra retry delay and 64-packet batches match the observed constants. Identical record and retry-count semantics are not established: OpenNOW keeps 16 pending missing ranges and evicts the oldest (`opennow-streamer-transport/src/nvst.rs:845-878`), while Windows logs a 2,048-record NACK limit. The 1,024-packet RTP reorder window is a separate queue. `MAX_NACK_ATTEMPTS=3` counts total sends with an RTT-dependent cap (`1213-1259`), not a demonstrated three retries after the initial send. The explicit 1 ms initial guard is absent (T4).
- **Chroma, proved serialization difference:** CloudMatch JSON's HEVC `10bit_444` request uses flags 1/1. S6's Bifrost config instead has depth/chroma **10/1**. Windows ANNOUNCE field sites `0x1804ef015` and `0x1804ef513` call unchanged-byte writer `0x1803f7970`; comparison with DESCRIBE controls omission. OpenNOW writes depth 8/10 and chroma 1/3 (`nvst_rtsp_color.rs:15-29`; `nvst_rtsp_color_tests.rs:16-31`). Its depth 10 agrees; 4:4:4 chroma 3 differs from Windows 1. Server acceptance and which changed keys S6 sent remain unknown. JSON flags do not establish the SDP encoding.
- **4:4:4:** OpenNOW selects HEVC when capabilities support the requested 4:4:4 format; otherwise it reduces the color format rather than force an unsupported codec (`native/opennow-core/src/streamer.rs:478-499`).
- **RFI:** OpenNOW already withholds dependent frames and handles recovery (`opennow-streamer-transport/src/nvst_invalidation.rs:169-227`). Windows normal 0x301, IDR 0x302, separate NvWac 0x30c and active retry policy are now traced; T7 concerns the narrower policy and negotiation differences.

## Newly recovered transport differences

These refine the stable rows above rather than invent new gap IDs:

- Windows DCEP advertises count-limited partial reliability for ordered control and one retransmission for unreliable control. OpenNOW's advertised reliability, protocol and priority values differ. Per-message overrides mean OPEN policy does not describe every packet. See [handshake.md](handshake.md).
- Windows v9 outcome acknowledgements distinguish decode failures, skipped decode, invalid references and missing presentation. Network frame assembly alone cannot populate that record (T9).
- Windows handles idle timer 0x118, pacing 0x112, QoS notification 0x122 and termination 0x109 in the command dispatcher. PingBackACK admission fails terminally on the third failed send (`0x180247620`), not on a proved missing response. See [transport-feedback.md](transport-feedback.md) for lengths and source addresses (T2/T3).
- The Windows NACK builder accepts version 2 only, copies entries without sorting and emits the first 64. Its pending ledger is 2048; this is not OpenNOW's 16-range ledger or the separate 1024-packet receive queue. Equal logged settings do not prove equal total-send/retry policy (T4).
